**E-008 Архитектура процессов и координация сервисов**

**Версия:** 1.0

**Статус:** Approved

**Раздел:** E — Engineering Architecture

**1. Scope**

Настоящий документ определяет архитектуру управления рабочими процессами платформы Simple Solutions Practice.

Документ описывает:

- модель Workflow;

- модель Task;

- управление жизненным циклом процессов;

- взаимодействие Human Workers и Cognitive Workers;

- архитектуру оркестрации;

- требования к надёжности и воспроизводимости.

**2. Workflow Principles**

Workflow представляет собой управляемый процесс выполнения работы.

Workflow не является бизнес-логикой.

Он координирует выполнение бизнес-операций.

**WF-001**

Workflow состоит из последовательности Task.

**WF-002**

Каждый Task выполняется одним Worker.

Исполнителем может быть:

- Human Worker;

- Cognitive Worker.

**WF-003**

Workflow не содержит бизнес-правил.

Все бизнес-правила реализуются в Domain Layer.

**WF-004**

Workflow управляет:

- последовательностью выполнения;

- зависимостями;

- передачей Task;

- ожиданием событий;

- обработкой ошибок.

**WF-005**

Workflow является воспроизводимым.

При одинаковых входных данных и одинаковой последовательности событий результат выполнения должен быть одинаковым.

**Архитектурное правило**

Workflow управляет выполнением работы.

Business Rules управляют принятием решений.

**3. Workflow Position**

Workflow Engine является инфраструктурным компонентом Platform Kernel.

Platform Kernel

Platform API

Workflow Engine не содержит бизнес-логики.

Он использует сервисы Platform Kernel для выполнения операций.

**Архитектурное правило**

Workflow является механизмом координации, а не механизмом принятия решений.

**4. Workflow Lifecycle**

Каждый Workflow проходит полный жизненный цикл.

**WL-001**

Создание.

**WL-002**

Инициализация.

**WL-003**

Выполнение.

**WL-004**

Ожидание событий.

**WL-005**

Продолжение выполнения.

**WL-006**

Завершение.

**WL-007**

Архивирование.

**Архитектурное правило**

Workflow является долгоживущей сущностью платформы.

**5. Workflow Identity**

Каждый Workflow имеет собственную идентичность.

**WI-001**

Workflow имеет уникальный Workflow ID.

**WI-002**

Каждый экземпляр Workflow имеет собственное состояние.

**WI-003**

Workflow может существовать независимо от подключённых пользователей.

**WI-004**

Workflow сохраняет своё состояние между этапами выполнения.

**WI-005**

Все действия Workflow журналируются.

**Архитектурное правило**

Workflow является самостоятельным объектом Platform Kernel.

**6. Workflow State Model**

Каждый Workflow рассматривается как конечный автомат (Finite State Machine).

Состояние Workflow определяется исключительно текущим состоянием и поступающим событием.

**WS-001**

Workflow всегда находится ровно в одном состоянии.

**WS-002**

Переход между состояниями выполняется только по событию.

**WS-003**

Прямое изменение состояния Workflow запрещается.

Все переходы должны быть зарегистрированы Platform Kernel.

**WS-004**

Каждый переход сопровождается записью в журнал событий.

**WS-005**

История переходов является неизменяемой.

**Архитектурное правило**

Workflow развивается посредством последовательности состояний, а не изменения своего прошлого.

**7. Workflow Events**

Событие является единственным механизмом изменения состояния Workflow.

**WE-001**

Событие публикуется Platform Kernel.

**WE-002**

Каждое событие имеет:

- Event ID;

- Event Type;

- Timestamp;

- Correlation ID;

- Source;

- Payload.

**WE-003**

Событие не изменяется после публикации.

**WE-004**

Одно событие может инициировать несколько независимых Workflow.

**WE-005**

Workflow реагирует только на события, явно определённые в его конфигурации.

**Архитектурное правило**

Workflow управляется событиями, а не вызовами методов.

**8. Task Scheduling**

Workflow Engine отвечает за назначение Task исполнителям.

**TS-001**

Каждый Task назначается одному Worker.

**TS-002**

Назначение выполняется Platform Kernel.

**TS-003**

Worker может принять либо отклонить Task в соответствии с политиками платформы.

**TS-004**

Неназначенные Task помещаются в очередь ожидания.

**TS-005**

Все назначения и переназначения журналируются.

**Архитектурное правило**

Task принадлежит Workflow, а не Worker.

**9. Waiting States**

Workflow может переходить в состояние ожидания.

**WT-001**

Причинами ожидания могут быть:

- внешнее событие;

- завершение Task;

- подтверждение Human Worker;

- завершение Cognitive Task;

- наступление заданного времени.

**WT-002**

В состоянии ожидания Workflow не потребляет вычислительные ресурсы, кроме ресурсов, необходимых для хранения его состояния.

**WT-003**

Возобновление Workflow выполняется только после получения соответствующего события.

**WT-004**

Истечение времени ожидания генерирует системное событие Timeout.

**WT-005**

Переход в состояние ожидания и выход из него фиксируются в журнале.

**Архитектурное правило**

Ожидание является штатным состоянием Workflow, а не исключительной ситуацией.

**10. Task Ownership**

Каждый Task имеет одного владельца.

Владелец отвечает за достижение результата независимо от того, кто является непосредственным исполнителем.

**TO-001**

Owner определяется при создании Task.

**TO-002**

Owner может быть:

- Human Worker;

- Cognitive Worker;

- Workflow.

**TO-003**

Исполнитель Task может изменяться без изменения Owner.

**TO-004**

Передача Task другому Worker не изменяет ответственность Owner.

**TO-005**

Изменение Owner допускается только посредством явной операции Platform Kernel.

**Архитектурное правило**

Ответственность принадлежит Owner.

Исполнение принадлежит Worker.

**11. Task Queue**

Все ожидающие выполнения Task размещаются в очередях платформы.

**TQ-001**

Очереди являются логическими сущностями Platform Kernel.

**TQ-002**

Task может находиться только в одной очереди одновременно.

**TQ-003**

Очередь определяется:

- типом Task;

- Workspace;

- приоритетом;

- политиками платформы.

**TQ-004**

Platform Kernel самостоятельно выбирает следующую задачу для назначения.

**TQ-005**

Worker не взаимодействует с очередью напрямую.

**Архитектурное правило**

Workers получают Task от Platform Kernel.

Workers не извлекают Task самостоятельно.

**12. Prioritization**

Все Task имеют уровень приоритета.

**PR-001**

Приоритет определяется политиками платформы.

**PR-002**

Изменение приоритета журналируется.

**PR-003**

Высокий приоритет не отменяет требований безопасности и бизнес-правил.

**PR-004**

Platform Kernel может изменять порядок назначения Task на основании приоритетов.

**PR-005**

Приоритет влияет только на порядок выполнения.

Он не изменяет бизнес-смысл Task.

**Архитектурное правило**

Приоритет управляет временем выполнения, а не логикой процесса.

**13. Escalation**

Если Task не может быть выполнен в установленные сроки, запускается процедура эскалации.

**ES-001**

Причинами эскалации могут быть:

- превышение времени выполнения;

- отсутствие доступного Worker;

- неоднократный отказ от выполнения;

- системная ошибка.

**ES-002**

Эскалация оформляется как событие Platform Kernel.

**ES-003**

Политики эскалации определяются конфигурацией платформы.

**ES-004**

Эскалация может привести к:

- переназначению Task;

- уведомлению Owner;

- уведомлению Supervisor;

- запуску компенсационного Workflow.

**ES-005**

Все случаи эскалации фиксируются в Audit Service.

**Архитектурное правило**

Эскалация является штатным механизмом управления процессами.

**14. Retry Policy**

Повторное выполнение Task осуществляется по управляемым политикам.

**RP-001**

Повтор допускается только для операций, объявленных повторяемыми (Retryable).

**RP-002**

Количество повторов ограничивается конфигурацией платформы.

**RP-003**

Между повторами может использоваться задержка или стратегия Backoff.

**RP-004**

Каждая попытка выполнения фиксируется как отдельное событие.

**RP-005**

Исчерпание лимита повторов инициирует событие Failure и передаёт управление Workflow.

**Архитектурное правило**

Повтор является осознанной стратегией выполнения, а не бесконечным циклом.

**15. Work Contract**

Каждый Task создаётся на основании неизменяемого Work Contract.

Work Contract определяет обязательства между Platform Kernel и исполнителем Task.

**WCN-001**

Work Contract создаётся одновременно с Task.

**WCN-002**

Work Contract содержит:

- Task ID;

- Owner;

- Assigned Worker (при наличии);

- описание работы;

- ожидаемый результат;

- критерии завершения;

- срок выполнения;

- уровень приоритета;

- политики выполнения.

**WCN-003**

После создания Work Contract не изменяется.

Изменение требований приводит к созданию нового Task и нового Work Contract.

**WCN-004**

Все изменения состояния Task выполняются в рамках соответствующего Work Contract.

**WCN-005**

Work Contract хранится в истории платформы и доступен для аудита.

**Архитектурное правило**

Task является процессом выполнения.

Work Contract является неизменяемым соглашением о работе.

**16. Task Completion**

Task считается завершённым только после проверки результата.

**TCM-001**

Завершение Task инициируется Worker.

**TCM-002**

Platform Kernel проверяет выполнение обязательных условий завершения.

**TCM-003**

При успешной проверке Task получает статус Completed.

**TCM-004**

При невыполнении условий Task возвращается в состояние Active или Escalated в соответствии с политиками платформы.

**TCM-005**

Workflow получает событие только после окончательного завершения Task.

**Архитектурное правило**

Task завершается не по заявлению исполнителя, а по подтверждению Platform Kernel.

**17. Compensation**

Не все операции могут быть отменены.

Вместо отката платформа использует компенсационные действия.

**CMP-001**

Компенсация представляет собой отдельный Task.

**CMP-002**

Компенсационный Task имеет собственный Work Contract.

**CMP-003**

Компенсация не изменяет историю выполнения исходного Task.

**CMP-004**

Компенсационный Workflow выполняется независимо от исходного процесса.

**CMP-005**

Все компенсационные действия журналируются.

**Архитектурное правило**

История не изменяется.

Ошибки компенсируются новыми действиями.

**18. Workflow Recovery**

Platform Kernel обеспечивает восстановление Workflow после сбоя.

**WR-001**

Состояние Workflow регулярно сохраняется.

**WR-002**

После восстановления Platform Kernel продолжает выполнение с последнего подтверждённого состояния.

**WR-003**

Повторное выполнение уже подтверждённых переходов запрещается.

**WR-004**

Все операции восстановления фиксируются в журнале событий.

**WR-005**

Recovery не изменяет историю Workflow.

**Архитектурное правило**

Восстановление продолжает выполнение процесса.

Оно не переписывает его историю.

**19. Workflow Governance**

Workflow находится под управлением Platform Kernel на протяжении всего жизненного цикла.

Workflow Engine отвечает только за исполнение процесса.

**WG-001**

Platform Kernel является владельцем состояния Workflow.

**WG-002**

Workflow Engine не изменяет бизнес-состояние самостоятельно.

**WG-003**

Все изменения состояния Workflow выполняются через Platform Kernel.

**WG-004**

Workflow Engine не принимает бизнес-решений.

**WG-005**

Platform Kernel обеспечивает целостность выполнения Workflow.

**Архитектурное правило**

Workflow Engine исполняет.

Platform Kernel управляет.

**20. Workflow Versioning**

Каждый Workflow имеет собственную версию.

**WV-001**

Версия Workflow определяется при публикации.

**WV-002**

После публикации Workflow становится неизменяемым.

**WV-003**

Изменение Workflow требует публикации новой версии.

**WV-004**

Новые экземпляры Workflow создаются только на основе последней опубликованной версии, если иное не определено политиками платформы.

**WV-005**

Уже выполняющиеся Workflow продолжают работу на той версии, на которой были созданы.

**Архитектурное правило**

Выполняющийся Workflow никогда не меняет собственную версию.

**21. Workflow Migration**

Переход выполняющихся Workflow на новую версию является управляемой операцией.

**WMG-001**

Миграция выполняется только Platform Kernel.

**WMG-002**

Миграция допускается только при наличии явно определённых правил совместимости.

**WMG-003**

При невозможности безопасной миграции Workflow завершает выполнение на исходной версии.

**WMG-004**

Все операции миграции журналируются.

**WMG-005**

Миграция не должна нарушать целостность Work Contract.

**Архитектурное правило**

Стабильность процесса важнее использования последней версии.

**22. Workflow Templates**

Workflow публикуются в виде шаблонов.

**WTPL-001**

Шаблон Workflow описывает структуру процесса.

**WTPL-002**

Экземпляр Workflow создаётся на основании шаблона.

**WTPL-003**

Изменение экземпляра Workflow не изменяет шаблон.

**WTPL-004**

Шаблоны являются версионируемыми артефактами платформы.

**WTPL-005**

Все шаблоны проходят стандартный жизненный цикл публикации и утверждения.

**Архитектурное правило**

Шаблон описывает процесс.

Экземпляр выполняет процесс.

**23. Case Lifecycle**

Case является основной бизнес-сущностью, жизненный цикл которой управляется Workflow.

**CL-001**

Каждый Case имеет уникальный идентификатор.

**CL-002**

Case содержит:

- идентичность;

- состояние;

- связанные Workflow;

- Work Contracts;

- Tasks;

- Artifacts;

- Decisions;

- Audit History.

**CL-003**

Case существует независимо от конкретного Workflow.

Несколько Workflow могут последовательно или параллельно работать с одним Case.

**CL-004**

Изменение состояния Case выполняется только Platform Kernel.

**CL-005**

История изменений Case является неизменяемой.

**Архитектурное правило**

Workflow обслуживает Case.

Case является долговременной бизнес-сущностью платформы.

**24. Workflow Outcome**

Результатом выполнения Workflow является изменение состояния Case.

**WO-001**

Workflow не создаёт бизнес-результат напрямую.

**WO-002**

Workflow завершает выполнение одним из следующих исходов:

- Completed;

- Cancelled;

- Failed;

- Compensated.

**WO-003**

После завершения Workflow Platform Kernel обновляет состояние Case в соответствии с Business Rules.

**WO-004**

Workflow не изменяет состояние Case самостоятельно.

**WO-005**

Все изменения состояния Case оформляются как отдельные события платформы.

**Архитектурное правило**

Workflow завершается.

Case продолжает жить.

**25. Parallel Execution**

Workflow может содержать независимые ветви выполнения.

**PE-001**

Параллельные ветви создаются Platform Kernel.

**PE-002**

Каждая ветвь имеет собственные Task и собственное состояние выполнения.

**PE-003**

Объединение ветвей выполняется только после выполнения условий синхронизации.

**PE-004**

Ошибка одной ветви не должна автоматически завершать остальные ветви, если это не определено политикой Workflow.

**PE-005**

Состояние каждой ветви журналируется независимо.

**Архитектурное правило**

Параллельность является свойством Workflow, а не отдельных Workers.

**26. Synchronization**

Workflow поддерживает управляемую синхронизацию результатов.

**SY-001**

Синхронизация выполняется Platform Kernel.

**SY-002**

Условия синхронизации определяются шаблоном Workflow.

**SY-003**

Синхронизация может ожидать:

- завершения всех ветвей;

- завершения любой ветви;

- достижения заданного количества результатов;

- наступления события.

**SY-004**

Несогласованные результаты не изменяют состояние Case до завершения процедуры синхронизации.

**SY-005**

Результат синхронизации оформляется как отдельное событие.

**Архитектурное правило**

Все объединения результатов являются явными и управляемыми.

**27. Workflow Observability**

Все Workflow являются полностью наблюдаемыми.

**WO-001**

Для каждого Workflow доступны:

- текущее состояние;

- история переходов;

- активные Task;

- ожидаемые события;

- связанные Work Contracts;

- связанные Workers.

**WO-002**

Platform Kernel публикует основные метрики Workflow.

Минимальный набор включает:

- количество активных Workflow;

- количество завершённых Workflow;

- среднее время выполнения;

- количество ошибок;

- количество компенсаций;

- количество эскалаций.

**WO-003**

Каждый Workflow поддерживает трассировку по Correlation ID.

**WO-004**

Все изменения состояния Workflow доступны для анализа средствами мониторинга платформы.

**WO-005**

Workflow не содержит скрытых внутренних состояний.

Все значимые изменения должны быть наблюдаемыми.

**Архитектурное правило**

Любой Workflow должен быть полностью диагностируемым.

**28. Workflow Principles**

Архитектура Workflow SSP основана на следующих принципах.

1.  Workflow координирует работу, но не содержит бизнес-логики.

2.  Platform Kernel управляет жизненным циклом Workflow.

3.  Workflow развивается посредством событий.

4.  Task является единицей работы.

5.  Work Contract является неизменяемым обязательством.

6.  Worker является исполнителем, Owner — ответственным.

7.  История выполнения никогда не изменяется.

8.  Ошибки компенсируются новыми действиями.

9.  Все процессы являются воспроизводимыми.

10. Все процессы являются наблюдаемыми.

**29. Workflow Philosophy**

Платформа рассматривает Workflow как механизм организации интеллектуальной и операционной работы.

Workflow не управляет людьми.

Workflow не управляет Cognitive Workers.

Workflow организует выполнение работы между участниками цифровой организации.

Platform Kernel обеспечивает единые правила взаимодействия всех участников независимо от их природы.
