**E-014 Архитектура рабочих модулей**

**Версия:** 1.0

**Статус:** Draft

**Раздел:** E — Engineering Architecture

**1. Scope**

Настоящий документ определяет архитектурную модель модулей платформы Simple Solutions Practice.

Модуль является основной единицей функционального развития платформы.

**2. Module Principles**

Функциональность платформы реализуется посредством независимых модулей.

Каждый модуль представляет собой изолированную область ответственности.

**MP-001**

Каждый модуль реализует ограниченную бизнес-функцию.

**MP-002**

Каждый модуль взаимодействует с Platform Kernel посредством архитектурных контрактов.

**MP-003**

Модуль не зависит от внутренней реализации других модулей.

**MP-004**

Модуль может заменяться без изменения Platform Kernel.

**MP-005**

Каждый модуль обладает собственным жизненным циклом.

**Архитектурное правило**

Платформа развивается посредством модулей.

Архитектурное ядро остаётся неизменным.

**3. Module Types**

Платформа поддерживает различные типы модулей.

Тип определяет архитектурную роль модуля.

**MT-001**

Business Module

Реализует бизнес-функциональность платформы.

**MT-002**

Integration Module

Обеспечивает взаимодействие с внешними системами.

**MT-003**

Capability Module

Предоставляет специализированные возможности платформы.

**MT-004**

Infrastructure Module

Реализует технические функции платформы.

**MT-005**

Administrative Module

Обеспечивает сопровождение и администрирование платформы.

**Архитектурное правило**

Тип определяет роль модуля.

Не способ его реализации.

**4. Module Lifecycle**

Каждый модуль проходит единый жизненный цикл.

Жизненный цикл определяется Platform Kernel и не зависит от назначения модуля.

**ML-001**

Registration

Модуль регистрируется в Platform Kernel.

**ML-002**

Initialization

Platform Kernel выполняет инициализацию модуля.

**ML-003**

Activation

Модуль становится доступным для использования.

**ML-004**

Operation

Модуль выполняет свои функции.

**ML-005**

Deactivation

Platform Kernel завершает работу модуля.

**Архитектурное правило**

Жизненным циклом модуля управляет Platform Kernel.

**5. Module Contract**

Каждый модуль обязан реализовать единый архитектурный контракт.

Контракт обеспечивает совместимость всех модулей платформы.

**MC-001**

Модуль должен иметь уникальный идентификатор.

**MC-002**

Модуль должен объявлять собственную версию.

**MC-003**

Модуль должен объявлять предоставляемые Capability.

**MC-004**

Модуль должен объявлять необходимые зависимости.

**MC-005**

Модуль должен поддерживать процедуры инициализации и завершения работы.

**Архитектурное правило**

Platform Kernel взаимодействует с контрактом модуля.

Не с его внутренней реализацией.

**6. Module Registration**

Все модули регистрируются в Platform Kernel.

Незарегистрированный модуль не может использоваться платформой.

**MR-001**

Регистрация выполняется до активации модуля.

**MR-002**

Platform Kernel проверяет корректность архитектурного контракта.

**MR-003**

При нарушении контракта регистрация отклоняется.

**MR-004**

Успешная регистрация делает модуль доступным для Platform Kernel.

**MR-005**

История регистрации сохраняется Platform Kernel.

**Архитектурное правило**

Любой модуль сначала становится известен Platform Kernel.

Только затем он может выполнять работу.

**7. Module Dependencies**

Модули не должны образовывать жёсткие зависимости между собой.

**MD-001**

Модуль объявляет только необходимые зависимости.

**MD-002**

Зависимости проверяются Platform Kernel.

**MD-003**

Циклические зависимости не допускаются.

**MD-004**

Модуль не обращается напрямую к внутренней реализации другого модуля.

**MD-005**

Замена одного модуля не должна требовать изменения остальных модулей.

**Архитектурное правило**

Зависимости управляются Platform Kernel.

Не разработчиками модулей.

**8. Self-Describing Modules**

Каждый модуль платформы обязан содержать собственное архитектурное описание.

Platform Kernel использует описание модуля для регистрации, проверки совместимости и управления жизненным циклом.

**SDM-001**

Модуль обязан объявить своё назначение.

**SDM-002**

Модуль обязан объявить реализуемую бизнес-функцию.

**SDM-003**

Модуль обязан объявить предоставляемые Capability.

**SDM-004**

Модуль обязан объявить необходимые Capability.

**SDM-005**

Модуль обязан объявить поддерживаемые Event и типы взаимодействия с Platform Kernel.

**Архитектурное правило**

Platform Kernel взаимодействует с архитектурным описанием модуля.

Не с его внутренней реализацией.

**9. Module Manifest**

Архитектурное описание модуля представляется в виде Module Manifest.

Module Manifest является обязательной частью каждого модуля.

**MM-001**

Module Manifest содержит идентификатор модуля.

**MM-002**

Module Manifest содержит версию модуля.

**MM-003**

Module Manifest содержит описание назначения модуля.

**MM-004**

Module Manifest содержит перечень предоставляемых Capability.

**MM-005**

Module Manifest содержит перечень требуемых Capability, зависимостей и поддерживаемых Event.

**Архитектурное правило**

Без корректного Module Manifest модуль не может быть зарегистрирован в Platform Kernel.

**10. Module Discovery**

Platform Kernel автоматически обнаруживает и регистрирует доступные модули на основании их Module Manifest.

**MD-001**

Kernel анализирует Module Manifest до загрузки модуля.

**MD-002**

Kernel проверяет совместимость версии платформы и модуля.

**MD-003**

Kernel проверяет зависимости и доступность требуемых Capability.

**MD-004**

Kernel формирует внутренний каталог доступных модулей.

**MD-005**

Только успешно зарегистрированные модули могут быть активированы.

**Архитектурное правило**

Модуль сначала описывает себя.

Затем Platform Kernel принимает решение о возможности его использования.

**11. Semantic Module Description**

Каждый модуль обязан содержать семантическое описание своего назначения.

Семантическое описание используется Platform Kernel и Cognitive Worker для понимания роли модуля в архитектуре платформы.

**SMD-001**

Модуль обязан описать свою предметную область.

**SMD-002**

Модуль обязан описать решаемые бизнес-задачи.

**SMD-003**

Модуль обязан описать основные Platform Objects, с которыми он работает.

**SMD-004**

Модуль обязан описать ожидаемые результаты своей работы.

**SMD-005**

Модуль обязан описать ограничения своего применения.

**Архитектурное правило**

Назначение модуля должно быть понятно без анализа его исходного кода.

**12. Module Intent**

Каждый модуль обязан объявить архитектурное намерение (Module Intent).

Module Intent определяет роль модуля в экосистеме платформы.

**MI-001**

Модуль объявляет, какую проблему он решает.

**MI-002**

Модуль объявляет условия своего использования.

**MI-003**

Модуль объявляет ожидаемый результат выполнения.

**MI-004**

Модуль объявляет ситуации, в которых его использование нецелесообразно.

**MI-005**

Module Intent является частью Module Manifest.

**Архитектурное правило**

Platform Kernel выбирает модуль не по имени.

Platform Kernel выбирает модуль по его назначению.

**13. Module Catalog**

Platform Kernel формирует единый каталог зарегистрированных модулей.

Module Catalog представляет собой машиночитаемое описание возможностей платформы.

**MC-001**

Module Catalog создаётся автоматически.

**MC-002**

Module Catalog обновляется при регистрации, обновлении и удалении модулей.

**MC-003**

Module Catalog доступен Human Worker и Cognitive Worker в соответствии с предоставленными полномочиями.

**MC-004**

Module Catalog используется Platform Kernel при поиске подходящего модуля.

**MC-005**

Module Catalog является частью Organizational Memory платформы.

**Архитектурное правило**

Платформа всегда знает, какими возможностями она обладает.

**14. Module Catalog**

Platform Kernel не взаимодействует с модулями напрямую.

Platform Kernel использует Module Catalog как единственный источник информации о функциональных возможностях платформы.

Module Catalog автоматически формируется на основании Module Manifest всех зарегистрированных модулей.

**MCG-001**

Module Catalog содержит сведения обо всех зарегистрированных модулях платформы.

**MCG-002**

Module Catalog автоматически обновляется при регистрации, обновлении и удалении модулей.

**MCG-003**

Platform Kernel принимает решения о выборе модуля исключительно на основании Module Catalog.

**MCG-004**

Module Catalog содержит техническое и семантическое описание каждого модуля.

**MCG-005**

Module Catalog является частью архитектурной модели платформы и доступен Platform Kernel, Human Worker и Cognitive Worker в соответствии с предоставленными полномочиями.

**Архитектурное правило**

Platform Kernel знает возможности платформы.

Platform Kernel не знает внутреннюю реализацию модулей.

**15. Module Resolution**

Выбор модуля для выполнения задачи осуществляется Platform Kernel.

Kernel определяет наиболее подходящий модуль на основании информации, содержащейся в Module Catalog.

**MR-001**

Выбор выполняется по семантическому назначению модуля.

**MR-002**

Выбор выполняется по поддерживаемым Capability.

**MR-003**

Выбор выполняется с учётом совместимости версий и объявленных зависимостей.

**MR-004**

При наличии нескольких подходящих модулей Platform Kernel использует политики выбора, определённые архитектурой платформы.

**MR-005**

Platform Kernel не обращается к модулю, отсутствующему в Module Catalog.

**Архитектурное правило**

Сначала определяется подходящая возможность.

Только затем определяется модуль, реализующий эту возможность.

**16. Capability Resolution**

Capability является архитектурной единицей функциональности платформы.

Модуль является единицей поставки и сопровождения.

**CR-001**

Один модуль может предоставлять несколько Capability.

**CR-002**

Одна Capability может иметь несколько реализаций.

**CR-003**

Platform Kernel разрешает Capability в конкретную реализацию во время исполнения.

**CR-004**

Замена реализации Capability не должна изменять остальные компоненты платформы.

**CR-005**

Capability Resolution полностью управляется Platform Kernel.

**Архитектурное правило**

Модули публикуют возможности.

Platform Kernel выбирает исполнителя.

**17. Dynamic Platform Growth**

Функциональные возможности платформы определяются составом зарегистрированных модулей.

Расширение платформы осуществляется посредством регистрации новых модулей без изменения архитектурного ядра.

**DPG-001**

Новый модуль автоматически становится частью Platform Kernel после успешной регистрации.

**DPG-002**

Регистрация нового модуля автоматически расширяет Module Catalog.

**DPG-003**

Все новые Capability становятся доступны Platform Kernel сразу после регистрации модуля.

**DPG-004**

Platform Kernel не требует изменения исходного кода для поддержки новых модулей.

**DPG-005**

Архитектурное ядро платформы остаётся неизменным при расширении функциональности.

**Архитектурное правило**

Платформа развивается посредством регистрации новых возможностей.

Не посредством изменения Platform Kernel.

**18. Module Contract Interface**

Platform Kernel взаимодействует с каждым модулем посредством единого Module Contract Interface.

Module Contract Interface определяет архитектурную границу между Platform Kernel и модулем.

**MCI-001**

Модуль обязан поддерживать процедуру регистрации.

**MCI-002**

Модуль обязан предоставлять собственное архитектурное описание.

**MCI-003**

Модуль обязан объявлять доступные Capability.

**MCI-004**

Модуль обязан поддерживать выполнение предоставляемых Capability через единый контракт исполнения.

**MCI-005**

Модуль обязан корректно завершать свою работу по запросу Platform Kernel.

**Архитектурное правило**

Platform Kernel взаимодействует только с Module Contract Interface.

**19. Module Isolation**

Каждый модуль является полностью изолированной единицей исполнения.

Внутренняя реализация модуля не влияет на архитектурную модель платформы.

**MIS-001**

Внутренние структуры данных модуля недоступны Platform Kernel.

**MIS-002**

Модуль самостоятельно управляет своей внутренней логикой.

**MIS-003**

Модуль не предоставляет внутренние API другим модулям.

**MIS-004**

Обмен информацией осуществляется исключительно посредством Platform Kernel и архитектурных контрактов.

**MIS-005**

Замена внутренней реализации модуля не должна изменять Platform Kernel.

**Архитектурное правило**

Изоляция является обязательным свойством каждого модуля.

**20. Module Compatibility**

Каждый модуль обязан обеспечивать архитектурную совместимость с текущей версией платформы.

**MCO-001**

Совместимость определяется Module Manifest.

**MCO-002**

Platform Kernel проверяет совместимость до активации модуля.

**MCO-003**

Несовместимый модуль не может быть зарегистрирован.

**MCO-004**

Обновление модуля не должно нарушать совместимость опубликованных Capability Contract без изменения версии контракта.

**MCO-005**

История совместимости фиксируется Platform Kernel.

**Архитектурное правило**

Совместимость проверяется до выполнения модуля.

Не во время его работы.

**21. Module Health**

Platform Kernel непрерывно контролирует архитектурное состояние каждого зарегистрированного модуля.

Module Health отражает готовность модуля к выполнению своих функций.

Module Health не заменяет инфраструктурный мониторинг и не описывает состояние аппаратных или программных ресурсов.

**MH-001**

Каждый зарегистрированный модуль имеет текущее архитектурное состояние.

**MH-002**

Platform Kernel обновляет состояние модуля на протяжении всего его жизненного цикла.

**MH-003**

Состояние модуля используется при выборе реализации Capability.

**MH-004**

Module Health не зависит от внутренней реализации модуля.

**MH-005**

Изменение состояния фиксируется Platform Kernel.

**Архитектурное правило**

Platform Kernel принимает решение на основании текущего состояния модуля.

**22. Module States**

Каждый модуль может находиться только в одном архитектурном состоянии.

**MS-001**

Registered

Модуль зарегистрирован, но ещё не инициализирован.

**MS-002**

Initializing

Выполняется инициализация.

**MS-003**

Ready

Модуль полностью готов к выполнению Capability.

**MS-004**

Degraded

Модуль работоспособен частично.

Некоторые Capability могут быть временно недоступны.

**MS-005**

Unavailable

Модуль недоступен для использования.

**MS-006**

Stopping

Platform Kernel завершает работу модуля.

**MS-007**

Stopped

Модуль полностью остановлен.

**Архитектурное правило**

Архитектурное состояние определяет возможность использования модуля.

**23. Capability Availability**

Доступность Capability определяется Platform Kernel.

Platform Kernel анализирует зарегистрированные реализации и их текущее состояние.

**CA-001**

Capability считается доступной при наличии хотя бы одной реализации в состоянии Ready.

**CA-002**

Если существует несколько реализаций одной Capability, Platform Kernel самостоятельно выбирает подходящую.

**CA-003**

Недоступность одной реализации не делает Capability недоступной при наличии альтернативных реализаций.

**CA-004**

Platform Kernel обязан исключать из выбора реализации, находящиеся в состоянии Unavailable.

**CA-005**

Алгоритм выбора реализации определяется архитектурной политикой платформы.

**Архитектурное правило**

Platform Kernel выбирает доступную возможность.

Не конкретный модуль.

**24. Architecture Stability**

Замена, обновление или удаление модулей не должны изменять архитектурную модель платформы.

Архитектурное ядро платформы остаётся неизменным.

**AS-001**

Platform Kernel продолжает работать независимо от состава модулей.

**AS-002**

Новые модули расширяют функциональность платформы без изменения её архитектуры.

**AS-003**

Удаление модуля не должно нарушать работу остальных модулей при отсутствии прямой архитектурной зависимости.

**AS-004**

Capability Contract является стабильной границей взаимодействия.

**AS-005**

Развитие платформы достигается посредством регистрации новых модулей и Capability.

**Архитектурное правило**

Платформа развивается посредством изменения состава возможностей.

Архитектура остаётся неизменной.
