**E-004 Архитектура бэкэнда**

**Версия:** 1.0

**Статус:** Approved

**Раздел:** E — Engineering Architecture

**1. Scope**

Настоящий документ определяет архитектуру backend-платформы Simple Solutions Practice.

Документ описывает структуру программного кода, организацию проектов, правила зависимостей и принципы реализации серверной части платформы.

**2. Architectural Style**

Backend SSP реализуется как модульная сервисная архитектура на платформе ASP.NET Core.

Каждый Platform Service представляет собой самостоятельное приложение, имеющее:

- собственную область ответственности;

- собственную модель данных;

- собственную конфигурацию;

- собственный жизненный цикл.

Все сервисы используют единые инженерные стандарты платформы.

**3. Solution Structure**

Каждый Platform Service организуется по единой структуре проектов.

ServiceName/

├── ServiceName.Api

├── ServiceName.Application

├── ServiceName.Domain

├── ServiceName.Infrastructure

├── ServiceName.Contracts

└── ServiceName.Tests

Дополнительные проекты допускаются только при наличии архитектурного обоснования.

**4. Project Responsibilities**

**Api**

Отвечает за взаимодействие с внешним миром.

Содержит:

- Controllers;

- Endpoints;

- Authentication;

- Authorization;

- Dependency Injection;

- Middleware;

- OpenAPI.

Не содержит бизнес-логики.

**Application**

Содержит прикладную логику.

Отвечает за:

- Use Cases;

- Commands;

- Queries;

- Validation;

- Orchestration;

- DTO;

- взаимодействие между слоями.

Application не знает о способах хранения данных.

**Domain**

Содержит предметную модель.

Включает:

- Entities;

- Value Objects;

- Business Rules;

- Domain Events;

- Enumerations;

- Domain Services.

Domain является полностью независимым от инфраструктуры.

**Infrastructure**

Отвечает за техническую реализацию.

Включает:

- PostgreSQL;

- Entity Framework Core;

- NATS;

- Valkey;

- S3 Storage;

- OpenSearch;

- внешние API;

- файловую систему;

- реализацию репозиториев.

Infrastructure зависит от Domain, но Domain не зависит от Infrastructure.

**Contracts**

Содержит публичные контракты сервиса.

Включает:

- DTO;

- Events;

- API Models;

- версии сообщений;

- интеграционные модели.

Contracts являются единственным способом взаимодействия между сервисами.

**Tests**

Содержит:

- Unit Tests;

- Integration Tests;

- Contract Tests;

- Performance Tests.

Тестовый проект не используется в рабочем окружении.

**5. Dependency Rules**

Зависимости между проектами должны быть однонаправленными.

Нарушение правил зависимостей не допускается.

**ADR-001**

Api может зависеть от:

- Application

- Contracts

**ADR-002**

Application может зависеть от:

- Domain

- Contracts

Application не должен зависеть от Infrastructure.

**ADR-003**

Domain не зависит ни от одного проекта платформы.

Допускается использование только библиотек .NET Base Class Library, необходимых для реализации предметной модели.

**ADR-004**

Infrastructure может зависеть от:

- Domain

- Application

- Contracts

Infrastructure реализует технические интерфейсы, определённые в Application.

**ADR-005**

Contracts не зависят ни от одного проекта.

Контракты являются независимым пакетом обмена данными.

**Архитектурное правило**

Зависимости всегда направлены к более абстрактному уровню.

Обратные ссылки запрещены.

**6. Dependency Injection**

Все сервисы используют встроенный контейнер Dependency Injection платформы ASP.NET Core.

Использование сторонних IoC-контейнеров не допускается без архитектурного обоснования.

**DI-001**

Регистрация зависимостей выполняется только в проекте Api.

**DI-002**

Конструкторная инъекция является основным способом получения зависимостей.

Использование Service Locator запрещается.

**DI-003**

Singleton допускается только для компонентов, не содержащих изменяемого состояния.

**DI-004**

Scoped используется для компонентов, связанных с обработкой запроса.

**DI-005**

Transient применяется только для лёгких объектов без внутреннего состояния.

**7. Data Access**

Доступ к данным должен быть максимально простым и прозрачным.

**DA-001**

Entity Framework Core является основным механизмом работы с PostgreSQL.

**DA-002**

DbContext является основной точкой доступа к данным.

Создание дополнительных универсальных Repository не является обязательным.

**DA-003**

Repository создаются только при наличии самостоятельной бизнес-ценности.

В MVP допускается использование DbContext напрямую в Application Layer без дополнительной абстракции Repository.

Примеры:

- работа со сложными агрегатами;

- объединение нескольких источников данных;

- специализированные алгоритмы выборки.

**DA-004**

Application не должен содержать SQL-запросов.

Все обращения к базе данных инкапсулируются в Infrastructure.

**DA-005**

Использование ORM и прямого SQL допускается одновременно.

Прямой SQL рекомендуется использовать для:

- сложной аналитики;

- массовых операций;

- высокопроизводительных запросов;

- специализированных представлений.

При этом владельцем модели данных остаётся Entity Framework Core.

**Архитектурное правило**

Простые операции не должны усложняться искусственными архитектурными слоями.

Архитектура должна уменьшать сложность системы, а не увеличивать её.

**8. Business Logic**

Бизнес-логика платформы должна иметь единственное место реализации.

Правила предметной области не должны дублироваться между компонентами системы.

**BL-001**

Business Rules реализуются только в проекте **Domain**.

**BL-002**

Application координирует выполнение операций, но не принимает бизнес-решений.

Application отвечает за:

- последовательность выполнения;

- вызов Domain;

- обработку результатов;

- публикацию событий.

**BL-003**

Api не содержит бизнес-логики.

Api отвечает только за:

- получение запроса;

- проверку модели;

- вызов Application;

- формирование ответа.

**BL-004**

Infrastructure не содержит бизнес-правил.

Infrastructure реализует только технические механизмы:

- хранение данных;

- интеграции;

- обмен сообщениями;

- файловые операции.

**BL-005**

Если бизнес-правило используется несколькими сценариями, оно реализуется один раз в Domain.

Повторение бизнес-логики запрещается.

**Архитектурное правило**

Бизнес-правило должно существовать в системе только в одном месте.

**9. Commands and Queries**

Backend использует разделение операций изменения и чтения данных.

Полная реализация CQRS не является обязательной.

**CQ-001**

Command изменяет состояние платформы.

Command:

- создаёт;

- изменяет;

- удаляет;

- инициирует Business Events.

**CQ-002**

Query не изменяет состояние платформы.

Query:

- выполняет поиск;

- формирует представления;

- строит отчёты;

- возвращает данные пользователю.

**CQ-003**

Command не должен возвращать сложные модели данных.

После успешного выполнения возвращаются:

- идентификатор объекта;

- статус операции;

- минимально необходимая информация.

**CQ-004**

Query не публикует Business Events.

**CQ-005**

Command и Query являются независимыми сценариями.

Объединение их логики допускается только при наличии архитектурного обоснования.

**Архитектурное правило**

Операция либо изменяет систему, либо читает данные.

Одновременное выполнение обеих функций не рекомендуется.

**10. Validation**

Проверка данных выполняется на нескольких уровнях платформы.

**VL-001**

Api проверяет корректность структуры запроса.

Примеры:

- обязательные поля;

- типы данных;

- формат JSON;

- размер сообщений.

**VL-002**

Application проверяет корректность сценария выполнения.

Примеры:

- существование объекта;

- наличие прав;

- выполнение предварительных условий.

**VL-003**

Domain проверяет бизнес-ограничения.

Примеры:

- допустимость перехода состояния;

- ограничения жизненного цикла;

- инварианты предметной области.

**VL-004**

Infrastructure не содержит бизнес-валидации.

Допускается только проверка технических ограничений.

**VL-005**

Каждый уровень отвечает только за собственный тип проверки.

Дублирование проверок между уровнями не допускается.

**Архитектурное правило**

Чем ближе проверка к предметной области, тем выше её приоритет.

**11. Error Handling**

Backend использует единый механизм обработки ошибок.

Ошибки подразделяются на бизнес-ошибки и технические ошибки.

**EH-001**

Business Error отражает нарушение бизнес-правил.

Примеры:

- недостаточно прав;

- недопустимый переход состояния;

- объект уже существует;

- объект находится в архиве.

Business Error является ожидаемым результатом выполнения операции.

**EH-002**

Technical Error отражает отказ инфраструктуры.

Примеры:

- недоступность PostgreSQL;

- ошибка сети;

- отказ NATS;

- недоступность внешнего API;

- ошибки файлового хранилища.

Technical Error требует регистрации и последующего анализа.

**EH-003**

Business Error не должен использовать исключения как основной механизм управления логикой.

Предпочтительно использовать типизированные результаты выполнения операций.

**EH-004**

Все необработанные исключения должны регистрироваться централизованно.

**EH-005**

Пользователю возвращается только безопасная информация об ошибке.

Внутренние детали реализации не раскрываются.

**Архитектурное правило**

Ошибки должны быть предсказуемыми, диагностируемыми и воспроизводимыми.

**12. Transactions**

Все изменения состояния платформы выполняются в транзакции.

**TR-001**

Одна бизнес-операция использует одну транзакцию базы данных.

**TR-002**

Транзакция должна быть максимально короткой.

Запрещается выполнять внутри транзакции:

- HTTP-вызовы;

- AI-запросы;

- файловые операции;

- длительные вычисления.

**TR-003**

После успешной фиксации транзакции могут запускаться асинхронные процессы.

**TR-004**

При откате транзакции Business Events не публикуются.

**TR-005**

Все изменения должны обеспечивать согласованность данных.

**Архитектурное правило**

Сначала фиксируются данные.

Только после успешной фиксации начинается взаимодействие с внешним миром.

**13. Event Publication**

Business Events публикуются после успешного завершения бизнес-операции.

**EP-001**

Каждое событие имеет уникальный идентификатор.

**EP-002**

Событие содержит минимально необходимый объём информации.

В событие не включаются технические детали реализации.

**EP-003**

Публикация события не должна изменять результат завершённой бизнес-операции.

**EP-004**

Подписчики являются полностью независимыми.

Количество подписчиков заранее неизвестно.

**EP-005**

Повторная обработка одного события не должна приводить к повреждению данных.

Все обработчики событий должны быть идемпотентными.

**Архитектурное правило**

Business Event является уведомлением о факте, а не запросом на выполнение действия.

**14. Background Processing**

Длительные операции выполняются асинхронно.

**BG-001**

Следующие операции рекомендуется выполнять в фоне:

- генерация документов;

- отправка уведомлений;

- экспорт данных;

- AI-обработка;

- индексация поиска;

- построение аналитики.

**BG-002**

Фоновые процессы не должны блокировать пользовательский запрос.

**BG-003**

Каждая фоновая задача должна иметь возможность безопасного повторного выполнения.

**BG-004**

Результаты фоновых задач регистрируются в Audit Service.

**BG-005**

Ошибка фоновой задачи не должна влиять на завершённые пользовательские операции.

**Архитектурное правило**

Все операции продолжительностью более нескольких секунд должны проектироваться как асинхронные процессы.

**15. Transactional Outbox Pattern**

Все Business Events публикуются с использованием паттерна **Transactional Outbox**.

Использование иных механизмов публикации событий допускается только после архитектурного согласования.

**TOP-001 Transaction Consistency**

Изменение бизнес-данных и регистрация события Outbox выполняются в одной транзакции PostgreSQL.

Фиксация только одного из этих действий не допускается.

**TOP-002 Outbox Storage**

Outbox представляет собой отдельную таблицу базы данных.

Каждая запись Outbox содержит:

- уникальный идентификатор события;

- тип события;

- версию контракта;

- полезную нагрузку (Payload);

- дату создания;

- дату публикации;

- количество попыток публикации;

- текущий статус обработки.

**TOP-003 Event Publisher**

Публикация сообщений в NATS JetStream выполняется отдельным сервисом (Outbox Publisher).

Publisher не содержит бизнес-логики.

Единственной его задачей является доставка зарегистрированных событий в Event Bus.

**TOP-004 Delivery Guarantee**

После успешной публикации события Publisher помечает запись Outbox как опубликованную.

При невозможности публикации событие остаётся в Outbox и повторно обрабатывается при следующем цикле работы Publisher.

**TOP-005 Idempotency**

Повторная публикация одного и того же события не должна нарушать корректность работы платформы.

Все подписчики обязаны поддерживать идемпотентную обработку сообщений.

**TOP-006 Retry Policy**

При временных ошибках доставки Publisher выполняет повторные попытки публикации.

Политика повторных попыток определяется конфигурацией платформы.

**TOP-007 Dead Letter Handling**

После превышения максимально допустимого количества попыток событие переводится в состояние Failed.

Такие события требуют анализа и обработки оператором платформы.

**Архитектурное правило**

Публикация Business Events напрямую из бизнес-кода запрещается.

Все события проходят через механизм Transactional Outbox.

**16. Message Contracts**

Все сообщения платформы являются версионируемыми контрактами.

**MC-001**

Каждый контракт имеет уникальное имя и номер версии.

**MC-002**

Изменение структуры сообщения без изменения версии запрещается.

**MC-003**

Новая версия сообщения должна сохранять совместимость с существующими потребителями либо публиковаться как новый контракт.

**MC-004**

Контракты сообщений размещаются исключительно в проекте **Contracts**.

Копирование моделей сообщений между сервисами запрещается.

**MC-005**

Payload сообщения должен содержать только данные, необходимые для обработки события.

Передача внутренних моделей Domain через Event Bus запрещается.

**Архитектурное правило**

Контракт сообщения является частью публичного API платформы и должен рассматриваться как долгосрочное обязательство по совместимости.

**17. Contracts Architecture**

Все публичные интерфейсы платформы реализуются через независимые контрактные пакеты.

Контракты являются единственным допустимым способом обмена данными между сервисами.

**CA-001 Package Separation**

Каждый Platform Service публикует собственный пакет контрактов.

Пример структуры:

SSP.Contracts.Identity

SSP.Contracts.Business

SSP.Contracts.Automation

SSP.Contracts.Artifacts

SSP.Contracts.Notification

SSP.Contracts.Configuration

**CA-002 Package Contents**

Контрактный пакет может содержать:

- Request Models;

- Response Models;

- Event Contracts;

- Enumerations;

- Shared Value Objects;

- Error Codes.

Контрактные пакеты не содержат:

- бизнес-логики;

- Entity Framework;

- Domain Models;

- Infrastructure Components;

- Application Services.

**CA-003 Versioning**

Каждый пакет имеет собственную семантическую версию.

Используется схема:

Major.Minor.Patch

Изменение Major-версии допускается только при нарушении обратной совместимости.

**CA-004 Backward Compatibility**

Все изменения контрактов должны сохранять совместимость существующих клиентов.

Удаление публичных полей допускается только при выпуске новой Major-версии.

**CA-005 Dependency Isolation**

Platform Services не должны ссылаться друг на друга напрямую.

Допустимы только зависимости от контрактных пакетов.

**Архитектурное правило**

Контракт является единственной формой публичного взаимодействия между сервисами.

**18. Backend Coding Standards**

Все сервисы платформы придерживаются единых правил разработки.

**BCS-001**

Nullable Reference Types должны быть включены во всех проектах.

**BCS-002**

Warnings рассматриваются как ошибки при сборке.

Сборка с предупреждениями не допускается.

**BCS-003**

Async/Await используется для всех операций ввода-вывода.

Блокирующие вызовы запрещаются.

**BCS-004**

Все публичные методы должны поддерживать CancellationToken, если операция потенциально может выполняться длительное время.

**BCS-005**

Использование статического изменяемого состояния запрещается.

**BCS-006**

Все даты и время внутри платформы хранятся в UTC.

Преобразование в локальное время выполняется только на уровне представления данных.

**BCS-007**

Все идентификаторы новых бизнес-объектов используют UUID версии 7 (UUIDv7).

Использование автоинкрементных идентификаторов допускается только для внутренних технических таблиц.

**BCS-008**

Все публичные API, события и контракты документируются автоматически через OpenAPI и XML Documentation.

**BCS-009**

Каждый новый сервис должен содержать:

- Health Check;

- Readiness Check;

- Liveness Check;
