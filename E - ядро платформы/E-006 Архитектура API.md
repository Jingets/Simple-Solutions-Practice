**E-006 Архитектура API**

**Версия:** 1.0

**Статус:** Approved

**Раздел:** E — Engineering Architecture

**1. Scope**

Настоящий документ определяет архитектуру прикладных интерфейсов (API) платформы Simple Solutions Practice.

Документ устанавливает единые правила проектирования, публикации, версионирования и сопровождения API.

API является официальным публичным контрактом платформы и должно обеспечивать стабильное взаимодействие между всеми компонентами SSP.

**2. API Principles**

Все API платформы проектируются на основании единых архитектурных принципов.

**AP-001**

API является контрактом, а не внутренней реализацией сервиса.

Изменение внутренней логики сервиса не должно требовать изменения API.

**AP-002**

Каждый Platform Service публикует только собственный API.

Доступ к внутренним данным других сервисов осуществляется исключительно через их публичные интерфейсы.

**AP-003**

API должно быть максимально простым и предсказуемым.

Для выполнения одной операции существует один официальный способ.

**AP-004**

API не должно раскрывать внутреннюю структуру платформы.

Клиент взаимодействует с бизнес-возможностями, а не с внутренними объектами реализации.

**AP-005**

Все публичные API автоматически документируются.

**Архитектурное правило**

API описывает возможности платформы, а не её внутреннее устройство.

**3. API Types**

Платформа использует несколько типов API.

Каждый тип предназначен для собственной категории взаимодействия.

**External API**

Предназначено для:

- Web Client;

- Mobile Client;

- Desktop Client;

- внешних информационных систем;

- партнёрских интеграций.

**Internal API**

Используется исключительно для взаимодействия Platform Services.

Недоступно внешним клиентам.

**Event API**

Используется для асинхронного обмена Business Events через NATS JetStream.

**AI API**

Предназначено для взаимодействия AI-агентов с платформой.

Поддерживает выполнение команд, получение контекста и работу с инструментами (Tools).

**Архитектурное правило**

Каждый тип API имеет собственные правила безопасности, версионирования и сопровождения.

**4. REST API**

Основным синхронным интерфейсом платформы является REST API.

**REST-001**

Все API используют HTTPS.

Нешифрованный HTTP не поддерживается.

**REST-002**

Формат обмена данными:

application/json

**REST-003**

Используется семантика HTTP.

Примеры:

/api/artifacts

/api/workspaces

В URL запрещается использовать названия внутренних классов, сервисов и таблиц базы данных.

**REST-005**

Все ответы возвращаются в формате JSON UTF-8.

**Архитектурное правило**

REST API должно оставаться понятным человеку без знания внутренней реализации платформы.

**5. Resource Design**

REST API проектируется вокруг бизнес-ресурсов платформы.

Ресурс представляет собой бизнес-сущность или бизнес-возможность.

**RD-001**

URI должен использовать существительные.

Примеры:

/projects

/customers

/workspaces

/artifacts

**RD-002**

Использование глаголов в URI запрещается.

Недопустимо:

/createProject

/updateCustomer

/deleteArtifact

**RD-003**

Действия, не являющиеся CRUD-операциями, оформляются как команды.

Пример:

POST /projects/{id}/archive

POST /workspaces/{id}/publish

POST /documents/{id}/approve

**RD-004**

URI должны быть стабильными.

Изменение URI допускается только при выпуске новой Major-версии API.

**Архитектурное правило**

URI описывает бизнес-объект.

HTTP-метод описывает действие.

**6. Request & Response Model**

Все запросы и ответы используют единые правила.

**RRM-001**

Все запросы используют JSON UTF-8.

**RRM-002**

Ответ содержит только данные, необходимые клиенту.

Передача внутренних моделей Domain запрещается.

**RRM-003**

DTO являются частью публичного контракта.

Изменение DTO требует соблюдения правил версионирования.

**RRM-004**

Ответы должны иметь стабильную структуру.

Не допускается изменение типа существующего поля.

**RRM-005**

Неиспользуемые поля не включаются в контракт.

API не должно возвращать данные "на будущее".

**Архитектурное правило**

Контракт API должен быть минимальным, но достаточным.

**8. Error Response**

Все ошибки имеют единую структуру.

Минимальный состав ответа:

{

"errorCode": "PROJECT\_ALREADY\_ARCHIVED",

"message": "The project has already been archived.",

"correlationId": "...",

"timestamp": "..."

}

**ER-001**

Каждая ошибка имеет стабильный errorCode.

**ER-002**

Текст сообщения предназначен для человека и может быть локализован.

Логика клиента не должна зависеть от текста сообщения.

**ER-003**

correlationId включается во все ответы с ошибкой.

**ER-004**

В ответах запрещается раскрывать:

- стек вызовов;

- SQL-запросы;

- внутренние имена классов;

- конфигурацию платформы.

**Архитектурное правило**

Клиент должен понимать, **что произошло**, но не должен получать сведения о внутреннем устройстве платформы.

**9. API Versioning**

Все публичные API платформы являются версионируемыми.

Версионирование обеспечивает возможность развития платформы без нарушения совместимости существующих клиентов.

**AV-001**

Основной механизм версионирования — Major Version.

Версия указывается в URL.

Пример:

/api/v1/projects

/api/v2/projects

**AV-002**

Изменения, нарушающие обратную совместимость, допускаются только в новой Major-версии.

**AV-003**

Minor и Patch изменения не должны требовать изменения URL.

**AV-004**

Одновременно могут поддерживаться несколько Major-версий API.

Срок поддержки определяется политикой жизненного цикла платформы.

**AV-005**

Устаревшие версии API должны быть помечены как Deprecated до их удаления.

**Архитектурное правило**

Клиент самостоятельно выбирает используемую версию API.

**10. Pagination**

Все операции получения коллекций должны поддерживать постраничный вывод.

**PG-001**

Получение полной коллекции без пагинации запрещается.

**PG-002**

Стандартные параметры:

page

pageSize

**PG-003**

Максимальный размер страницы определяется конфигурацией платформы.

**PG-004**

Ответ должен содержать информацию о навигации.

Минимальный состав:

- page;

- pageSize;

- totalItems;

- totalPages.

**PG-005**

Для больших наборов данных допускается использование Cursor Pagination.

**Архитектурное правило**

API должно масштабироваться независимо от объёма данных.

**11. Filtering and Sorting**

Все коллекции используют единые правила фильтрации.

**FS-001**

Фильтрация выполняется через Query Parameters.

Пример:

GET /projects?status=Active

**FS-002**

Сортировка выполняется параметром:

sort=

Пример:

sort=CreatedAt

sort=-CreatedAt

Префикс "-" означает сортировку по убыванию.

**FS-003**

Поддерживаются только явно разрешённые поля сортировки.

**FS-004**

Сложные поисковые сценарии реализуются отдельными специализированными API.

**FS-005**

API не должно предоставлять универсальный язык запросов.

**Архитектурное правило**

Чем проще запрос, тем проще его сопровождать.

**12. Idempotency**

Все операции должны иметь предсказуемое поведение при повторном выполнении.

**IDP-001**

Все GET являются идемпотентными.

**IDP-002**

PUT и DELETE должны быть идемпотентными.

Повторный вызов не должен изменять конечное состояние системы.

**IDP-003**

Для операций POST, приводящих к созданию ресурсов или выполнению команд, поддерживается заголовок:

Idempotency-Key

**IDP-004**

Повторный запрос с тем же Idempotency-Key должен возвращать результат первоначальной операции без повторного выполнения.

**IDP-005**

Период хранения ключей идемпотентности определяется конфигурацией платформы.

**Архитектурное правило**

Повторная отправка одного и того же запроса не должна приводить к дублированию бизнес-операций.

**13. Correlation and Traceability**

Каждый запрос должен иметь уникальный идентификатор трассировки.

**CT-001**

Каждый входящий запрос получает Correlation ID.

**CT-002**

Если Correlation ID передан клиентом, он сохраняется при условии соответствия формату платформы.

В противном случае создаётся новый идентификатор.

**CT-003**

Correlation ID передаётся:

- между Platform Services;

- в Business Events;

- в журналы;

- в Audit Service;

- в диагностические сообщения.

**CT-004**

Все ответы API содержат Correlation ID в заголовке ответа.

**CT-005**

Все журналы платформы используют единый Correlation ID как основной идентификатор трассировки.

**Архитектурное правило**

Любую пользовательскую операцию должно быть возможно проследить через всю платформу по одному Correlation ID.

**14. API Security**

Безопасность API строится по принципу **Zero Trust**.

Ни один запрос не считается доверенным до завершения всех необходимых проверок.

**AS-001**

Каждый запрос проходит обязательную аутентификацию либо использует явно разрешённый механизм анонимного доступа.

**AS-002**

После успешной аутентификации выполняется авторизация.

Наличие действительного токена не означает наличие прав на выполнение операции.

**AS-003**

Права проверяются для каждой бизнес-операции.

Недостаточность прав приводит к немедленному завершению обработки запроса.

**AS-004**

Все проверки безопасности выполняются до передачи управления бизнес-логике.

**AS-005**

Business Logic не должна зависеть от механизма аутентификации.

Domain не знает:

- JWT;

- OAuth;

- OpenID Connect;

- API Keys;

- Cookies.

**Архитектурное правило**

Безопасность является частью платформы, а не частью бизнес-логики.

**15. Authentication**

Платформа поддерживает несколько механизмов аутентификации.

Конкретный механизм определяется типом клиента.

**AU-001**

Пользовательские приложения используют Bearer Token.

**AU-002**

Platform Services используют отдельную модель Service Authentication.

Использование пользовательских токенов для взаимодействия сервисов запрещается.

**AU-003**

Временные токены имеют ограниченный срок действия.

**AU-004**

Долгоживущие токены не используются.

**AU-005**

Обновление токенов выполняется через Identity Service.

**Архитектурное правило**

Аутентификация подтверждает личность.

Она не предоставляет права.

**16. Authorization**

Авторизация основана на модели разрешений платформы.

**AZ-001**

Права определяются бизнес-возможностями, а не HTTP-методами.

**AZ-002**

Разрешения являются независимыми от пользовательского интерфейса.

**AZ-003**

Каждая операция API требует явно определённого разрешения.

**AZ-004**

Отсутствие необходимого разрешения приводит к ответу:

403 Forbidden

**AZ-005**

Решение о предоставлении доступа принимается до выполнения бизнес-операции.

**Архитектурное правило**

Права определяются возможностями платформы, а не структурой API.

**17. Service-to-Service Security**

Взаимодействие Platform Services рассматривается как взаимодействие недоверенных участников.

**S2S-001**

Каждый сервис имеет собственную идентичность.

**S2S-002**

Каждый запрос между сервисами проходит проверку подлинности.

**S2S-003**

Внутренняя сеть не считается доверенной средой.

**S2S-004**

Service Identity не предоставляет неограниченного доступа.

Каждый сервис получает только минимально необходимые разрешения.

**S2S-005**

Все обращения между сервисами журналируются.

**Архитектурное правило**

Внутренний сервис не обладает большим доверием, чем внешний клиент.

**18. API Gateway**

Все внешние запросы проходят через единый API Gateway.

**AG-001**

API Gateway является единственной точкой входа во внешнюю часть платформы.

**AG-002**

Platform Services не публикуются напрямую в Интернет.

**AG-003**

API Gateway отвечает за:

- маршрутизацию;

- завершение TLS;

- проверку токенов;

- ограничение скорости запросов;

- централизованное журналирование.

**AG-004**

Бизнес-логика не реализуется в API Gateway.

**AG-005**

API Gateway не хранит состояние пользовательских сессий.

**Архитектурное правило**

API Gateway защищает платформу, но не заменяет механизмы безопасности отдельных сервисов.

**19. API Documentation**

Все публичные API должны быть полностью документированы.

Документация является частью поставляемого продукта.

**AD-001**

Каждый Endpoint автоматически публикуется в OpenAPI Specification.

**AD-002**

Документация содержит:

- описание операции;

- параметры;

- модели запросов;

- модели ответов;

- возможные ошибки;

- требования безопасности.

**AD-003**

Изменение API без обновления документации запрещается.

**AD-004**

Документация генерируется автоматически из исходного кода.

Ручное сопровождение документации API не допускается.

**AD-005**

Каждая опубликованная версия API имеет собственную документацию.

**Архитектурное правило**

Документация является частью контракта API.

**20. API Monitoring**

Работа всех публичных интерфейсов платформы контролируется средствами наблюдаемости.

**AM-001**

Каждый запрос регистрируется.

**AM-002**

Для каждого Endpoint собираются:

- количество запросов;

- среднее время ответа;

- процент ошибок;

- нагрузка;

- объём передаваемых данных.

**AM-003**

Все показатели публикуются через OpenTelemetry.

**AM-004**

Аномальное поведение API должно обнаруживаться автоматически.

**AM-005**

Метрики API являются частью общей системы мониторинга платформы.

**Архитектурное правило**

Если состояние API невозможно измерить, им невозможно управлять.

**21. API Lifecycle**

Каждый Endpoint проходит полный жизненный цикл.

**ALC-001**

Проектирование.

**ALC-002**

Реализация.

**ALC-003**

Автоматическое тестирование.

**ALC-004**

Публикация.

**ALC-005**

Мониторинг эксплуатации.

**ALC-006**

Устаревание (Deprecated).

**ALC-007**

Вывод из эксплуатации.

**Архитектурное правило**

API является долгосрочным контрактом.

Его жизненный цикл управляется так же строго, как жизненный цикл любого другого компонента платформы.

**22. Fundamental Principles**

Архитектура API SSP основана на следующих принципах:

1.  API является контрактом, а не реализацией.

2.  Один бизнес-сценарий — один официальный способ выполнения.

3.  Контракты стабильнее внутреннего устройства сервисов.

4.  Безопасность обязательна для каждого запроса.

5.  API должно быть простым, предсказуемым и самодокументируемым.

6.  Все изменения выполняются с сохранением обратной совместимости либо через новую Major-версию.

7.  Клиент взаимодействует с возможностями платформы, а не с её внутренней архитектурой.

8.  Все обращения должны быть трассируемыми, наблюдаемыми и измеримыми.
