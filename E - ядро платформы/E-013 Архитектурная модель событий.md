**E-013 Архитектурная модель событий**

**Версия:** 1.0

**Статус:** Draft

**Раздел:** E — Engineering Architecture

**1. Scope**

Настоящий документ определяет архитектурную модель событий платформы Simple Solutions Practice.

Event является единственной архитектурной причиной изменения состояния платформы.

Все процессы платформы инициируются обработкой Event.

**2. Event Principles**

Event представляет собой зарегистрированный факт наступления определённого события.

Event является неизменяемым после регистрации.

**EP-001**

Каждый Event обладает собственной идентичностью.

**EP-002**

Каждый Event имеет время возникновения.

**EP-003**

После регистрации Event не изменяется.

**EP-004**

Event может использоваться несколькими Workflow.

**EP-005**

Event может использоваться повторно при анализе истории платформы.

**Архитектурное правило**

Event фиксирует факт.

Он не описывает намерение.

**3. Event Categories**

Все события платформы относятся к одной из архитектурных категорий.

**EC-001**

Business Event

Событие предметной области.

Отражает изменение состояния бизнеса.

**EC-002**

Platform Event

Событие внутренней работы платформы.

Отражает изменение архитектурного состояния платформы.

**EC-003**

Infrastructure Event

Событие инфраструктуры.

Отражает состояние технических компонентов платформы.

**EC-004**

Категория Event определяется при его регистрации.

**EC-005**

Категория Event не изменяется в течение жизненного цикла Event.

**Архитектурное правило**

Каждое событие имеет единственную архитектурную категорию.

**4. Business Events**

Business Event является единственной допустимой причиной изменения бизнес-состояния платформы.

Business Event отражает факт наступления события предметной области.

**BE-001**

Business Event создаётся после подтверждения факта наступления соответствующего бизнес-события.

**BE-002**

Business Event может инициировать один или несколько Workflow.

**BE-003**

Business Event может приводить к созданию Platform Objects.

**BE-004**

Business Event является частью организационной памяти платформы.

**BE-005**

Business Event сохраняется в истории платформы.

**Архитектурное правило**

Изменение бизнес-состояния возможно только посредством Business Event.

**5. Event Lifecycle**

Каждый Event проходит единый жизненный цикл независимо от своей категории.

Жизненный цикл Event управляется Platform Kernel.

**EL-001**

Event создаётся после регистрации соответствующего факта.

**EL-002**

После регистрации Event становится доступным для маршрутизации.

**EL-003**

Platform Kernel определяет подписчиков Event.

**EL-004**

После завершения обработки Event сохраняется в истории платформы.

**EL-005**

Жизненный цикл Event не зависит от количества его обработчиков.

**Архитектурное правило**

Event сначала регистрируется.

Только после этого начинается его обработка.

**6. Event Routing**

Platform Kernel определяет маршрут распространения каждого Event.

Маршрутизация выполняется на основании архитектурных правил платформы.

**ER-001**

Каждый Event может иметь одного или нескольких подписчиков.

**ER-002**

Маршрутизация выполняется независимо для каждого подписчика.

**ER-003**

Порядок обработки определяется Platform Kernel.

**ER-004**

Ошибки одного подписчика не должны препятствовать обработке остальных.

**ER-005**

Маршрут обработки фиксируется в истории исполнения.

**Архитектурное правило**

Platform Kernel управляет распространением Event.

**7. Event Subscription**

Компоненты платформы получают Event исключительно посредством подписки.

**ES-001**

Workflow может подписываться на один или несколько Business Event.

**ES-002**

Capability Provider может подписываться только на Platform Event, если это предусмотрено архитектурой.

**ES-003**

Infrastructure Components могут публиковать Infrastructure Event.

**ES-004**

Подписка определяется архитектурной конфигурацией платформы.

**ES-005**

Компонент не может получать Event вне механизма подписки.

**Архитектурное правило**

Получение Event всегда является результатом подписки.

Не прямого вызова.

**8. Event Persistence**

Все зарегистрированные Event сохраняются Platform Kernel.

История событий является неизменяемой.

**EV-001**

Каждый Event сохраняется после регистрации.

**EV-002**

Изменение зарегистрированного Event не допускается.

**EV-003**

Удаление Event допускается только в соответствии с политикой хранения платформы.

**EV-004**

История Event используется для анализа и аудита.

**EV-005**

Event может использоваться при восстановлении истории деятельности платформы.

**Архитектурное правило**

История событий является неизменяемой частью платформы.

**9. Event Responsibility**

Event является архитектурным сообщением о произошедшем факте.

Event не содержит поведения и не определяет дальнейшие действия платформы.

**EVR-001**

Event сообщает только о факте наступления события.

**EVR-002**

Event не содержит бизнес-логики.

**EVR-003**

Event не определяет последовательность обработки.

**EVR-004**

Event не инициирует выполнение операций самостоятельно.

**EVR-005**

Решение о реакции на Event принимает Platform Kernel.

**Архитектурное правило**

Event сообщает.

Platform Kernel принимает решение.

**10. Event Independence**

Каждый Event является самостоятельной архитектурной сущностью.

**EID-001**

Event не зависит от количества подписчиков.

**EID-002**

Event существует независимо от наличия Workflow.

**EID-003**

Event не зависит от состава Capability Provider.

**EID-004**

Event не зависит от технологий реализации платформы.

**EID-005**

Event может использоваться повторно для анализа истории платформы.

**Архитектурное правило**

Событие не знает, кто будет его использовать.

**11. Event Traceability**

Каждый Event должен быть полностью трассируемым.

Platform Kernel обеспечивает возможность восстановления полной цепочки происхождения события.

**ET-001**

Для каждого Event определяется источник возникновения.

**ET-002**

Для каждого Event определяется Execution Request, в рамках которого он был зарегистрирован, если применимо.

**ET-003**

Для каждого Event сохраняются связанные Platform Objects.

**ET-004**

Для каждого Event сохраняются созданные Artifact.

**ET-005**

Для каждого Event сохраняются последующие Platform Event, непосредственно вызванные его обработкой.

**Архитектурное правило**

Каждое событие должно иметь полностью прослеживаемое происхождение и последствия.

**12. Event Replay**

История зарегистрированных Event может использоваться для повторного анализа деятельности платформы.

Повторное использование Event не изменяет исторические данные.

**ERP-001**

Event Replay выполняется только Platform Kernel.

**ERP-002**

Replay использует неизменяемую историю зарегистрированных Event.

**ERP-003**

Replay не изменяет исходную последовательность зарегистрированных событий.

**ERP-004**

Replay может использоваться для анализа, диагностики и проверки архитектурных решений.

**ERP-005**

Replay не заменяет стандартное исполнение Workflow.

**Архитектурное правило**

История событий используется для анализа.

Не для изменения прошлого.

**13. Event Relationships**

Event связывает архитектурные компоненты платформы в единую причинно-следственную модель.

Event не заменяет Platform Objects, Workflow или Artifact.

Он определяет последовательность их возникновения.

**ERL-001**

Business Event может инициировать один или несколько Workflow.

**ERL-002**

Workflow может создавать Platform Event.

**ERL-003**

Platform Event может инициировать выполнение Execution Request.

**ERL-004**

Execution Request может приводить к созданию Artifact.

**ERL-005**

Artifact может становиться источником Organizational Memory.

**Архитектурное правило**

Event определяет причинно-следственную связь между архитектурными объектами.

**14. Event Consistency**

Platform Kernel обеспечивает логическую согласованность зарегистрированных Event.

**ECN-001**

События фиксируются в порядке их регистрации.

**ECN-002**

Каждый Event имеет единственное происхождение.

**ECN-003**

Причина возникновения Event должна быть определена.

**ECN-004**

Последствия обработки Event должны быть полностью прослеживаемы.

**ECN-005**

Логическая последовательность Event не должна нарушаться при изменении технологий реализации.

**Архитектурное правило**

История событий должна оставаться логически непротиворечивой.

**15. Event Architecture Principles**

Event Architecture SSP основана на следующих принципах.

1.  Event является зарегистрированным фактом.

2.  Event является неизменяемым после регистрации.

3.  Business Event является единственной причиной изменения бизнес-состояния платформы.

4.  Platform Event отражает изменение архитектурного состояния.

5.  Infrastructure Event отражает состояние технической инфраструктуры.

6.  Platform Kernel управляет жизненным циклом Event.

7.  Event не содержит бизнес-логики.

8.  Event не определяет способ обработки.

9.  Все Event полностью трассируемы.

10. История Event является неизменяемой.

11. Event связывает все архитектурные компоненты платформы в единую причинно-следственную модель.
