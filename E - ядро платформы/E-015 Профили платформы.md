**E-015 Профили платформы**

**Версия:** 1.0

**Статус:** Draft

**Раздел:** E — Engineering Architecture

**1. Scope**

Настоящий документ определяет механизм формирования конфигурации платформы Simple Solutions Practice.

Platform Profile определяет состав, назначение и режим работы конкретной инсталляции платформы.

**2. Platform Profile**

Platform Profile представляет собой архитектурное описание конфигурации платформы.

Platform Profile определяет, какие модули, Capability и политики используются в конкретной среде.

**PP-001**

Каждая инсталляция платформы использует один активный Platform Profile.

**PP-002**

Platform Profile определяет состав модулей платформы.

**PP-003**

Platform Profile определяет набор активных Capability.

**PP-004**

Platform Profile определяет архитектурные политики платформы.

**PP-005**

Platform Profile используется Platform Kernel при запуске платформы.

**Архитектурное правило**

Платформа запускается не сама по себе.

Платформа запускается в рамках Platform Profile.

**3. Profile Boot Process**

Перед запуском Platform Kernel выполняет загрузку Platform Profile.

**PB-001**

Platform Profile загружается до регистрации модулей.

**PB-002**

Platform Profile определяет перечень модулей, подлежащих регистрации.

**PB-003**

Platform Profile определяет обязательные Capability.

**PB-004**

Platform Profile определяет архитектурные параметры запуска.

**PB-005**

Platform Kernel начинает выполнение только после успешной проверки Platform Profile.

**Архитектурное правило**

Platform Profile определяет состав платформы до запуска Platform Kernel.

**4. Profile Composition**

Platform Profile состоит из архитектурных компонентов платформы.

**PC-001**

Platform Profile определяет используемые модули.

**PC-002**

Platform Profile определяет доступные Capability.

**PC-003**

Platform Profile определяет архитектурные политики.

**PC-004**

Platform Profile определяет режим эксплуатации платформы.

**PC-005**

Platform Profile определяет ограничения конкретной инсталляции.

**Архитектурное правило**

Profile описывает платформу целиком.

Не отдельные модули.

**5. Profile Resolution**

Перед запуском Platform Kernel выполняется разрешение Platform Profile.

Цель процесса — определить возможность построения требуемой конфигурации платформы.

**PR-001**

Platform Profile анализируется до регистрации модулей.

**PR-002**

Все требуемые Capability должны быть разрешены.

**PR-003**

Для каждой обязательной Capability должна существовать хотя бы одна совместимая реализация.

**PR-004**

Все архитектурные зависимости должны быть удовлетворены.

**PR-005**

При невозможности разрешения Platform Profile запуск платформы запрещается.

**Архитектурное правило**

Платформа запускается только после успешного разрешения Profile.

**6. Capability Resolution Policy**

Platform Kernel определяет реализацию каждой Capability в соответствии с политиками платформы.

**CRP-001**

Если существует единственная реализация Capability, используется она.

**CRP-002**

При наличии нескольких реализаций выбор осуществляется Platform Kernel.

**CRP-003**

Политика выбора определяется Platform Profile.

**CRP-004**

Platform Kernel может заменить реализацию Capability без изменения Platform Profile.

**CRP-005**

Все решения о выборе реализации фиксируются в журнале запуска платформы.

**Архитектурное правило**

Profile определяет требуемую возможность.

Kernel определяет её реализацию.

**7. Profile Validation**

Каждый Platform Profile проходит обязательную архитектурную проверку.

**PV-001**

Проверяется корректность структуры Platform Profile.

**PV-002**

Проверяется наличие обязательных Capability.

**PV-003**

Проверяется совместимость архитектурных политик.

**PV-004**

Проверяется отсутствие конфликтующих требований.

**PV-005**

Только успешно проверенный Profile может использоваться для запуска платформы.

**Архитектурное правило**

Некорректный Profile не может быть использован Platform Kernel.

**8. Profile Immutability**

После завершения процесса запуска активный Platform Profile считается неизменяемым.

Изменение конфигурации выполняется посредством создания новой версии Platform Profile и повторного процесса разрешения.

**PI-001**

Активный Platform Profile не изменяется во время работы платформы.

**PI-002**

Изменение состава возможностей требует новой процедуры Profile Resolution.

**PI-003**

Все версии Platform Profile сохраняются в истории платформы.

**PI-004**

История изменения Profile используется для анализа развития платформы.

**PI-005**

Platform Kernel всегда работает только с одной активной версией Platform Profile.

**Архитектурное правило**

Конфигурация платформы должна быть воспроизводимой.

**9. Organization Profile**

Platform Profile определяет архитектурную конфигурацию платформы.

Organization Profile определяет особенности эксплуатации платформы в конкретной организации.

Organization Profile не изменяет архитектуру платформы.

**OP-001**

Organization Profile описывает организационную структуру.

**OP-002**

Organization Profile описывает бизнес-роли.

**OP-003**

Organization Profile описывает политики организации.

**OP-004**

Organization Profile описывает особенности бизнес-процессов.

**OP-005**

Organization Profile описывает корпоративные ограничения и правила.

**Архитектурное правило**

Platform Profile определяет платформу.

Organization Profile определяет организацию.

**10. Separation of Responsibilities**

Platform Profile и Organization Profile являются независимыми архитектурными сущностями.

Изменение одного профиля не требует изменения другого.

**SR-001**

Изменение состава модулей не изменяет Organization Profile.

**SR-002**

Изменение организационной структуры не изменяет Platform Profile.

**SR-003**

Platform Kernel использует оба профиля одновременно.

**SR-004**

Platform Profile отвечает за технические возможности платформы.

**SR-005**

Organization Profile отвечает за правила эксплуатации платформы.

**Архитектурное правило**

Архитектура платформы и модель организации развиваются независимо.

**11. Profile Hierarchy**

Конфигурация платформы формируется последовательным применением архитектурных профилей.

**PH-001**

Platform Profile определяет архитектурные возможности платформы.

**PH-002**

Organization Profile определяет правила работы организации.

**PH-003**

Permission Context определяет полномочия конкретного пользователя.

**PH-004**

Execution Context определяет параметры конкретного выполнения.

**PH-005**

Все уровни конфигурации применяются последовательно и не подменяют друг друга.

**Архитектурное правило**

Каждый уровень конфигурации отвечает только за собственную область ответственности.

**12. Profile Independence**

Профили не содержат бизнес-логики.

Профили являются декларативным описанием конфигурации платформы и условий её эксплуатации.

**PI-001**

Профиль описывает требуемое состояние.

**PI-002**

Профиль не содержит алгоритмов исполнения.

**PI-003**

Профиль не содержит программного кода.

**PI-004**

Профиль используется Platform Kernel при принятии архитектурных решений.

**PI-005**

Все профили являются машиночитаемыми и семантически описанными.

**Архитектурное правило**

Профили описывают систему.

Platform Kernel обеспечивает её работу.

**13. Policy-Based Configuration**

Платформа не использует единый объект конфигурации.

Правила функционирования платформы определяются независимыми Policy.

Каждая Policy описывает отдельную область поведения платформы.

**PBC-001**

Каждая Policy отвечает только за одну область ответственности.

**PBC-002**

Policy являются декларативными объектами.

**PBC-003**

Policy не содержат программной логики.

**PBC-004**

Platform Kernel использует Policy при принятии архитектурных решений.

**PBC-005**

Policy могут изменяться независимо друг от друга.

**Архитектурное правило**

Поведение платформы определяется набором независимых Policy.

Не глобальными настройками.

**14. Configuration Model**

Конфигурация платформы формируется совокупностью архитектурных моделей.

Каждая модель отвечает только за собственную область ответственности.

**CM-001**

Platform Profile определяет состав платформы.

**CM-002**

Organization Profile определяет модель организации.

**CM-003**

Policy определяют правила функционирования платформы.

**CM-004**

Permission Context определяет полномочия.

**CM-005**

Execution Context определяет параметры конкретного выполнения.

**Архитектурное правило**

Конфигурация платформы представляет собой совокупность специализированных архитектурных моделей.

Не единый объект Settings.

**15. Context-Oriented Execution**

Все модули платформы работают исключительно с предоставленным Platform Kernel контекстом.

Модуль не получает доступ к архитектурным моделям платформы напрямую.

**COE-001**

Platform Kernel формирует Module Context перед каждым выполнением.

**COE-002**

Module Context содержит только информацию, необходимую для выполнения текущей операции.

**COE-003**

Модуль не определяет состав получаемого контекста самостоятельно.

**COE-004**

Platform Kernel несёт ответственность за полноту и корректность Module Context.

**COE-005**

Модуль не обращается к Platform Profile, Organization Profile, Policy или другим архитектурным моделям напрямую.

**Архитектурное правило**

Модуль получает контекст.

Не конфигурацию платформы.

**16. Module Context**

Module Context представляет собой архитектурный объект, содержащий всю информацию, необходимую для выполнения конкретной операции.

**MCX-001**

Module Context содержит Execution Context.

**MCX-002**

Module Context содержит Permission Context.

**MCX-003**

Module Context содержит необходимые организационные данные.

**MCX-004**

Module Context содержит необходимые архитектурные Policy.

**MCX-005**

Module Context может содержать дополнительные данные, подготовленные Platform Kernel специально для данного выполнения.

**Архитектурное правило**

Platform Kernel формирует Context.

Модуль использует Context.

**17. Context Isolation**

Module Context существует только в рамках одного выполнения.

Контекст не используется повторно после завершения операции.

**CI-001**

Контекст создаётся Platform Kernel.

**CI-002**

Контекст уничтожается после завершения выполнения.

**CI-003**

Контекст является неизменяемым для модуля.

**CI-004**

Модуль не сохраняет ссылок на полученный Context после завершения работы.

**CI-005**

Каждое выполнение использует собственный Module Context.

**Архитектурное правило**

Каждое выполнение получает собственный архитектурный контекст.

**18. Domain Profiles**

Организационный опыт платформы разделяется по независимым предметным областям (Domain).

Каждая предметная область формирует собственную модель знаний, собственный организационный опыт и собственную историю развития.

**DPF-001**

Каждый Domain представляет самостоятельную область бизнеса.

**DPF-002**

Каждый Domain обладает собственной Organizational Memory.

**DPF-003**

Каждый Domain накапливает собственные Artifact.

**DPF-004**

Каждый Domain использует собственные специализированные Module и Capability.

**DPF-005**

Взаимодействие между Domain осуществляется только посредством Platform Kernel и архитектурных контрактов.

**Архитектурное правило**

Организационный опыт разделяется по предметным областям.

**19. Domain Isolation**

Предметные области не смешивают собственные модели знаний.

Накопление опыта выполняется независимо для каждого Domain.

**DI-001**

Финансовый Domain не использует организационную память логистического Domain напрямую.

**DI-002**

Логистический Domain не использует организационную память HR Domain напрямую.

**DI-003**

Каждый Domain развивает собственную экспертную модель.

**DI-004**

Повторяемость практики анализируется внутри Domain.

**DI-005**

Автоматизация принимается на основании опыта соответствующего Domain.

**Архитектурное правило**

Автоматизация развивается внутри предметной области, в которой был накоплен опыт.

**20. Domain Evolution**

Каждая предметная область развивается независимо.

Развитие одного Domain не требует изменения моделей знаний других Domain.

**DE-001**

Каждый Domain может иметь собственные Module.

**DE-002**

Каждый Domain может иметь собственные Capability.

**DE-003**

Каждый Domain может иметь собственные Policy.

**DE-004**

Каждый Domain формирует собственную экспертную практику.

**DE-005**

Platform Kernel обеспечивает единое взаимодействие между всеми Domain без смешения их организационного опыта.

**Архитектурное правило**

Платформа едина.

Организационный опыт специализирован.

**21. Federated Organizational Memory**

Organizational Memory платформы является федеративной.

Организационный опыт разделяется между независимыми Domain Memory.

Каждый Domain Memory развивается самостоятельно.

**FOM-001**

Каждый Domain обладает собственной Organizational Memory.

**FOM-002**

Domain Memory хранит только знания своей предметной области.

**FOM-003**

Перемещение знаний между Domain допускается только после подтверждения их применимости.

**FOM-004**

Platform Kernel управляет доступом к Domain Memory.

**FOM-005**

Cognitive Worker получают знания через Platform Kernel, а не посредством прямого доступа к Domain Memory.

**Архитектурное правило**

Память распределена.

Доступ централизован.

**22. Domain Knowledge**

Каждая предметная область формирует собственную экспертную модель.

Экспертная модель развивается на основании накопленного организационного опыта.

**DK-001**

Domain Knowledge содержит проверенные практики.

**DK-002**

Domain Knowledge содержит архитектурные решения.

**DK-003**

Domain Knowledge содержит повторяющиеся бизнес-паттерны.

**DK-004**

Domain Knowledge содержит специализированные рекомендации.

**DK-005**

Domain Knowledge используется Cognitive Worker соответствующей предметной области.

**Архитектурное правило**

Экспертиза развивается внутри Domain.

**23. Cross-Domain Collaboration**

При решении комплексных задач Platform Kernel может организовывать взаимодействие нескольких Domain.

Каждый Domain остаётся ответственным только за собственную область знаний.

**CDC-001**

Каждый Domain принимает решения только в пределах собственной компетенции.

**CDC-002**

Platform Kernel объединяет результаты работы нескольких Domain.

**CDC-003**

Обмен знаниями между Domain осуществляется посредством структурированных Artifact.

**CDC-004**

Domain не изменяют знания других Domain напрямую.

**CDC-005**

Совместное решение формируется Platform Kernel.

**Архитектурное правило**

Domain сотрудничают.

Domain не смешиваются.

**24. Decision Support Architecture**

Simple Solutions Practice является платформой поддержки принятия решений.

Платформа анализирует информацию, формирует рекомендации и подготавливает Decision Package.

Окончательное управленческое решение принимает Human Worker.

**DSA-001**

Платформа не принимает стратегические решения самостоятельно.

**DSA-002**

Каждый Cognitive Worker формирует структурированный Decision Package.

**DSA-003**

Decision Package содержит основания для предлагаемого решения.

**DSA-004**

Decision Package содержит возможные альтернативы.

**DSA-005**

Decision Package содержит ограничения и риски.

**Архитектурное правило**

Платформа рекомендует.

Человек принимает решение.

**25. Decision Package**

Decision Package является единым архитектурным форматом передачи результатов аналитической работы Cognitive Worker.

**DP-001**

Описание проблемы.

**DP-002**

Использованные данные и источники.

**DP-003**

Результаты анализа.

**DP-004**

Возможные варианты решения.

**DP-005**

Рекомендуемое действие.

**DP-006**

Оценка уверенности.

**DP-007**

Известные ограничения.

**DP-008**

Действия, требующие подтверждения Human Worker.

**Архитектурное правило**

Каждая рекомендация должна быть объяснимой.

**26. Human Authority**

Ответственность за управленческие решения принадлежит Human Worker.

Платформа не подменяет управленческую ответственность.

**HA-001**

Human Worker подтверждает решения, выходящие за пределы предоставленных полномочий платформы.

**HA-002**

Platform Kernel фиксирует факт принятия или отклонения рекомендации.

**HA-003**

Принятые решения используются для развития Organizational Memory.

**HA-004**

Отклонённые рекомендации также сохраняются вместе с обоснованием, если оно предоставлено.

**HA-005**

История решений используется для совершенствования Cognitive Worker и Domain Knowledge.

**Архитектурное правило**

Каждое решение становится новым организационным опытом.

**27. MVP Simplification**

Первая реализация платформы использует минимально необходимое количество архитектурных компонентов.

Архитектура должна предусматривать дальнейшее развитие без изменения Platform Kernel.

**MVP-001**

Первая версия платформы может использовать один Domain.

**MVP-002**

Первая версия платформы может использовать одного универсального Cognitive Worker.

**MVP-003**

Разделение Domain выполняется только после накопления достаточного организационного опыта.

**MVP-004**

Специализированные Cognitive Worker создаются по мере появления устойчивых предметных областей.

**MVP-005**

Архитектура платформы не изменяется при переходе от универсальных компонентов к специализированным.

**Архитектурное правило**

Сначала проверенная практика.

Потом специализация.

**28. Architectural Completeness**

Platform Profile определяет архитектурную конфигурацию платформы.

Organization Profile определяет модель конкретной организации.

Policy определяют правила функционирования платформы.

Context обеспечивает выполнение отдельных операций.

Domain обеспечивают разделение предметных областей.

Совместно данные архитектурные модели образуют единую систему конфигурации платформы.

**AC-001**

Каждая архитектурная модель отвечает только за собственную область ответственности.

**AC-002**

Новые архитектурные модели могут добавляться без изменения существующих.

**AC-003**

Platform Kernel является единственной точкой объединения архитектурных моделей.

**AC-004**

Модули не взаимодействуют с архитектурными моделями напрямую.

**AC-005**

Архитектурные модели являются декларативными и машиночитаемыми.

**Архитектурное правило**

Архитектурные модели описывают платформу.

Platform Kernel обеспечивает их совместную работу.

**29. Evolution Principle**

Архитектура платформы проектируется с учётом долгосрочного развития.

Первая реализация платформы использует только функциональность, необходимую для создания работающего MVP.

Все дополнительные возможности реализуются посредством новых модулей, Capability и Domain без изменения архитектурного ядра.

**EP-001**

Архитектура развивается эволюционно.

**EP-002**

Специализация появляется только после накопления подтверждённой практики.

**EP-003**

Platform Kernel сохраняет обратную совместимость архитектурных контрактов.

**EP-004**

Новые компоненты расширяют платформу, не изменяя существующую архитектуру.

**EP-005**

Каждая новая версия платформы должна оставаться совместимой с основными архитектурными принципами SSP.

**Архитектурное правило**

Развитие достигается расширением.

Не перепроектированием.
