
# AI-008. Pilot MVP Canonical Specification

## 1. Статус документа

**Статус:** Approved  
**Приоритет:** наивысший для Pilot MVP  
**Назначение:** устранить неоднозначности между целевой архитектурой SSP и первой рабочей версией продукта.

При прямом противоречии требований Pilot MVP настоящий документ имеет приоритет над остальной документацией. Противоречие необходимо зарегистрировать, но реализация продолжается по настоящей спецификации.

## 2. Порядок применения документации

1. **AI-008** — канонические решения Pilot MVP.
2. **M** — функциональное поведение модулей Pilot MVP.
3. **X** — исполняемая доменная модель, данные и порядок реализации.
4. **E** — инженерная архитектура, если она не противоречит AI-008, M и X.
5. **R** — контракты модулей и структура репозитория.
6. **S** — стандарты разработки, API, БД и тестирования.
7. **B** — целевая бизнес-модель и терминология.
8. **C** — целевая техническая архитектура.
9. **A** — принципы платформы.

Документ более низкого уровня может быть источником требований для более высокого. При прямом текстовом противоречии применяется порядок выше.

## 3. Цель Pilot MVP

Реализовать и развернуть один полный консультационный цикл:

Lead
→ Project + Workspace
→ Check-up Report
→ Estimation Report
→ Offer Contract + Invoice
→ OfferAccepted
→ Project Execution
→ Acceptance Certificate
→ Project Closed

## 5. Границы Pilot MVP

### Входят

* JWT-аутентификация;
* роли `ADMIN`, `MANAGER`, `SYSTEM`;
* Lead;
* Customer;
* Project;
* Project Workspace;
* Check-up;
* Estimation Report;
* Offer Contract;
* Invoice;
* Artifact;
* Business Event;
* Acceptance Certificate;
* минимальный Platform Kernel;
* in-process Event Dispatcher;
* минимальный Workflow Dispatcher;
* REST API;
* OpenAPI;
* Docker Compose deployment;
* полный E2E-тест консультационного цикла.

### Не входят

* Organizational Memory;
* Repository Optimization;
* NATS JetStream и распределённый Event Bus;
* AI/Cognitive Worker;
* полноценный Automation Engine;
* параллельные и компенсирующие workflow;
* клиентская учётная запись;
* Trust Levels и Delegated Identity;
* Discovery Meeting как отдельная сущность;
* Proposal как отдельная сущность;
* Agreement как отдельная сущность;
* Notification System;
* многоарендность;
* сложный UI.

## 6. Сопоставление целевой бизнес-модели и Pilot MVP

| Целевая модель B       | Pilot MVP                   |
| ---------------------- | --------------------------- |
| Inquiry                | Lead                        |
| Proposal               | Estimation Report           |
| Agreement + Offer      | Offer Contract              |
| Deliverable / Document | Artifact                    |
| Partner                | Customer без учётной записи |
| Consultant             | MANAGER                     |

## 7. Канонический жизненный цикл Project

DRAFT
→ IN_PROGRESS
→ ON_HOLD
→ IN_PROGRESS
→ WAITING_CLIENT
→ IN_PROGRESS
→ REVIEW
→ COMPLETED
→ CLOSED

Допустимые переходы:

| Текущее состояние | Событие                | Новое состояние |
| ----------------- | ---------------------- | --------------- |
| DRAFT             | OfferAccepted          | IN_PROGRESS     |
| IN_PROGRESS       | ProjectSuspended       | ON_HOLD         |
| ON_HOLD           | ProjectResumed         | IN_PROGRESS     |
| IN_PROGRESS       | ClientActionRequired   | WAITING_CLIENT  |
| WAITING_CLIENT    | ClientResponseReceived | IN_PROGRESS     |
| IN_PROGRESS       | ResultsSubmitted       | REVIEW          |
| REVIEW            | ResultsAccepted        | COMPLETED       |
| COMPLETED         | ProjectClosed          | CLOSED          |

`AWAITING_PAYMENT` не является состоянием Project. До оплаты Project остаётся `DRAFT`; состояние оплаты хранится в Offer Contract/Invoice.

## 9. API-контракт Pilot MVP

Базовый префикс: `/api/v1`.

Успех:

{
  "success": true,
  "data": {},
  "meta": {}
}

Ошибка:

{
  "success": false,
  "error": {
    "code": "PROJECT_INVALID_TRANSITION",
    "message": "Transition is not allowed",
    "details": {}
  }
}


Correlation ID передаётся заголовком `X-Correlation-ID`.
Пагинация: `page`, `page_size`.
Сортировка: `sort=created_at`, обратная — `sort=-created_at`.

## 10. Канонический жизненный цикл модуля

Состояния модуля:


REGISTERED
→ INITIALIZING
→ READY
→ RUNNING
→ DEGRADED
→ STOPPING
→ STOPPED

`DEGRADED` допускает возврат в `RUNNING`. `STOPPED` является конечным состоянием экземпляра модуля.

Последовательность bootstrap SDK:

install
→ initialize
→ register manifest
→ register capabilities
→ register event subscriptions
→ ready
→ running

Bootstrap-последовательность не является отдельной моделью состояний.

## 11. Definition of Done Pilot MVP

Pilot MVP завершён, когда:

1. система запускается командой `docker compose up -d`;
2. пользователь `MANAGER` входит по JWT;
3. полный цикл из раздела 3 проходит через REST API и UI;
4. все изменения Project выполняются только допустимыми событиями;
5. OFR, INV и ACT генерируются из `knowledge/`;
6. OpenAPI соответствует фактическому API;
7. миграции создают БД с нуля;
8. unit, integration и E2E tests проходят;
9. известные ограничения перечислены в release notes;
10. Organizational Memory и NATS не требуются для приёмки.
