# AI-001. How to Read SSP Documentation

## 1. Назначение

Документ определяет порядок чтения документации Simple Solutions Practice AI-разработчиком при реализации Pilot MVP.

Цель — получить минимально достаточный, непротиворечивый набор требований для выполнения конкретной задачи.

---

## 2. Канонический документ Pilot MVP

Перед началом любой задачи необходимо прочитать:


docs/AI/AI-008. Pilot MVP Canonical Specification.md


AI-008 фиксирует:

* границы Pilot MVP;
* технологический стек;
* приоритет документации;
* канонические статусы;
* канонические события;
* API-контракт;
* жизненный цикл модулей;
* Definition of Done.

Если другой документ противоречит AI-008, для Pilot MVP применяется AI-008.

---

## 3. Порядок применения документации

После AI-008 документы применяются в следующем порядке:

1. **M** — функциональные требования конкретного MVP-модуля;
2. **X** — доменная модель, физическая модель данных и технические спецификации;
3. **E** — инженерная архитектура;
4. **R** — контракты модулей и структура репозитория;
5. **S** — стандарты разработки, API, БД и тестирования;
6. **B** — целевая бизнес-модель;
7. **C** — целевая техническая архитектура;
8. **A** — архитектурные и операционные принципы.

Разделы более низкого приоритета могут быть источником требований для разделов более высокого приоритета. При прямом текстовом противоречии применяется порядок выше.

---

## 4. Минимальный набор документов для задачи

AI-разработчик не должен читать весь репозиторий для каждой задачи.

Для реализации конкретного модуля необходимо использовать:

1. AI-008;
2. соответствующий документ серии M;
3. применимые документы серии X;
4. применимые документы E, R и S;
5. связанные YAML и шаблоны из `knowledge/`;
6. документы B, C и A только для уточнения терминологии, бизнес-смысла и архитектурных ограничений.

## 6. Порядок анализа задачи

Перед написанием кода AI-разработчик обязан выполнить следующие действия:

1. определить, к какому модулю относится задача;
2. определить затрагиваемые сущности;
3. определить применимые события;
4. определить изменяемые состояния;
5. определить необходимые Artifact;
6. определить требуемые endpoints;
7. определить источники данных;
8. определить необходимые миграции;
9. определить требуемые тесты;
10. проверить границы Pilot MVP.

---

## 7. Проверка противоречий

Для каждого требования необходимо проверить:

* совпадают ли имена сущностей;
* совпадают ли имена статусов;
* совпадают ли имена событий;
* совпадают ли поля доменной и физической моделей;
* совпадают ли API-форматы;
* существуют ли источники данных для шаблонов;
* существуют ли обязательные X-003-спецификации;
* существует ли формальная схема контракта;
* не относится ли требование к Post-MVP.

---

## 8. Правила разрешения противоречий

### 8.1 Противоречие разрешено AI-008

Использовать AI-008 и продолжить выполнение задачи.

### 8.2 Противоречие между документами разных уровней

Использовать порядок приоритета из раздела 3.

### 8.3 Противоречие между документами одного уровня

Остановить соответствующую часть задачи и запросить решение владельца архитектуры.

### 8.4 Отсутствующая спецификация

Не реконструировать её самостоятельно, если это требует нового бизнес-решения.

Разрешено использовать существующий аналог только для технической формы, но не для добавления новых полей, состояний, событий или правил.

### 8.5 Неоднозначное имя

Не выбирать вариант самостоятельно. Использовать каноническое имя из AI-008 либо остановить задачу.

---

## 9. Правила работы с разделом B

Раздел B описывает целевую бизнес-модель.

Для Pilot MVP используются только сопоставления, зафиксированные в AI-008:

| Раздел B               | Pilot MVP         |
| ---------------------- | ----------------- |
| Inquiry                | Lead              |
| Proposal               | Estimation Report |
| Agreement + Offer      | Offer Contract    |
| Deliverable / Document | Artifact          |
| Partner                | Customer          |
| Consultant             | MANAGER           |

Сущности B, отсутствующие в Pilot MVP, не должны автоматически добавляться в код.

---

## 10. Правила работы с разделом C

Раздел C описывает целевую техническую архитектуру.

AI-разработчик обязан отделять:

* обязательные принципы;
* реализацию Pilot MVP;
* механизмы Post-MVP.

Trust Levels, Delegated Identity, распределённые интеграции, полноценная Notification System и другие механизмы, исключённые AI-008, не реализуются в Pilot MVP.

---

## 11. Правила работы с разделом E

Раздел E используется только в части, совместимой с AI-008.

Для Pilot MVP не применяются требования E, основанные на:

* C#;
* ASP.NET Core;
* Entity Framework Core;
* Vue;
* PrimeVue;
* NATS JetStream;
* LiteLLM;
* Ollama.

Инженерные принципы, не зависящие от стека, продолжают действовать.

---

## 12. Правила работы с knowledge/

Перед реализацией генерации документа необходимо проверить:

1. существует ли YAML-спецификация;
2. существует ли шаблон;
3. все ли обязательные поля соответствуют `document-standard.md`;
4. существует ли каждое событие-триггер;
5. существует ли источник каждого поля шаблона;
6. существует ли связь между Project и Service;
7. доступны ли данные Customer;
8. доступны ли реквизиты Platform Legal Profile;
9. определено ли место хранения результата;
10. соответствует ли результат типу Artifact.

Если хотя бы один обязательный источник отсутствует, генерация документа не реализуется до исправления спецификации.

---

## 13. Правила работы с X-003

Если для сущности существует отдельный документ `X-003-*`, он является основным источником требований к:

* полям;
* типам;
* ограничениям;
* Repository;
* API;
* переходам;
* validation rules.

Если отдельного X-003 нет, AI-разработчик не должен самостоятельно проектировать полный контракт сущности, если задача требует бизнес-решений.

Технические заготовки допустимы только после явного указания в задаче.

---

## 14. Ожидаемый результат чтения

До начала реализации AI-разработчик должен сформировать краткий рабочий контекст:


Задача:
Модуль:
Сущности:
Статусы:
События:
Artifacts:
Endpoints:
Источники данных:
Применимые документы:
Обнаруженные противоречия:
Блокирующие пробелы:
Границы задачи:


После этого допускается переход к коду.

---

## 15. Запреты

AI-разработчику запрещено:

* читать отдельный документ вне контекста связанных спецификаций;
* реализовывать сущность только по её упоминанию в B или C;
* использовать неканонический статус;
* использовать неканоническое событие;
* добавлять Post-MVP-компоненты;
* смешивать целевой и Pilot MVP технологические стеки;
* использовать шаблон без проверяемых источников данных;
* создавать API-контракт по собственному усмотрению;
* обходить обязательные переходы состояния;
* заменять отсутствующую спецификацию предположениями.

---

## 16. Критерий готовности к разработке

Задача готова к реализации, если:

* применимые документы определены;
* противоречия разрешены;
* сущности и поля определены;
* статусы и переходы определены;
* события определены;
* API-контракт определён;
* источники данных определены;
* формальные контракты доступны;
* задача входит в Pilot MVP;
* критерии приёмки определены.

Если хотя бы один обязательный элемент отсутствует, соответствующая часть задачи не готова к генерации кода.
