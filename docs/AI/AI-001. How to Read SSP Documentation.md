# AI-001. How to Read SSP Documentation

## Purpose

The Human Documentation is the only authoritative description of the SSP platform.

Do not infer architecture from source code.

Do not invent missing behaviour.

Always consult the documentation before implementation.

---

# Documentation Priority

When documents appear to overlap, use them in the following order:

1. M — Functional modules
2. E — Platform architecture
3. R — Module contracts
4. B — Business model
5. C — Business context
6. S — Development standards
7. A — Platform overview

If documents contradict each other, stop implementation and report the conflict.

Do not resolve documentation conflicts by changing the code.

# Reading Strategy

Never read the entire documentation.

Read only the documents required to complete the current task.

Always start with the functional module.

Read architectural documents only when additional context is required.

---

# Missing Information

If the required behaviour is not described:

* do not invent it;
* do not extend the architecture;
* do not introduce new business concepts.

Report that the documentation is incomplete.

---

# Architecture Changes

AI agents are not allowed to change the documented architecture.

If implementation requires an architectural change, stop and request a documentation update before continuing.

Documentation is always updated before code.
