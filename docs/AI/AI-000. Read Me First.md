# AI-000. Read Me First

## 1. Назначение

Этот документ определяет обязательный порядок работы AI-разработчика с документацией Simple Solutions Practice при создании Pilot MVP.

Перед началом любой задачи AI-разработчик обязан прочитать:

1. `AI-008. Pilot MVP Canonical Specification.md`;
2. применимый документ раздела `M`;
3. применимые документы раздела `X`;
4. применимые инженерные и контрактные документы разделов `E`, `R` и `S`;
5. соответствующие машинные спецификации и шаблоны из `knowledge/`.

## 2. Цель разработки

Создать и запустить Pilot MVP, реализующий полный консультационный цикл:

Lead
→ Project + Workspace
→ Check-up Report
→ Estimation Report
→ Offer Contract + Invoice
→ OfferAccepted
→ Project Execution
→ Acceptance Certificate
→ Project Closed

Реализация считается завершённой только после прохождения полного E2E-сценария.

## 3. Канонический источник требований Pilot MVP

Для Pilot MVP высший приоритет имеет:

docs/AI/AI-008. Pilot MVP Canonical Specification.md

При противоречии между документами AI-разработчик обязан:

1. применить решение из AI-008;
2. зафиксировать найденное противоречие;
3. не расширять задачу самостоятельными архитектурными решениями;
4. продолжить реализацию, если AI-008 содержит однозначное правило.

Если AI-008 не разрешает противоречие, разработка соответствующей части останавливается до получения решения владельца архитектуры.

## 7. Запрет на самостоятельное проектирование

AI-разработчик не должен:

* создавать новые бизнес-сущности;
* добавлять новые состояния жизненного цикла;
* переименовывать канонические события;
* менять структуру API-ответов;
* выбирать другой технологический стек;
* добавлять архитектурные слои без требования документации;
* реализовывать функциональность Post-MVP;
* заменять требования собственными предположениями.

При отсутствии спецификации AI-разработчик фиксирует пробел и запрашивает решение.

## 8. Канонические статусы Project

Допустимы только:

DRAFT
IN_PROGRESS
ON_HOLD
WAITING_CLIENT
REVIEW
COMPLETED
CLOSED

`AWAITING_PAYMENT` не является статусом Project.

## 9. Канонические события

Допустимые события Pilot MVP определены в AI-008.

Запрещено использовать вместо них:

* `ContractAccepted`;
* `ProposalApproved`;
* `OfferGenerated`;
* `ContractSent`.

Для подтверждения принятия оферты используется:

OfferAccepted

## 10. Требования к реализации

Каждая реализованная возможность должна содержать:

* доменную модель;
* схему БД;
* миграцию;
* Pydantic-модели;
* Repository;
* Service или Capability;
* API endpoint;
* проверку полномочий;
* обработку ошибок;
* публикацию предусмотренных событий;
* unit tests;
* integration tests;
* обновлённую OpenAPI-схему.

## 11. Требования к изменениям состояния

Изменение состояния Project выполняется только через разрешённый переход и сопровождается Business Event.

Прямое изменение статуса без проверки перехода запрещено.

Каждое событие должно содержать минимум:

event_id: uuid
event_type: string
aggregate_type: string
aggregate_id: uuid
occurred_at: datetime
actor_id: uuid | null
correlation_id: uuid
payload: object

## 12. Требования к API

Базовый префикс:

/api/v1

Успешный ответ:

{
  "success": true,
  "data": {},
  "meta": {}
}

Ответ с ошибкой:

{
  "success": false,
  "error": {
    "code": "ERROR_CODE",
    "message": "Human-readable message",
    "details": {}
  }
}

Пагинация:

page
page_size

Сортировка:

sort=created_at
sort=-created_at

## 13. Порядок выполнения задачи

Для каждой задачи AI-разработчик обязан:

1. определить применимые документы;
2. перечислить требования;
3. проверить отсутствие противоречий;
4. проверить зависимости;
5. определить изменяемые файлы;
6. реализовать минимально необходимый объём;
7. добавить тесты;
8. выполнить миграции и тесты;
9. проверить OpenAPI;
10. проверить отсутствие выхода за границы MVP;
11. сформировать отчёт о выполнении.

## 15. Условия остановки

AI-разработчик обязан остановить выполнение конкретной части задачи, если:

* отсутствует обязательная доменная спецификация;
* невозможно определить источник данных;
* два канонических документа дают разные требования;
* требуется новая бизнес-сущность;
* требуется новый статус или переход;
* отсутствует контракт события;
* отсутствует шаблон обязательного документа;
* изменение выходит за границы Pilot MVP.

Остановка одной части не блокирует выполнение независимых частей задачи.

## 16. Definition of Done

Pilot MVP считается завершённым только при выполнении Definition of Done из AI-008 и успешном прохождении полного E2E-сценария.

Organizational Memory, NATS JetStream и AI-компоненты не являются условиями приёмки Pilot MVP.
