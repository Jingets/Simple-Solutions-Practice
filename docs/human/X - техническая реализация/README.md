# Раздел X — Доменная модель и технические спецификации

## Назначение раздела

Раздел **X** содержит описание доменной модели платформы **Simple Solutions Practice (SSP)**, физической модели данных, технических спецификаций сущностей, внутренних взаимосвязей и архитектуры развёртывания.

Документы этого раздела являются мостом между бизнес-архитектурой (раздел B), инженерной архитектурой (раздел E) и реализацией (раздел R). Они определяют:
- доменные сущности и их атрибуты;
- физическую модель хранения данных (PostgreSQL);
- технические спецификации каждой сущности (поля, типы, связи, индексы);
- жизненные циклы и допустимые переходы состояний;
- архитектуру бэкэнда, фронтэнда и развёртывания;
- последовательность реализации MVP.

Все компоненты платформы — база данных, ORM-модели, репозитории, API, Workflow Engine и пользовательский интерфейс — должны соответствовать спецификациям, описанным в данном разделе.

---

## Перечень документов раздела

### 1. X-001 Доменная модель

**Назначение:**  
Определяет основные бизнес-сущности платформы, их назначение, атрибуты, взаимосвязи и жизненный цикл. Является основой для проектирования базы данных, ORM-моделей, DTO, Repository Layer и API.

**Содержание:**
- Основной принцип (сущности отражают реальные объекты бизнес-процесса)
- Доменные сущности MVP (12 сущностей)
- Связи между сущностями (схема)
- Жизненный цикл проекта (Lead → Project → Check-up → Estimation → Offer → Execution → Acceptance → Memory)
- Архитектурные ограничения
- Главный принцип (независимость от технологии)

---

### 2. X-002 Физическая модель данных

**Назначение:**  
Определяет физическую модель хранения данных в PostgreSQL. Является основой для проектирования схемы БД, моделей SQLAlchemy (или Entity Framework Core) и миграций.

**Содержание:**
- Основной принцип (реализация доменной модели)
- Общая структура базы данных (12 таблиц)
- Общие требования (поля id, created_at, updated_at, created_by, updated_by)
- Описание каждой таблицы (поля, типы, связи)
- Правила связей (Foreign Keys)
- Правила удаления (Soft Delete)
- Индексирование (обязательные индексы)
- Версионирование (версионируемые сущности)
- Архитектурные ограничения
- Главный принцип (прямое отображение доменной модели)

---

### 3. X-003 Технические спецификации сущностей

**Назначение:**  
Определяют техническую спецификацию каждой доменной сущности. Каждый документ является единственным источником требований для генерации ORM-модели, таблицы, репозитория, DTO и API-схемы.

**Перечень спецификаций:**
- X-003-003 — Project (центральная сущность)
- X-003-008 — Artifact (универсальный контейнер результатов)

**Структура каждой спецификации:**
- Назначение сущности
- Таблица
- Первичный ключ
- Поля (название, тип, null, описание)
- Статусы (допустимые значения)
- Связи (родительские и дочерние)
- Индексы
- Repository Contract
- API Contract
- Artifact Contract (при необходимости)
- Event Contract
- Validation Rules
- Автоматическая генерация
- Главный принцип

---

### 4. X-004 Внутренние взаимосвязи платформы

**Назначение:**  
Определяет взаимосвязи между доменными сущностями и допустимые переходы их состояний. Является основой для реализации SQLAlchemy Relationships, Workflow Engine, Business Rules, Repository Layer и API Validation.

**Содержание:**
- Основной принцип (определённые связи и жизненные циклы)
- Общая модель связей (схема)
- Кардинальность связей (таблица 1:N, 1:1)
- Жизненный цикл Project (статусы и переходы)
- Жизненный цикл Lead (NEW → QUALIFIED → CONVERTED/REJECTED)
- Жизненный цикл Offer Contract (DRAFT → SENT → ACCEPTED/REJECTED/EXPIRED)
- Жизненный цикл Artifact (ACTIVE → SUPERSEDED/ARCHIVED)
- Organizational Memory (создание после COMPLETED)
- Business Event и System Event
- Ограничения связей (каскадные правила)
- Workflow Validation
- Автоматическая генерация
- Главный принцип (никаких изменений в обход Workflow Engine)

---

### 5. X-005 Архитектура бэкэнда

**Назначение:**  
Определяет структуру серверной части платформы. Является обязательной спецификацией для реализации Backend MVP.

**Содержание:**
- Основной принцип (Backend строится вокруг Platform Kernel)
- Используемые технологии (C# 13, ASP.NET Core 9, Entity Framework Core, PostgreSQL)
- Общая структура проекта (14 каталогов)
- Назначение каждого каталога (app, kernel, modules, repositories, workflows, artifacts, events, policies, models, schemas, api, infrastructure, config, tests)
- Зависимости (направление сверху вниз)
- Архитектурные ограничения (7 запретов)
- Главный принцип (модульная система с Platform Kernel)

---

### 6. X-006 Архитектура фронтэнда

**Назначение:**  
Определяет архитектуру клиентской части платформы. Является технической спецификацией для реализации Frontend MVP.

**Содержание:**
- Основной принцип (Frontend — тонкий клиент, без бизнес-логики)
- Используемые технологии (Vue 3, TypeScript, Vite, PrimeVue, Tailwind CSS)
- Общая структура проекта (10 каталогов)
- Структура страниц MVP (10 страниц)
- Навигация (главное меню)
- API (взаимодействие только через Backend API)
- Управление состоянием (локальное состояние только для UI)
- Обработка ошибок
- Архитектурные ограничения (6 запретов)
- Главный принцип (Frontend — тонкий клиент)

---

### 7. X-007 Архитектура развёртывания

**Назначение:**  
Определяет архитектуру развёртывания платформы MVP. Является технической спецификацией для сборки рабочей среды.

**Содержание:**
- Основной принцип (один Docker Compose проект)
- Используемые технологии (Docker, Docker Compose, Nginx, PostgreSQL, NATS JetStream)
- Общая архитектура (схема)
- Контейнеры MVP (nginx, frontend, backend, postgres, nats)
- Docker Network (ssp-network)
- Volumes (postgres_data, artifacts_storage, nginx_logs)
- Artifact Storage (локальное файловое хранилище)
- Переменные окружения (8 переменных)
- Backend (REST API через Nginx)
- Frontend (статическая сборка через Nginx)
- PostgreSQL (миграции Alembic/EF Core)
- Nginx (TLS Termination, Reverse Proxy)
- HTTPS (Certbot для production)
- Логирование (разделение по компонентам)
- Backup (PostgreSQL и Artifact Storage)
- Масштабирование (MVP — один экземпляр)
- Архитектурные ограничения (4 запрета)
- Запуск платформы (docker compose up -d)
- Главный принцип (максимально простой и автоматизированный запуск)

---

### 8. X-008 MVP Последовательность реализации

**Назначение:**  
Определяет последовательность реализации платформы MVP. Каждый этап должен завершаться полностью работоспособной системой.

**Содержание:**
- Основной принцип (последовательное расширение функциональности)
- Milestone 1: Foundation (4 этапа)
  - Platform Skeleton
  - Platform Kernel
  - Database Layer
  - Authentication
- Milestone 2: Core Business (5 этапов)
  - Lead Module
  - Project Module
  - Check-up Module
  - Estimation Module
  - Offer Contract Module
- Milestone 3: Execution & Memory (5 этапов)
  - Workspace Module
  - Artifact Module
  - Project Execution Module (управление статусами)
  - Acceptance Module
  - Organizational Memory
  - Repository Optimization
- Milestone 4: MVP Ready (1 этап)
  - MVP Completion (E2E-тест полного цикла)
- Общая оценка трудозатрат (50–58 дней для одного разработчика)
- Definition of Ready (5 критериев)
- Definition of Done (8 критериев)
- Риски и митигация
- Главный принцип (каждый этап увеличивает возможности, не нарушая уже реализованное)
