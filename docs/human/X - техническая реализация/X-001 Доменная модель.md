## Цель

Настоящий документ определяет доменную модель платформы Simple Solutions Practice.

Документ описывает основные бизнес-сущности платформы, их назначение, взаимосвязи и жизненный цикл.

Документ является основой для проектирования базы данных, моделей SQLAlchemy (или Entity Framework Core), DTO, Repository Layer и API.

---

## Основной принцип

Все сущности платформы отражают реальные объекты бизнес-процесса.

Технические сущности не могут существовать без соответствующей бизнес-сущности.

Доменная модель описывает бизнес-платформу Simple Solutions Practice независимо от конкретной технологии хранения данных или реализации программного кода.

---

## Доменные сущности MVP

Первая версия платформы использует следующие основные сущности:

- **User** (Consultant) — пользователь платформы, эксперт.
- **Customer** — заказчик услуг.
- **Lead** — первичное обращение потенциального клиента.
- **Project** — центральная сущность, выполняемый консалтинговый проект.
- **Check‑up** — результаты первичной диагностики.
- **Estimation Report** — экспертная оценка объёма работ и стоимости.
- **Offer Contract** — договор-оферта.
- **Project Workspace** — рабочая область проекта.
- **Artifact** — результат интеллектуальной работы (документ, файл, отчёт).
- **Business Event** — факт изменения бизнес-состояния (неизменяем).
- **System Event** — техническое событие платформы.
- **Acceptance Certificate** — акт выполненных работ.
- **Organizational Memory Entry** — запись организационной памяти (опыт).

## Описание сущностей

### User (Consultant)

**Назначение**  
Представляет эксперта платформы, который ведёт проекты и принимает управленческие решения.

**Основные атрибуты**
- User ID (UUID)
- Email (уникальный)
- Password Hash
- Full Name
- Role (ADMIN / MANAGER / SYSTEM)
- Status (ACTIVE / INACTIVE)
- Created At
- Updated At

**Связи**  
User может быть назначен ответственным за несколько Projects.

**Основные атрибуты**
- Customer ID (UUID)
- Company Name
- Contact Name
- Email
- Phone
- Status (ACTIVE / INACTIVE)
- Created At
- Updated At
- Created By (ссылка на User)
- Updated By (ссылка на User)

### Lead

**Назначение**  
Представляет зарегистрированное обращение потенциального клиента.  
Lead является входной точкой жизненного цикла проекта.  
После принятия обращения Lead преобразуется в Project.

**Основные атрибуты**

- Updated At

### Project

**Назначение**  
Представляет выполняемый консалтинговый проект.  
Project является центральной сущностью платформы.  
Все остальные бизнес-сущности относятся к конкретному Project.

**Статусы (согласно M‑001 и M‑106)**
- **DRAFT** — проект зарегистрирован, но коммерческое предложение не оплачено.
- **IN_PROGRESS** — оплата получена, выполняются работы.
- **ON_HOLD** — выполнение приостановлено (по инициативе консультанта или клиента).
- **WAITING_CLIENT** — ожидание ответа или материалов от клиента.
- **REVIEW** — результаты переданы клиенту на проверку.
- **COMPLETED** — все работы выполнены, готовится акт.
- **CLOSED** — акт подписан, проект завершён.

**Единая таблица статусов проекта:**

Настоящая таблица устанавливает соответствие между статусами проекта, определёнными в **M‑001** (дорожная карта и соглашение о статусах), и статусами, используемыми в **X‑001** (доменная модель).

Таблица является обязательной для реализации **Workflow Engine**, **API валидации** и **UI отображения** статусов проекта.

---

| Статус в M‑001 / M‑106 | Статус в X‑001 | Business Event (событие перехода) | Описание |
|------------------------|----------------|-----------------------------------|----------|
| `DRAFT` | `DRAFT` | `ProjectCreated` | Проект зарегистрирован, но коммерческое предложение не оплачено. |
| `AWAITING_PAYMENT`¹ | _(отображается как `DRAFT` с флагом `offer_sent = true`)_ | `OfferSent` | Оферта направлена клиенту, оплата не поступила. |
| `IN_PROGRESS` | `IN_PROGRESS` | `ContractAccepted` | Оплата получена, договор заключён, выполняются работы. |
| `ON_HOLD` | `ON_HOLD` | `ProjectSuspended` | Выполнение приостановлено (по инициативе консультанта или клиента). |
| `WAITING_CLIENT` | `WAITING_CLIENT` | `ClientActionRequired` | Ожидание ответа или материалов от клиента. |
| `REVIEW` | `REVIEW` | `ResultsSubmitted` | Результаты переданы клиенту на проверку. |
| `COMPLETED` | `COMPLETED` | `ResultsAccepted` | Все работы выполнены, готовится акт. |
| `CLOSED` | `CLOSED` | `ProjectClosed` | Акт подписан, проект завершён. |

> ¹ **Статус `AWAITING_PAYMENT`** не выделен в отдельное состояние проекта, поскольку проект остаётся в `DRAFT` до момента оплаты. Однако в интерфейсе и API это состояние должно отображаться как `DRAFT` с дополнительным флагом `offer_sent = true` и `payment_status = AWAITING`. После регистрации события `OfferAccepted` проект автоматически переходит в `IN_PROGRESS`.

## Допустимые переходы статусов проекта

Все переходы выполняются исключительно через **Workflow Engine** и сопровождаются регистрацией соответствующего **Business Event**.

| Текущий статус | Событие | Новый статус |
|----------------|---------|--------------|
| `DRAFT` | `ContractAccepted` | `IN_PROGRESS` |
| `IN_PROGRESS` | `ProjectSuspended` | `ON_HOLD` |
| `ON_HOLD` | `ProjectResumed` | `IN_PROGRESS` |
| `IN_PROGRESS` | `ClientActionRequired` | `WAITING_CLIENT` |
| `WAITING_CLIENT` | `ClientResponseReceived` | `IN_PROGRESS` |
| `IN_PROGRESS` | `ResultsSubmitted` | `REVIEW` |
| `REVIEW` | `ResultsAccepted` | `COMPLETED` |
| `COMPLETED` | `ProjectClosed` | `CLOSED` |

**Обратные переходы запрещены.**  
**Переход через несколько статусов запрещён.**

Каждый переход статуса регистрирует соответствующий Business Event:

| Business Event | Описание |
|----------------|----------|

| `ProjectCompleted` | Работы завершены, готовится акт |

## Архитектурное ограничение

Ни один компонент платформы не имеет права изменять статус проекта в обход Workflow Engine.

Изменение статуса допускается только:
1. через явный вызов Workflow API;
2. после проверки допустимости перехода;
3. с обязательной регистрацией соответствующего Business Event.

Нарушение данного правила считается критической ошибкой архитектуры.

## Архитектурные ограничения

Каждая бизнес-сущность должна:
- иметь уникальный идентификатор (UUID);
- иметь определённый жизненный цикл;
- быть связана с Project (кроме Customer, Lead и User);
- поддерживать аудит изменений (created_at, updated_at, created_by, updated_by);
- использовать единые правила версионирования при необходимости;
- регистрировать Business Event при каждом изменении статуса.

## Definition of Done

Доменная модель считается утверждённой, если:
- определены все основные сущности MVP;
- определены связи между сущностями;
- определён жизненный цикл проекта с явными Business Events;
- статусы Project приведены в соответствие с M‑001 и M‑106;
- добавлена сущность User (Consultant);
- модель допускает автоматическую генерацию схемы базы данных, ORM-моделей и API-контрактов без изменения бизнес-смысла.

Доменная модель описывает бизнес-платформу Simple Solutions Practice независимо от конкретной технологии хранения данных или реализации программного кода.
