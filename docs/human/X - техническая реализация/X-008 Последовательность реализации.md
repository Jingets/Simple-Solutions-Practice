
**X-008 MVP Последовательность реализации**

**Статус:** MVP

**Приоритет:** P0

**Версия:** 1.1

**Дата:** 2026-07-21

---

## Цель

Настоящий документ определяет последовательность реализации платформы Simple Solutions Practice MVP.

Каждый этап должен завершаться полностью работоспособной системой.

Переход к следующему этапу допускается только после успешного завершения предыдущего.

---

## Основной принцип

Разработка ведётся по принципу последовательного расширения функциональности.

Каждый этап:
- добавляет одну законченную возможность;
- не нарушает предыдущие этапы;
- сопровождается автоматическими тестами;
- завершается рабочей версией платформы.

## Milestone 1: Foundation (Этапы 1–4)

### Этап 1. Platform Skeleton

**Цель:** Создать каркас проекта.

**Результат:**
- Backend запускается (FastAPI + Uvicorn);
- Frontend запускается (React + Vite);
- PostgreSQL подключена;
- Docker Compose работает;
- Platform Kernel инициализируется.

**Критерий Done:**
```bash
docker compose up -d
```
После выполнения:
- Frontend доступен по `http://localhost:3000`;
- Backend API доступен по `http://localhost:8000/docs`;
- PostgreSQL принимает подключения.

**Тесты:**
- Smoke-тест: проверка доступности `/health` эндпоинта.

**Ожидаемая длительность:** 2–3 дня

---

### Этап 2. Platform Kernel

**Цель:** Реализовать ядро платформы.

**Реализовать:**
- Module Registry (регистрация модулей);
- Capability Registry (регистрация возможностей);
- Event Dispatcher (синхронная и асинхронная отправка событий);
- Workflow Dispatcher (запуск и управление Workflow);
- Policy Engine (проверка бизнес-правил);
- Artifact Manager (интерфейс для работы с артефактами, без реализации хранилища).

**Результат:**
Kernel способен:
1. Зарегистрировать тестовый модуль;
2. Вызвать зарегистрированную Capability;
3. Отправить Event и получить ответ;
4. Проверить Policy и вернуть результат.

**Критерий Done:**
Написан интеграционный тест, который:
- регистрирует тестовый модуль;
- вызывает его метод через Capability Registry;
- отправляет Event через Event Dispatcher;
- получает корректный ответ.

**Тесты:**
- Модульные тесты для каждого компонента Kernel;
- Интеграционный тест полного цикла.

**Ожидаемая длительность:** 4–5 дней

**Критерий Done:**
```bash
alembic upgrade head
```
Все таблицы созданы.  
Написан тест, который:
- создаёт запись через Repository;
- читает её;
- обновляет;
- удаляет (soft delete).

**Тесты:**
- Unit-тесты Repository (с тестовой БД);
- Проверка миграций (up/down).

**Ожидаемая длительность:** 3–4 дня

### Этап 4. Authentication

**Цель:** Реализовать минимальную аутентификацию и авторизацию.

**Реализовать:**
- Модель пользователя (User);
- Роли:
  - `ADMIN` — полный доступ;
  - `MANAGER` — работа с Leads и Projects;
  - `SYSTEM` — сервисный аккаунт для внутренних вызовов;
- Регистрация пользователей (только через администрирование, для MVP);
- Вход: `email + password` → JWT;
- Защита эндпоинтов через JWT.

**Результат:**
Пользователь может войти и получить JWT.  
Защищённые эндпоинты доступны только с валидным токеном.

**Критерий Done:**
- Создан суперпользователь через команду `python manage.py createsuperuser`;
- API `/auth/login` возвращает JWT;
- API `/auth/me` возвращает информацию о пользователе;
- Запрос к защищённому эндпоинту без токена возвращает `401 Unauthorized`.

**Тесты:**
- Тесты регистрации (только админ);
- Тесты входа (успешный/неуспешный);
- Тесты защиты эндпоинтов.

**Ожидаемая длительность:** 3–4 дня

## Milestone 3: Execution & Memory (Этапы 10–14)

### Этап 10. Project Execution Module

**Цель:**  
Реализовать модуль сопровождения выполнения консалтингового проекта.

Модуль обеспечивает управление жизненным циклом проекта после перехода в статус `IN_PROGRESS`, фиксацию выполнения работ, взаимодействие с клиентом и подготовку проекта к завершению.

---

**Реализовать:**

**Модель Project (дополнение)**  
- Поддержка статусов:  
  - `IN_PROGRESS` — работа ведётся;  
  - `ON_HOLD` — выполнение приостановлено;  
  - `WAITING_CLIENT` — ожидание ответа или материалов от клиента;  
  - `REVIEW` — результаты переданы клиенту на проверку;  
  - `COMPLETED` — работы завершены, готовится акт.  
- Поля:  
  - `status` (Enum)  
  - `updated_at` (обновляется при каждом изменении статуса)  
  - `status_history` (JSON-массив или связанная таблица для хранения истории переходов)

**Рабочий журнал (Activity Log)**  
- Модель `ProjectActivity`  
- Поля:  
  - `id` (UUID)  
  - `project_id` (FK)  
  - `activity_type` (Enum: NOTE, MEETING, DECISION, DOCUMENT, MILESTONE)  
  - `description` (текст)  
  - `created_at`  
  - `created_by` (ссылка на User)  
- API для добавления и просмотра записей

**Workflow Engine (дополнение)**  
- Реализовать допустимые переходы статусов:  

| Текущий статус | Событие | Новый статус |
|----------------|---------|--------------|
| IN_PROGRESS | ProjectSuspended | ON_HOLD |
| ON_HOLD | ProjectResumed | IN_PROGRESS |
| IN_PROGRESS | ClientActionRequired | WAITING_CLIENT |
| WAITING_CLIENT | ClientResponseReceived | IN_PROGRESS |
| IN_PROGRESS | ResultsSubmitted | REVIEW |
| REVIEW | ResultsAccepted | COMPLETED |

- Все переходы регистрируют соответствующий **Business Event**:
  - `ProjectSuspended`
  - `ProjectResumed`
  - `ClientActionRequired`
  - `ClientResponseReceived`
  - `ResultsSubmitted`
  - `ResultsAccepted`

**API**  
- `POST /projects/{id}/activities` — добавление записи в рабочий журнал  
- `GET /projects/{id}/activities` — получение журнала проекта  
- `PATCH /projects/{id}/status` — смена статуса (через Workflow Engine)  
- `GET /projects/{id}/timeline` — хронология статусов и ключевых событий

**Business Events (дополнение)**  
Все переходы статусов регистрируют Business Events согласно X-001.

---

**Результат:**  
Проект перестаёт быть статичной сущностью.  
Консультант может:
- вести рабочий журнал;
- изменять статус проекта в зависимости от хода работ;
- фиксировать взаимодействие с клиентом;
- отслеживать полную историю выполнения проекта.

---

**Критерий Done:**  
- Проект переходит в `IN_PROGRESS` автоматически после `ContractAccepted`;  
- Все статусы изменяются только через Workflow Engine;  
- Недопустимые переходы отклоняются с понятной ошибкой;  
- Каждое изменение статуса регистрирует Business Event;  
- Рабочий журнал позволяет добавить запись и просмотреть историю;  
- История статусов доступна через API.

---

**Тесты:**  
- Создание записи в рабочем журнале;  
- Получение журнала проекта;  
- Каждый допустимый переход статуса (6 переходов);  
- Каждый недопустимый переход (например, `IN_PROGRESS → COMPLETED` без `REVIEW`);  
- Проверка регистрации Business Events при каждом переходе;  
- Проверка автоматического перехода в `IN_PROGRESS` после оплаты договора.

---

**Ожидаемая длительность:** 4 дня

**Цель:** Реализовать полноценное управление артефактами.

**Реализовать:**
- Полную реализацию Artifact Manager (хранилище, версионирование);

**Тесты:**
- Создание Artifact;
- Версионирование;

### Этап 15. Repository Optimization

**Тесты:**
- Обнаружение дублей;
- Объединение записей;
- Архивация устаревших записей;
- Проверка, что бизнес-данные не потеряны.

## Milestone 4: MVP Ready (Этап 15)

### Этап 16. MVP Completion

**Цель:** Финальная проверка и интеграционное тестирование.

**Реализовать:**
- Сквозной E2E-тест полного цикла;
- Проверка всех интеграций;
- Нагрузочное тестирование (базовое);
- Документация для пользователей;
- Документация для разработчиков.

**E2E-тест должен проходить полный цикл:**

```
1. Регистрация Lead (через API)
2. Преобразование Lead в Project
3. Проведение Check-up
4. Получение Estimation Report
5. Формирование Offer Contract
6. Подписание Contract (переход в IN_PROGRESS)
7. Добавление Artifact'ов в Workspace
8. Завершение проекта (Acceptance Certificate)
9. Формирование Organizational Memory Entry
10. Оптимизация памяти (проверка, что дубли удалены)
```

**Результат:**
Система полностью готова к демонстрации.

**Критерий Done:**
- E2E-тест проходит успешно без ручного вмешательства;
- Пользователь может пройти полный цикл через UI;
- Документация актуальна;
- Система стабильна (нет критических ошибок).

**Тесты:**
- E2E-тест (автоматический);
- Нагрузочный тест (10 параллельных проектов);
- Тесты безопасности (JWT, роли).

**Ожидаемая длительность:** 5 дней

## Definition of Ready

Перед началом каждого этапа должны быть:
- ✅ утверждены документы серии M;
- ✅ утверждены документы серии X;
- ✅ реализованы предыдущие этапы;
- ✅ пройдены автоматические тесты;

- ✅ назначен ответственный разработчик.

## Definition of Done

Этап считается завершённым, если:
- ✅ функциональность реализована полностью;
- ✅ проходят все тесты (unit, integration, e2e);
- ✅ соблюдены стандарты серии S;
- ✅ отсутствуют нарушения Specification Compliance;
- ✅ система остаётся работоспособной;
- ✅ код задокументирован;
- ✅ выполнено ревью кода;
- ✅ изменения влиты в основную ветку.

## Риски и их митигация

| Риск | Вероятность | Митигация |
|------|-------------|-----------|
| Задержка реализации Kernel | Средняя | Реализовать минимально рабочую версию, расширять позже |
| Сложность расчёта стоимости | Низкая | Правила фиксированы для MVP |
| Проблемы с производительностью | Низкая | MVP не требует высокой нагрузки |
| Изменение требований | Средняя | Документы X-серии фиксированы, изменения только через ADR |
| Интеграционные проблемы | Средняя | E2E-тест на каждом этапе |

## Главный принцип

Каждый этап разработки должен увеличивать возможности платформы, не нарушая уже реализованную функциональность.

После завершения любого этапа платформа должна оставаться полностью работоспособной и готовой к дальнейшему развитию.

После завершения MVP и трёх реальных проектов проводится анализ повторяющихся действий (согласно M-001, Rule of Three). Автоматизация внедряется только на этапе 2 развития платформы.
