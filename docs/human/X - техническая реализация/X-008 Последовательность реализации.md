# X-008. Последовательность реализации

## 1. Назначение

Документ определяет каноническую последовательность реализации Pilot MVP платформы Simple Solutions Practice.

Все этапы разработки выполняются последовательно. Переход к следующему этапу допускается только после выполнения критериев завершения предыдущего.

---

# 2. Принципы реализации

Разработка строится по следующим правилам:

- сначала создаётся инфраструктура;
- затем Platform Kernel;
- затем доменная модель;
- затем бизнес-модули;
- затем генерация документов;
- затем пользовательский интерфейс;
- затем тестирование;
- затем подготовка демонстрационной версии.

Каждый этап должен быть работоспособен независимо.

---

# 3. Этап 1. Инфраструктура

Цель:

Создать воспроизводимое окружение разработки.

Результат:

- Docker Compose;
- PostgreSQL;
- Backend;
- Frontend;
- nginx;
- Alembic;
- Health Check.

Критерии завершения:

- система запускается командой

```bash
docker compose up -d
```

- открывается `/health`;
- открывается `/docs`.

---

# 4. Этап 2. Platform Kernel

Реализуются:

- Module Registry;
- Capability Registry;
- Event Dispatcher;
- Workflow Dispatcher;
- Artifact Manager;
- Business Event Store.

Критерии завершения:

- все компоненты регистрируются автоматически;
- Kernel запускается без ошибок.

---

# 5. Этап 3. Identity

Реализуются:

- User;
- JWT;
- Authentication;
- Authorization;
- роли ADMIN, MANAGER, SYSTEM.

Критерии завершения:

- пользователь может войти в систему;
- защищённые endpoints требуют JWT.

---

# 6. Этап 4. Customer Management

Реализуются:

- Lead;
- Customer;
- создание;
- поиск;
- просмотр.

Создаются события:

```text
LeadRegistered
CustomerCreated
```

---

# 7. Этап 5. Project

Реализуются:

- Project;
- жизненный цикл;
- проверки переходов;
- Business Events.

Статусы:

```text
DRAFT
IN_PROGRESS
ON_HOLD
WAITING_CLIENT
REVIEW
COMPLETED
CLOSED
```

Критерии завершения:

Все допустимые переходы проходят integration tests.

---

# 8. Этап 6. Workspace

Реализуются:

- Workspace;
- файловое хранилище;
- список Artifact;
- журнал проекта.

---

# 9. Этап 7. Check-up

Реализуются:

- проведение диагностики;
- Check-up Report;
- Business Event.

Создаётся:

```text
CheckupCompleted
```

---

# 10. Этап 8. Estimation

Реализуются:

- расчёт стоимости;
- Estimation Report;
- публикация результата.

Создаётся:

```text
ProjectEstimated
```

---

# 11. Этап 9. Offer

Реализуются:

- Offer Contract;
- Invoice;
- публикация оферты.

События:

```text
OfferPublished
InvoiceGenerated
```

---

# 12. Этап 10. Payment

Реализуются:

- регистрация оплаты;
- подтверждение оплаты;
- запуск проекта.

События:

```text
PaymentRegistered
OfferAccepted
```

После `OfferAccepted` Project переходит в:

```text
IN_PROGRESS
```

---

# 13. Этап 11. Execution

Реализуются:

- выполнение проекта;
- изменение состояний;
- загрузка документов;
- рабочее пространство проекта.

События:

```text
ResultsSubmitted
ClientActionRequired
ClientResponseReceived
ProjectResumed
ProjectSuspended
```

---

# 14. Этап 12. Acceptance

Реализуются:

- Acceptance Certificate;
- завершение проекта;
- закрытие проекта.

События:

```text
ResultsAccepted
AcceptanceCertificateGenerated
ProjectCompleted
ProjectClosed
```

---

# 15. Этап 13. Генерация документов

Подключаются:

- YAML;
- Markdown Templates;
- Artifact Manager.

Генерируются:

- Check-up Report;
- Estimation Report;
- Offer Contract;
- Invoice;
- Acceptance Certificate.

Все документы должны формироваться автоматически.

---

# 16. Этап 14. Frontend

Реализуются страницы:

- Login;
- Dashboard;
- Projects;
- Project Card;
- Workspace;
- Documents.

Frontend использует только REST API.

---

# 17. Этап 15. Integration Tests

Проверяются:

- API;
- миграции;
- Repository;
- генерация документов;
- события;
- авторизация.

---

# 18. Этап 16. End-to-End

Полностью выполняется сценарий:

```text
Lead
→ Customer
→ Project
→ Workspace
→ Check-up
→ Estimation
→ Offer
→ Invoice
→ Payment
→ Execution
→ Acceptance Certificate
→ Closed Project
```

Без ручного вмешательства.

---

# 19. Definition of Done Pilot MVP

Pilot MVP считается завершённым, если:

- выполняется полный сценарий;
- все документы генерируются автоматически;
- REST API соответствует OpenAPI;
- Business Events сохраняются;
- Docker Compose запускает систему;
- integration tests проходят;
- E2E tests проходят;
- отсутствуют ручные изменения БД.

---

# 20. Запрещённые отклонения

Во время реализации запрещено:

- изменять последовательность этапов;
- добавлять новые сущности без документации;
- изменять жизненный цикл Project;
- добавлять новые события;
- менять технологический стек;
- реализовывать Post-MVP функциональность.
