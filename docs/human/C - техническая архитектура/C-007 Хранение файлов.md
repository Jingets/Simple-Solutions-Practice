**C-007 Хранение файлов**

**Версия:** 1.0

**Статус:** Draft

**Раздел:** C — Technical Architecture

**Связанные документы**

- B-001 Бизнес-модель

- B-003 Справочник бизнес-событий

- C-001 Обзор архитектуры платформы

- C-004 Модель доступа и матрица доверия

- C-005 Генерация бизнес-материалов

**1. Назначение**

File Storage определяет единый подход к хранению, использованию и сопровождению файлов цифровой платформы Simple Solutions Practice.

Документ устанавливает:

- модель файлов;

- жизненный цикл файлов;

- связь файлов с Business Objects;

- правила хранения;

- архитектурные принципы.

Настоящий документ не зависит от конкретной файловой системы или технологии хранения.

**2. Архитектурный принцип**

Платформа хранит не файлы.

Платформа хранит информацию, представленную файлами.

Файл является способом хранения или передачи информации, но не самостоятельной бизнес-сущностью.

**3. File Model**

File представляет собой цифровой объект, содержащий информацию, связанную с одним или несколькими Business Objects.

File не содержит бизнес-логики.

File существует только как приложение к бизнес-модели платформы.

**3.1 File Categories**

Платформа поддерживает следующие категории файлов.

**Generated Files**

Файлы, автоматически сформированные платформой.

Примеры:

- PDF;

- DOCX;

- экспортные отчёты;

- архивы.

**Uploaded Files**

Файлы, загруженные пользователями.

Примеры:

- изображения;

- презентации;

- таблицы;

- документы;

- архивы.

**Media Files**

Мультимедийные материалы.

Примеры:

- фотографии;

- аудио;

- видео;

- схемы;

- диаграммы.

**System Files**

Файлы, используемые внутренними сервисами платформы.

Примеры:

- шаблоны;

- логотипы;

- служебные изображения;

- ресурсы интерфейса.

**Архитектурный принцип**

Категория файла определяет его назначение.

Категория не определяет место хранения.

**4. File Lifecycle**

Каждый File проходит единый жизненный цикл.

**4.1 Registration**

После появления файла платформа регистрирует его.

Фиксируются:

- идентификатор;

- категория;

- владелец;

- источник;

- дата создания;

- размер;

- тип содержимого.

**4.2 Validation**

Перед использованием файл проходит проверку.

Проверяются:

- целостность;

- допустимый формат;

- размер;

- соответствие политике платформы.

При необходимости файл отклоняется.

**4.3 Association**

После проверки файл связывается с соответствующими Business Objects.

Один файл может использоваться несколькими объектами платформы.

Связь осуществляется посредством ссылок, а не копирования.

**4.4 Active Use**

Во время эксплуатации файл может использоваться:

- Business Artifacts;

- Workspace;

- Notification System;

- внешними интеграциями.

Использование файла не изменяет его содержимое.

**4.5 Archive**

После завершения использования файл переводится в архивное состояние.

Архивация не нарушает существующие связи с историческими Business Objects.

**Архитектурный принцип**

Файл создаётся один раз.

Повторное использование осуществляется посредством ссылок.

**5. File Association Model**

Файл существует в платформе только в связи с другими архитектурными объектами.

Платформа не использует файлы как самостоятельные элементы бизнес-модели.

**5.1 Association Principles**

Файл может быть связан с:

- Business Object;

- Business Artifact;

- Workspace;

- Notification;

- Business Event.

Связь осуществляется посредством идентификаторов.

**5.2 Multiple Associations**

Один File может одновременно использоваться несколькими объектами платформы.

Создание дополнительных копий файла не допускается.

Все связи должны указывать на один зарегистрированный File.

**5.3 Association Integrity**

Удаление связи между File и Business Object не приводит к автоматическому удалению файла.

Удаление файла допускается только после проверки отсутствия активных связей.

**5.4 Ownership**

Каждый File имеет владельца.

Владельцем может быть:

- Platform;

- Partner;

- Customer;

- Workspace;

- System Service.

Владелец определяет ответственность за жизненный цикл файла, но не влияет на права доступа.

**5.5 Referential Consistency**

Все ссылки на File должны оставаться корректными на протяжении всего срока существования соответствующих Business Objects.

Платформа обеспечивает целостность ссылочной модели.

**Архитектурный принцип**

Файл существует один раз.

Количество ссылок на него не ограничено.

**6. File Integrity**

Платформа обеспечивает неизменность содержимого зарегистрированного файла.

**6.1 Immutable Content**

После регистрации содержимое файла не изменяется.

Любое изменение оформляется регистрацией нового File.

**6.2 Metadata**

Допускается изменение только служебных метаданных.

Например:

- описание;

- категория;

- теги;

- ссылки;

- статус.

Изменение метаданных не влияет на содержимое файла.

**6.3 Content Verification**

Для каждого файла фиксируются признаки, позволяющие подтвердить его неизменность.

Конкретный механизм проверки определяется технической реализацией платформы.

**6.4 Version Independence**

Версия файла определяется его содержимым.

Изменение Business Object не создаёт новую версию файла.

Изменение файла не изменяет Business Object автоматически.

**6.5 File Replacement**

Замена файла осуществляется путём регистрации нового экземпляра и обновления соответствующих связей.

Исходный файл сохраняется до завершения его жизненного цикла.

**Архитектурный принцип**

Зарегистрированный File является неизменяемым.

Изменяется связь с файлом, но не сам файл.

**7. File Access**

Доступ к файлам определяется общей моделью безопасности платформы.

File Storage не содержит собственной модели авторизации.

**7.1 Authorization**

Права доступа определяются:

- Identity;

- Trust Level;

- Permission Model;

- Business Rules.

**7.2 Context Access**

Файл доступен только в контексте соответствующего Business Object.

Получение прямого доступа к файлу вне бизнес-контекста не является обязательным требованием платформы.

**7.3 Audit**

Каждое обращение к File может быть зарегистрировано системой аудита.

Состав регистрируемых событий определяется Audit & Logging.

**7.4 External Access**

При необходимости файл может быть предоставлен внешним системам.

Порядок такого доступа определяется механизмами интеграции платформы.

**Архитектурный принцип**

Доступ предоставляется не к файлу.

Доступ предоставляется к информации, связанной с соответствующим Business Object.

**8. Storage Principles**

Storage обеспечивает долговременное и надёжное хранение файлов платформы независимо от используемой технологии.

**8.1 Storage Independence**

Архитектура платформы не зависит от конкретной технологии хранения файлов.

В качестве хранилища могут использоваться:

- локальные файловые системы;

- объектные хранилища;

- облачные сервисы;

- распределённые системы хранения.

Выбор технологии не влияет на архитектурную модель File Storage.

**8.2 Persistent Storage**

Все зарегистрированные файлы сохраняются до завершения их жизненного цикла.

Платформа не удаляет файлы автоматически без выполнения правил жизненного цикла.

**8.3 Availability**

Файлы должны быть доступны всем компонентам платформы, имеющим соответствующие полномочия.

Недоступность отдельных компонентов хранения не должна нарушать целостность бизнес-модели.

**8.4 Backup**

Файлы подлежат резервному копированию в соответствии с политиками платформы.

Механизм резервного копирования определяется технической реализацией и не является частью настоящего документа.

**8.5 Recovery**

Платформа должна обеспечивать возможность восстановления файлов после технических сбоев.

Процедуры восстановления определяются эксплуатационной документацией.

**Архитектурный принцип**

Storage отвечает за сохранность файлов.

File Storage не отвечает за бизнес-правила использования файлов.

**9. File Design Principles**

Настоящие принципы являются обязательными при проектировании всех механизмов хранения и использования файлов платформы.

**FDP-001 Business Context**

Файл существует только в контексте бизнес-модели.

Хранение файлов вне связи с Business Objects не допускается.

**FDP-002 Single Instance**

Каждый файл регистрируется один раз.

Повторное использование осуществляется посредством ссылок.

**FDP-003 Immutable Content**

После регистрации содержимое файла становится неизменяемым.

Любые изменения оформляются созданием нового файла.

**FDP-004 Referential Integrity**

Все ссылки на файлы должны сохранять корректность на протяжении всего жизненного цикла связанных объектов.

**FDP-005 Separation of Concerns**

Файл хранит информацию.

Business Objects определяют смысл этой информации.

**FDP-006 Technology Independence**

Архитектура хранения файлов не зависит от конкретной технологии реализации.

**FDP-007 Traceability**

Использование каждого файла должно быть прослеживаемо.

Платформа должна позволять определить:

- источник файла;

- связанные объекты;

- историю использования.

**FDP-008 Security by Platform**

Доступ к файлам определяется общей моделью безопасности платформы.

File Storage не реализует собственную систему авторизации.

**FDP-009 Long-Term Consistency**

Изменение бизнес-процессов не должно нарушать доступность ранее зарегистрированных файлов.

**FDP-010 Information Preservation**

Файл рассматривается как носитель информации, необходимой для обеспечения непрерывности бизнес-процессов и сохранения истории платформы.

**10. Заключительные положения**

File Storage определяет единый архитектурный подход к регистрации, хранению и использованию файлов в платформе Simple Solutions Practice.

Настоящий документ обязателен для всех компонентов платформы, создающих, использующих или сопровождающих файлы.

Любое расширение механизмов хранения должно соответствовать принципам настоящего документа.
