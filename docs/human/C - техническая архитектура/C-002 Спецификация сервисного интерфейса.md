**1. Назначение**

Service Interface Specification определяет единые принципы взаимодействия между компонентами цифровой платформы Simple Solutions Practice.

Документ описывает:

- правила обмена информацией;

- модель команд и запросов;

- обработку событий;

- взаимодействие внутренних модулей;

- взаимодействие с внешними сервисами.

Настоящий документ не определяет конкретные сетевые протоколы или способы передачи данных.

Он определяет логический контракт взаимодействия между всеми компонентами платформы.

**2. Основные принципы**

**2.1 Интерфейсы реализуют бизнес-модель**

Любой интерфейс платформы обязан соответствовать бизнес-архитектуре SSP.

Интерфейс не может изменять бизнес-логику, определённую документами раздела B.

**2.2 Команды изменяют состояние**

Любое изменение Business Objects выполняется посредством Command.

Command инициирует Business Event.

Непосредственное изменение Persistent Business Objects запрещается.

**2.3 Запросы не изменяют состояние**

Получение информации выполняется посредством Query.

Query не создаёт Business Events.

Query не изменяет состояние объектов.

**2.4 События информируют систему**

Business Events и System Events используются для информирования внутренних компонентов платформы о произошедших изменениях.

События не содержат бизнес-логики.

Они фиксируют факт её выполнения.

**2.5 Контракт важнее транспорта**

Логика взаимодействия определяется контрактом сервиса.

Выбор конкретного способа передачи данных (REST, GraphQL, gRPC, Message Bus и т.д.) является вопросом реализации и не влияет на архитектуру платформы.

**2.6 Интерфейсы должны быть идемпотентными**

Повторная передача одной и той же команды не должна приводить к повторному изменению бизнес-состояния.

Идемпотентность обеспечивается механизмами платформы.

**2.7 Каждый интерфейс имеет единственную ответственность**

Один сервисный интерфейс решает одну задачу предметной области.

Объединение нескольких независимых операций в одном интерфейсе не допускается.

**2.8 Интерфейсы независимы от пользовательского интерфейса**

Веб-сайт, Telegram, MAX, мобильное приложение или административная панель используют единые сервисные интерфейсы.

Добавление нового клиентского приложения не требует изменения бизнес-логики платформы.

**3. Service Interaction Model**

Все взаимодействие компонентов платформы осуществляется посредством трёх типов сообщений.

Каждый тип сообщения имеет собственное назначение и правила обработки.

**3.1 Command**

Command представляет собой намерение изменить бизнес-состояние платформы.

Command инициируется пользователем, системой либо внешней интеграцией.

Command всегда обрабатывается Automation Decision Pipeline.

Command не гарантирует успешное изменение состояния.

Результат определяется Business Rules и Permission Model.

**Примеры Command**

- Create Inquiry

- Create Proposal

- Send Proposal

- Accept Proposal

- Reject Proposal

- Create Agreement

- Activate Project

- Complete Stage

- Complete Project

- Archive Project

- Generate Invoice

- Register Payment

**Требования**

Каждый Command обязан:

- иметь единственную цель;

- быть идемпотентным;

- иметь автора выполнения;

- иметь время создания;

- иметь уникальный идентификатор;

- инициировать не более одного Business Event.

**3.2 Query**

Query представляет собой запрос информации.

Query никогда не изменяет бизнес-состояние платформы.

Query может обращаться как к Persistent Business Objects, так и к Derived Objects.

Получение информации не создаёт Business Events.

**Примеры Query**

- Get Project

- Get Workspace

- Get Partner

- Get Agreement

- Get Invoice

- Get Timeline

- Get Dashboard

- Get Notifications

**Требования**

Каждый Query обязан:

- быть детерминированным;

- не изменять состояние платформы;

- возвращать только разрешённые данные;

- учитывать Permission Model.

**3.3 Event**

Event представляет собой зарегистрированный факт произошедшего изменения.

Event используется для информирования внутренних компонентов платформы.

Event не содержит алгоритмов обработки.

**Типы Event**

Business Event

Отражает изменение предметной области.

System Event

Отражает выполнение внутренних процессов платформы.

**Требования**

Каждый Event обязан:

- иметь источник возникновения;

- иметь время регистрации;

- иметь уникальный идентификатор;

- иметь ссылку на связанный объект;

- быть неизменяемым после регистрации.

**4. Request Processing Pipeline**

Любое обращение к сервисному интерфейсу платформы проходит единый конвейер обработки.

Независимо от источника обращения, последовательность обработки остаётся неизменной.

**4.1 Приём запроса**

Платформа принимает Command или Query от одного из поддерживаемых источников.

Источник обращения может быть:

- Web Application;

- Telegram;

- MAX;

- Mobile Application;

- External Service;

- Internal Automation.

На данном этапе запрос получает уникальный идентификатор.

**4.2 Идентификация**

Платформа определяет источник обращения.

Проверяется:

- личность инициатора;

- тип клиента;

- способ взаимодействия;

- наличие действующей сессии либо иного механизма аутентификации.

**4.3 Авторизация**

Перед выполнением запроса применяется Permission Model.

Определяется:

- разрешена ли операция;

- над каким объектом допускается выполнение;

- имеются ли дополнительные ограничения.

При отсутствии необходимых прав дальнейшая обработка прекращается.

**4.4 Валидация**

Проверяется корректность полученных данных.

Проверке подлежат:

- обязательные параметры;

- формат данных;

- ссылки на существующие объекты;

- непротиворечивость запроса.

При обнаружении ошибок обработка прекращается.

**4.5 Business Rules Evaluation**

Перед выполнением Command применяется Business Rules Catalogue.

Проверяются:

- допустимость операции;

- текущее состояние объекта;

- ограничения предметной области;

- взаимосвязанные бизнес-правила.

При нарушении хотя бы одного правила изменение бизнес-состояния запрещается.

**4.6 Выполнение команды**

При успешном прохождении предыдущих этапов выполняется соответствующая бизнес-операция.

Изменение состояния производится исключительно посредством Business Objects.

**4.7 Регистрация Business Event**

После успешного выполнения операции регистрируется соответствующий Business Event.

Business Event становится частью Source of Truth.

**4.8 Запуск Automation**

Business Event передаётся в Automation Decision Pipeline.

Платформа определяет необходимые Business Automation и Infrastructure Automation.

**4.9 Формирование ответа**

После завершения обязательной обработки формируется ответ.

Ответ может содержать:

- результат выполнения;

- обновлённое состояние объекта;

- идентификаторы созданных объектов;

- диагностическую информацию;

- сообщения для пользователя.

**4.10 Аудит**

Факт обработки запроса регистрируется в Audit Log.

Фиксируются:

- идентификатор запроса;

- инициатор;

- время выполнения;

- результат;

- зарегистрированные события;

- ошибки (при наличии).

**Архитектурный принцип**

Все сервисные интерфейсы платформы используют единый Request Processing Pipeline.

Добавление нового способа взаимодействия не изменяет последовательность обработки.

Новые клиентские приложения обязаны использовать существующий конвейер без изменения бизнес-логики платформы.

**5. Response Model**

Все сервисные интерфейсы платформы используют единую модель ответа.

Независимо от способа взаимодействия ответ имеет одинаковую логическую структуру.

Конкретный формат представления определяется используемой технологией передачи данных.

**5.1 Общая структура ответа**

Ответ может содержать:

- результат выполнения;

- сведения об обработанном объекте;

- зарегистрированные события;

- предупреждения;

- диагностическую информацию;

- рекомендации по дальнейшим действиям.

Ответ не должен содержать внутренних технических деталей реализации платформы.

**5.2 Successful Response**

Успешный ответ подтверждает завершение обработки запроса.

Успешный ответ может содержать:

- идентификатор объекта;

- текущее состояние объекта;

- сведения о созданных объектах;

- зарегистрированные Business Events;

- последующие рекомендуемые действия.

**Примеры**

После регистрации Inquiry:

- создан Inquiry;

- зарегистрирован Business Event;

- определён следующий допустимый шаг.

После оплаты Invoice:

- зарегистрирован Payment;

- изменён статус Invoice;

- активирован Project;

- запущены соответствующие процессы автоматизации.

**5.3 Validation Response**

При невозможности обработки вследствие некорректных данных платформа возвращает сведения о выявленных нарушениях.

Ответ должен содержать:

- перечень нарушений;

- описание каждого нарушения;

- рекомендации по исправлению.

После устранения ошибок повторная отправка запроса допускается без изменения бизнес-состояния.

**5.4 Business Rule Response**

Если операция запрещена Business Rules Catalogue, платформа сообщает причину отказа.

Ответ содержит:

- нарушенное бизнес-правило;

- описание ограничения;

- возможные дальнейшие действия.

Бизнес-правила имеют приоритет над пользовательскими ожиданиями.

**5.5 Permission Response**

Если операция запрещена Permission Model, платформа сообщает об отсутствии необходимых полномочий.

Ответ не раскрывает информацию, доступ к которой запрещён.

**5.6 System Failure Response**

При возникновении технической ошибки платформа:

- сохраняет целостность бизнес-состояния;

- регистрирует ошибку;

- формирует диагностический идентификатор;

- возвращает пользователю сообщение о невозможности завершения операции.

Технические детали реализации не раскрываются.

**5.7 Partial Information**

Если часть вспомогательных сервисов временно недоступна, но Business Automation успешно завершена, ответ считается успешным.

Платформа дополнительно сообщает о недоступности соответствующих инфраструктурных функций.

Например:

- уведомление будет отправлено позже;

- документ находится в очереди генерации;

- синхронизация с внешним сервисом ожидает повторной попытки.

**Архитектурный принцип**

Ответ платформы описывает результат обработки бизнес-запроса, а не внутреннее устройство системы.

Пользователь получает информацию, необходимую для продолжения сотрудничества, независимо от способа взаимодействия с платформой.

**7. Service Interaction Rules**

Настоящий раздел определяет обязательные правила взаимодействия между сервисами платформы.

Цель настоящих правил — обеспечить независимость компонентов, прозрачность взаимодействия и возможность масштабирования платформы.

**7.1 Независимость сервисов**

Каждый сервис обладает собственной областью ответственности.

Сервис не должен изменять внутреннее состояние другого сервиса напрямую.

Все изменения выполняются посредством Service Contracts.

**7.2 Запрет общего состояния**

Сервисы не используют совместно изменяемые данные.

Передача информации осуществляется исключительно посредством:

- Command;

- Query;

- Event.

Использование скрытых механизмов обмена запрещается.

**7.3 Явные зависимости**

Каждая зависимость между сервисами должна быть явно определена.

Не допускаются циклические зависимости.

Каждый сервис должен иметь минимально необходимое количество зависимостей.

**7.4 Взаимодействие через контракты**

Сервис взаимодействует не с реализацией другого сервиса, а с его опубликованным контрактом.

Изменение внутренней реализации сервиса не должно влиять на остальных участников системы при сохранении контракта.

**7.5 Асинхронное взаимодействие**

Если операция не требует немедленного результата, взаимодействие выполняется посредством Event.

Асинхронное взаимодействие предпочтительно для:

- уведомлений;

- генерации документов;

- аналитики;

- интеграций;

- фоновых вычислений.

**7.6 Синхронное взаимодействие**

Синхронное взаимодействие допускается только тогда, когда результат необходим для продолжения текущего бизнес-процесса.

Например:

- проверка существования объекта;

- получение текущего состояния;

- выполнение Business Command.

**7.7 Граница ответственности**

Каждый сервис отвечает только за собственные Business Objects.

Получение информации о связанных объектах осуществляется посредством Query соответствующего сервиса.

Прямое изменение чужих объектов запрещается.

**7.8 Обработка ошибок**

Ошибка одного сервиса не должна приводить к повреждению бизнес-состояния других сервисов.

При невозможности завершения операции сервис обязан:

- вернуть диагностическую информацию;

- зарегистрировать событие ошибки;

- сохранить согласованность собственного состояния.

**7.9 Эволюция контрактов**

Контракты сервисов должны развиваться с сохранением совместимости.

Изменение существующего поведения допускается только при выпуске новой версии контракта.

Удаление используемых интерфейсов допускается только после завершения периода совместимости.

**Архитектурный принцип**

Любой сервис может быть заменён новой реализацией без изменения остальных компонентов платформы при условии сохранения опубликованного Service Contract.

**8. Versioning**

Все Service Contracts платформы подлежат обязательному версионированию.

Версия контракта отражает изменения логики взаимодействия, а не изменения программной реализации.

**8.1 Независимость версий**

Каждый Service Contract имеет собственную версию.

Версионирование одного сервиса не требует изменения версий остальных сервисов.

**8.2 Совместимость**

При изменении контракта предпочтение отдаётся обратной совместимости.

Если обратная совместимость невозможна, публикуется новая версия контракта.

Предыдущая версия сохраняется до завершения установленного периода поддержки.

**8.3 Принципы изменения**

Допускается:

- расширение существующих возможностей;

- добавление новых команд;

- добавление новых запросов;

- добавление новых событий.

Не допускается изменение поведения существующих операций без изменения версии контракта.

**8.4 Документирование изменений**

Каждое изменение Service Contract сопровождается:

- описанием изменений;

- причиной изменения;

- перечнем затронутых сервисов;

- рекомендациями по переходу на новую версию.

История изменений сохраняется на протяжении всего жизненного цикла платформы.

**9. Service Design Principles**

Настоящие принципы являются обязательными для проектирования, разработки и сопровождения всех сервисных интерфейсов платформы.

**SDP-001 Business Driven**

Сервисные интерфейсы строятся вокруг бизнес-процессов платформы.

Структура сервисов определяется предметной областью, а не технологией реализации.

**SDP-002 Single Responsibility**

Каждый сервис отвечает только за одну область ответственности.

Объединение нескольких независимых бизнес-процессов в одном сервисе не допускается.

**SDP-003 Contract First**

Сначала определяется Service Contract.

После утверждения контракта допускается разработка программной реализации.

Изменение реализации не должно изменять контракт сервиса.

**SDP-004 Command–Query Separation**

Команды изменяют бизнес-состояние.

Запросы только читают информацию.

Объединение этих операций в одном сервисном вызове запрещается.

**SDP-005 Event Driven**

Все изменения бизнес-состояния сопровождаются регистрацией Business Event.

Автоматические процессы запускаются исключительно зарегистрированными событиями.

**SDP-006 Explicit Dependencies**

Все зависимости между сервисами должны быть явными.

Использование скрытых зависимостей, общих внутренних состояний и неформализованных каналов взаимодействия запрещается.

**SDP-007 Stateless Processing**

Сервис не хранит состояние пользовательского взаимодействия между вызовами.

Все необходимые данные должны быть получены из Persistent Objects либо переданы в запросе.

**SDP-008 Fail Safely**

При возникновении ошибки сервис обязан сохранить целостность бизнес-модели.

Технический сбой не должен приводить к частичному изменению бизнес-состояния.

**SDP-009 Observable Behaviour**

Работа каждого сервиса должна быть наблюдаемой.

Любая операция должна иметь возможность быть прослеженной от входящего Command до зарегистрированного Business Event и результата обработки.

**SDP-010 Technology Independence**

Service Contract не зависит от:

- языка программирования;

- транспортного протокола;

- способа сериализации данных;

- способа развертывания.

Технология реализации не должна изменять архитектуру взаимодействия сервисов.

**10. Заключительные положения**

Service Interface Specification определяет единый стандарт взаимодействия компонентов цифровой платформы Simple Solutions Practice.

Все новые сервисы, независимо от их назначения, обязаны соответствовать требованиям настоящего документа.

Любые изменения сервисной архитектуры допускаются только при сохранении совместимости с бизнес-моделью платформы и связанными архитектурными документами.
