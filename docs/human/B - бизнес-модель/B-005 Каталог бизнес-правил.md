**B-005 Каталог бизнес-правил**

**Версия:** 1.0

**Статус:** Approved

**Раздел:** B — Business

- B-001 Бизнес-модель

**1. Назначение**

Business Rules Catalogue определяет обязательные правила принятия решений в цифровой платформе Simple Solutions Practice.

Бизнес-правила описывают условия, при которых выполнение определённого действия считается допустимым или недопустимым.

Настоящий документ является единым источником бизнес-логики платформы.

**2. Основные принципы**

**2.1 Правила определяет бизнес**

Все правила формируются исходя из методологии Simple Solutions Practice.

Техническая реализация обязана следовать установленным бизнес-правилам.

**2.2 Правило первично**

При возникновении противоречия между технической возможностью и бизнес-правилом применяется бизнес-правило.

**2.3 Правила независимы от интерфейса**

Изменение пользовательского интерфейса не изменяет действие бизнес-правил.

**2.4 Правила проверяются до выполнения действия**

Ни одно Business Event не может быть зарегистрировано без проверки соответствующих бизнес-правил.

**4. Правила жизненного цикла Inquiry**

**BR-001 Inquiry создаётся только один раз**

Объект: Inquiry

Правило:

Каждое первичное обращение создаёт новый Inquiry.

Повторное использование существующего Inquiry запрещается.

**BR-002 Inquiry должен завершиться решением**

Каждый Inquiry обязан закончиться одним из результатов:

- переход к Proposal;

- отказ от сотрудничества.

Промежуточное состояние не может сохраняться бесконечно.

**BR-003. Назначение Discovery Meeting**

После перехода Inquiry в состояние Accepted консультант может назначить Discovery Meeting.

Назначение Discovery Meeting для Inquiry в состоянии New, Closed или Rejected запрещается.

**BR-004. Создание Agreement**

Agreement может быть создан только после принятия Partner коммерческого предложения (Proposal).

Создание Agreement для Inquiry, не завершившего этап согласования Proposal, запрещается.

**BR-005. Регистрация Payment**

Payment может быть зарегистрирован только для подписанного Agreement.

Получение информации об оплате не изменяет состояние Inquiry напрямую.

**BR-006. Создание Notification**

Каждое изменение состояния Inquiry может инициировать создание одного или нескольких Notification.

Notification создаются системой автоматически на основании соответствующих Business Events.

**BR-007. Создание Workspace**

Workspace создаётся системой только после подтверждения первой оплаты по подписанному Agreement.

Ручное создание Workspace не допускается.

**5. Правила Proposal**

**BR-008 Proposal создаётся только после Discovery Meeting**

Создание Proposal допускается исключительно после завершения Discovery Meeting.

**BR-009 Proposal имеет ограниченный срок действия**

Срок действия Proposal устанавливается в документе. По умолчанию — 10 рабочих дней

После истечения срока Proposal не может быть принято.

Допускается создание новой версии.

**BR-010 Proposal не изменяется после отправки**

После отправки Proposal становится неизменяемым.

Изменение условий осуществляется созданием новой редакции.

**6. Правила Agreement**

**BR-011 Agreement создаётся только из принятого Proposal**

Создание Agreement напрямую запрещается.

**BR-012 Agreement не изменяется после подтверждения**

После подтверждения Agreement считается окончательным.

Любое изменение требует нового Proposal.

**7. Правила Project**

**BR-013 Project создаётся автоматически**

Project возникает исключительно после подтверждения Agreement.

Ручное создание запрещается.

**BR-014 Project имеет только одного ответственного консультанта**

В версии 1.0 каждый Project закрепляется за одним Consultant.

Передача проекта другому Consultant оформляется отдельным административным действием.

**BR-015 Project нельзя завершить при наличии незавершённых Stage**

Все Project Stage должны иметь состояние Completed или Cancelled.

Только после этого допускается завершение Project.

**8. Правила Project Stage**

**BR-016 Каждый Project Stage имеет измеримый результат**

Каждый этап проекта должен завершаться конкретным Deliverable.

Этап не может считаться завершённым только по факту выполнения работ.

**BR-017 Одновременно активен только один Project Stage**

В версии 1.0 платформы одновременно может выполняться только один этап проекта.

Следующий этап открывается автоматически после завершения предыдущего.

**BR-018 Приостановка Stage не завершает Project**

Если выполнение этапа временно невозможно, Stage переводится в состояние Waiting.

Project сохраняет состояние Active.

**9. Правила Deliverable**

**BR-019 Deliverable является обязательным результатом каждого оплаченного проекта**

Каждый оплаченный проект должен завершиться передачей партнёру согласованного результата.

Форма результата определяется выбранным форматом сотрудничества.

**BR-020 Deliverable проходит внутреннюю проверку**

Перед передачей партнёру Deliverable должен пройти внутреннюю экспертную проверку.

Публикация Deliverable без внутренней проверки запрещается.

**BR-021 Принятый Deliverable не изменяется**

После подтверждения получения Deliverable изменение его содержания не допускается.

При необходимости создаётся новая версия Deliverable.

**10. Правила финансовых операций**

**BR-022 Счёт формируется автоматически**

Invoice создаётся системой после подтверждения Agreement.

Ручное создание счёта допускается только в исключительных случаях, предусмотренных внутренними процедурами SSP.

**BR-023 Работы начинаются после подтверждения оплаты**

Project Stage может перейти в состояние Active только после регистрации полной оплаты либо после принятия консультантом отдельного решения о начале работ.

**BR-024 Каждый платёж относится к одному Project**

Платёж не может одновременно относиться к нескольким проектам.

Для каждого Project ведётся самостоятельная финансовая история.

**BR-025 Возврат оформляется отдельной операцией**

Возврат денежных средств не отменяет факт существования первоначального платежа.

Возврат фиксируется самостоятельной финансовой операцией с сохранением полной истории.

**11. Правила Workspace**

**BR-026 Workspace создаётся автоматически**

Workspace создаётся системой одновременно с созданием Project.

Ручное создание Workspace запрещается.

**BR-027 Workspace отображает актуальные данные**

Workspace не хранит собственную бизнес-информацию.

Все отображаемые сведения формируются из связанных бизнес-сущностей.

**BR-028 После завершения Project Workspace становится доступен только для просмотра**

Редактирование информации завершённого проекта запрещается.

Доступ к материалам проекта сохраняется в режиме Read Only.

**12. Правила документов**

**BR-029 Каждый официальный документ имеет версию**

Все документы платформы имеют уникальный номер и номер версии.

Изменение опубликованной версии документа запрещается.

**BR-030 Документы формируются на основании бизнес-данных**

Документ не является источником информации.

Источником являются соответствующие бизнес-сущности платформы.

При расхождении данных приоритет имеют бизнес-объекты.

**BR-031 История документов сохраняется полностью**

Создание новой редакции документа не удаляет предыдущие версии.

Все редакции остаются доступными для просмотра и аудита.

**13. Общие правила принятия решений**

Настоящие правила являются обязательными для всех бизнес-процессов платформы.

**BR-032 Приоритет бизнес-правил**

При возникновении противоречия между:

- пользовательским действием;

- полномочиями;

- автоматизацией;

- технической реализацией,

приоритет всегда имеет настоящее Business Rule.

**BR-033 Проверка выполняется до создания события**

Ни одно Business Event не может быть зарегистрировано без предварительной проверки применимых бизнес-правил.

При нарушении хотя бы одного правила событие не создаётся.

**BR-034 Приоритет автоматизации** 

Если действие может быть выполнено автоматически, ручное выполнение запрещается (кроме случаев, предусмотренных BR-032).

**BR-035 Каждое правило должно быть проверяемым**

Каждое бизнес-правило должно допускать однозначную автоматическую или экспертную проверку.

Правила, допускающие неоднозначную трактовку, не используются в цифровой платформе.

**BR-036 Правила не зависят от интерфейса**

Изменение пользовательского интерфейса, способа взаимодействия или внешней интеграции не влияет на действие бизнес-правил.

Правила применяются одинаково независимо от того, инициировано действие через:

- веб-интерфейс;

- Telegram;

- MAX;

- API;

- внутреннюю административную панель.

**BR-037 Правила применяются последовательно**

При выполнении одного действия система проверяет все применимые правила.

Нарушение любого обязательного правила прекращает дальнейшую обработку действия.

**14. Исключения**

**BR-038 Исключения принимаются только консультантом**

Если ситуация не может быть корректно обработана существующими бизнес-правилами, решение принимает Consultant.

Такое решение фиксируется в журнале проекта с указанием причины.

**BR-039 Исключение не изменяет правило**

Разовое исключение не изменяет действующие бизнес-правила.

Изменение правил допускается только путём актуализации настоящего документа.

**15. Архитектурные принципы**

**Простые решения имеют приоритет**

При наличии нескольких допустимых вариантов выбирается наиболее простое решение, обеспечивающее достижение результата.

Сложность процесса не рассматривается как самостоятельная ценность.

**Экспертное решение выше автоматизации**

Автоматизация реализует утверждённые правила.

Оценка ситуации, выбор стратегии и принятие профессиональных решений остаются ответственностью консультанта.

**Результат важнее процесса**

Платформа ориентирована на достижение согласованного результата.

Все процессы, документы и автоматизация существуют исключительно для поддержки этого результата.

**История сотрудничества является частью ценности**

Все ключевые решения, события и результаты проекта сохраняются.

История не удаляется и не переписывается.

Она является частью профессиональной ответственности SSP перед партнёром.

**Бизнес развивается без переписывания платформы**

Новые услуги, форматы сотрудничества и способы взаимодействия должны внедряться через расширение существующих бизнес-правил, не нарушая уже утверждённую архитектуру.

**16. Заключительные положения**

Business Rules Catalogue является нормативным документом цифровой платформы Simple Solutions Practice.

Все компоненты платформы — бизнес-модели, программный код, пользовательские интерфейсы, интеграции и автоматизация — обязаны соответствовать настоящему документу.

Изменение настоящего документа допускается только после анализа влияния на связанные архитектурные документы и утверждения владельцем платформы.
