**1. Назначение**

Business Event Catalogue определяет полный перечень бизнес-событий цифровой платформы Simple Solutions Practice.

Каждое событие представляет собой факт изменения состояния бизнес-процесса.

Business Events являются единственным допустимым механизмом запуска автоматизации платформы.

**2. Основные принципы**

**2.1 Событие фиксирует факт**

Событие описывает уже произошедшее изменение.

Событие не является командой.

Правильно:

- Payment Received

- Proposal Accepted

- Project Completed

Неправильно:

- Receive Payment

- Accept Proposal

- Complete Project

**2.2 Событие неизменно**

После регистрации Event не может быть изменён или удалён.

Исправление ошибок выполняется созданием нового события.

**2.3 Одно событие — один факт**

Каждый Event фиксирует только одно завершённое действие.

Объединение нескольких действий в одном событии запрещается.

**2.4 События являются частью истории проекта**

Все зарегистрированные события сохраняются в журнале проекта и доступны для последующего анализа.

**3. Классификация событий**

Платформа использует три категории событий.

**Business Events**

Изменяют состояние бизнеса.

Являются основой автоматизации.

**System Events**

Возникают в результате работы платформы.

Используются для внутренних процессов.

Не изменяют бизнес-логику.

**External Events**

Поступают от внешних сервисов.

Используются для интеграций.

**4. Правила идентификации**

Каждое событие получает уникальный идентификатор.

Формат:

EV-001

EV-002

EV-003

...

Номер события никогда не изменяется.

Даже после удаления функции событие остаётся зарезервированным.

**6. Жизненный цикл сотрудничества**

Business Events сгруппированы по этапам жизненного цикла партнёра.

1.  Привлечение партнёра

2.  Согласование сотрудничества

3.  Реализация проекта

4.  Финансовые операции

5.  Завершение сотрудничества

Именно в этой последовательности события рассматриваются далее.

**9. Общие правила обработки событий**

Настоящие правила являются обязательными для всех событий платформы.

**9.1 Каждое событие имеет источник**

Любое событие должно иметь определённого инициатора.

Допустимыми инициаторами являются:

- Partner;

- Consultant;

- System;

- External Service.

Событие без инициатора считается недействительным.

**9.2 Каждое событие относится к одному объекту**

Business Event всегда создаётся относительно конкретной бизнес-сущности.

Одно событие не может одновременно изменять несколько независимых объектов.

Если требуется изменение нескольких объектов, создаётся цепочка взаимосвязанных событий.

**9.3 События являются атомарными**

Каждый Event фиксирует один завершённый факт.

Событие не может быть выполнено частично.

При невозможности полного выполнения событие считается не произошедшим.

**9.4 События необратимы**

После регистрации Business Event не изменяется и не удаляется.

Исправление ошибок осуществляется созданием нового события.

История событий остаётся неизменной.

**9.5 Последовательность событий**

Business Events всегда возникают в соответствии с Business State Model.

Создание события, нарушающего жизненный цикл объекта, запрещается.

**10. Автоматическая обработка событий**

Business Events являются единственной точкой запуска автоматических процессов платформы.

После регистрации события система может:

- изменить состояние объекта;

- создать связанные объекты;

- сформировать документы;

- создать уведомления;

- инициировать интеграции;

- выполнить расчёты;

- обновить пользовательские интерфейсы.

Автоматические действия выполняются только после успешной регистрации события.

**11. Журнал событий**

Все события сохраняются в едином журнале платформы.

Для каждого события фиксируются:

- уникальный идентификатор;

- дата и время;

- инициатор;

- объект;

- тип события;

- результат обработки;

- связанные объекты;

- комментарий (при наличии).

Удаление записей журнала запрещается.

**12. Приоритет обработки**

Если несколько событий относятся к одному объекту одновременно, система обрабатывает их последовательно.

Порядок определяется:

1.  временем регистрации;

2.  бизнес-приоритетом;

3.  внутренними правилами платформы.

Одновременное изменение состояния одного объекта несколькими событиями не допускается.

**13. Ошибки обработки**

Если событие не может быть успешно обработано, система обязана:

- отменить изменение состояния;

- сохранить информацию об ошибке;

- уведомить ответственного консультанта (при необходимости);

- сохранить целостность бизнес-данных.

Частичное выполнение автоматических действий запрещается.

**14. Архитектурные принципы**

**Событие важнее действия**

Платформа хранит не команды пользователей, а факты произошедших изменений.

**Один факт — одно событие**

Каждый Business Event отражает одно завершённое бизнес-действие.

**Единый словарь событий**

Каждое событие имеет единственное каноническое название.

Использование различных наименований одного и того же события запрещается.

**Автоматизация следует за событиями**

Никакие автоматические процессы не запускаются напрямую.

Основанием автоматизации всегда является зарегистрированный Business Event.

**События первичны по отношению к интерфейсам**

Пользовательские интерфейсы являются лишь способом создания событий.

Изменение пользовательского интерфейса не должно изменять бизнес-логику платформы.

**Прослеживаемость**

Любое изменение в системе должно быть объяснимо последовательностью зарегистрированных событий.

Если изменение невозможно связать с конкретным Event, оно считается нарушением архитектуры платформы.

**15. Заключительные положения**

Business Event Catalogue определяет единый язык событий цифровой платформы Simple Solutions Practice.

Все программные компоненты платформы, пользовательские интерфейсы, API, интеграции и автоматические процессы обязаны использовать настоящий каталог событий.

Изменение настоящего документа допускается только после актуализации связанных бизнес-моделей.
