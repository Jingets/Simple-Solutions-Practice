**E-009 Метамодель платформы**

**Версия:** 1.0

**Статус:** Approved

**Раздел:** E — Engineering Architecture

**1. Scope**

Настоящий документ определяет метамодель платформы Simple Solutions Practice.

Метамодель описывает фундаментальные типы архитектурных объектов платформы.

Любая сущность платформы должна принадлежать одному из типов, определённых настоящим документом.

**2. Metamodel Principles**

Метамодель определяет архитектурную классификацию объектов платформы.

Она не описывает их внутреннюю реализацию.

**MM-001**

Каждый объект платформы имеет один основной архитектурный тип.

**MM-002**

Архитектурный тип определяет назначение объекта.

**MM-003**

Объект не может одновременно принадлежать нескольким архитектурным типам.

**MM-004**

Изменение архитектурного типа существующего объекта запрещается.

**MM-005**

Все новые объекты платформы должны быть классифицированы до начала реализации.

**Архитектурное правило**

Сначала определяется место объекта в метамодели.

Затем проектируется его реализация.

**3. Platform Object**

Platform Object является базовым понятием метамодели.

Любая архитектурная сущность платформы является Platform Object.

Platform Object обладает:

- Identity;

- Lifecycle;

- Metadata;

- Ownership;

- Audit History.

Конкретный набор свойств определяется специализированным типом объекта.

**Архитектурное правило**

Все архитектурные сущности платформы являются Platform Objects.

**4. Object Categories**

Метамодель определяет следующие категории Platform Objects.

**Structural Objects**

Описывают структуру цифровой организации.

Примеры:

- Workspace;

- Organization;

- Team;

- Worker;

- Role.

**Behavioral Objects**

Описывают поведение платформы.

Примеры:

- Workflow;

- Task;

- Policy;

- Rule;

- Decision.

**Informational Objects**

Представляют информацию и результаты работы.

Примеры:

- Artifact;

- Knowledge;

- Template;

- Report;

- Document.

**Runtime Objects**

Существуют только во время выполнения платформы.

Примеры:

- Session;

- Context;

- Queue Item;

- Notification;

- Job.

**Infrastructure Objects**

Обеспечивают функционирование платформы.

Примеры:

- Service;

- Module;

- Extension;

- Tool;

- Connector.

**Архитектурное правило**

Каждый Platform Object принадлежит одной архитектурной категории.

**5. Object Identity**

Каждый Platform Object обладает собственной идентичностью.

**ID-001**

Identity создаётся одновременно с созданием объекта.

**ID-002**

Identity является неизменяемой.

**ID-003**

Удаление объекта не приводит к повторному использованию его Identity.

**ID-004**

Identity используется всеми сервисами платформы для ссылки на объект.

**ID-005**

Все ссылки между объектами осуществляются только посредством Identity.

**Архитектурное правило**

Identity является единственным способом идентификации Platform Object.

**6. Object Lifecycle**

Каждый Platform Object проходит жизненный цикл.

Конкретные состояния определяются специализированным типом объекта.

**LC-001**

Жизненный цикл начинается созданием объекта.

**LC-002**

Каждый переход состояния фиксируется Platform Kernel.

**LC-003**

Переход между состояниями выполняется только посредством разрешённых операций.

**LC-004**

История жизненного цикла является неизменяемой.

**LC-005**

После завершения жизненного цикла объект сохраняется в истории платформы в соответствии с политиками хранения данных.

**Архитектурное правило**

Объект развивается посредством смены состояний.

Его история не изменяется.

**7. Object Relationships**

Platform Objects могут образовывать связи между собой.

**RL-001**

Связи являются самостоятельными элементами модели платформы.

**RL-002**

Связь всегда соединяет существующие Platform Objects.

**RL-003**

Удаление связи не изменяет связанные объекты.

**RL-004**

Каждая связь имеет собственный тип.

**RL-005**

Все изменения связей журналируются.

**Архитектурное правило**

Связь описывает отношение между объектами.

Она не изменяет их внутреннее состояние.

**8. Object Ownership**

Каждый Platform Object имеет владельца.

**OW-001**

Owner определяется при создании объекта.

**OW-002**

Owner отвечает за управление жизненным циклом объекта.

**OW-003**

Owner может изменяться только посредством операций Platform Kernel.

**OW-004**

Исполнитель операций над объектом может отличаться от Owner.

**OW-005**

История изменения Owner сохраняется в Audit Service.

**Архитектурное правило**

Ответственность принадлежит Owner.

Действия выполняются Worker.

**9. Object Metadata**

Каждый Platform Object содержит системные метаданные.

**MD-001**

Минимальный набор метаданных включает:

- Object ID;

- Object Type;

- Version;

- Created At;

- Updated At;

- Owner;

- Status.

**MD-002**

Метаданные управляются Platform Kernel.

**MD-003**

Пользовательские данные объекта не смешиваются с системными метаданными.

**MD-004**

Изменение системных метаданных допускается только через Platform Kernel.

**MD-005**

Метаданные доступны всем инфраструктурным сервисам платформы.

**Архитектурное правило**

Метаданные описывают объект.

Они не являются его бизнес-содержимым.

**10. Object Operations**

Platform Object поддерживает ограниченный набор архитектурных операций.

Конкретная реализация операций определяется специализированным типом объекта.

**OP-001**

Создание (Create)

Создание нового Platform Object.

**OP-002**

Чтение (Read)

Получение состояния объекта.

**OP-003**

Обновление (Update)

Изменение допустимого состояния объекта.

**OP-004**

Архивирование (Archive)

Перевод объекта в архивное состояние без удаления истории.

**OP-005**

Удаление (Delete)

Физическое удаление допускается только для объектов, политика хранения которых разрешает такую операцию.

**Архитектурное правило**

Операции определяют допустимое взаимодействие с объектом.

Они не определяют его бизнес-поведение.

**11. Object Events**

Любое значимое изменение Platform Object оформляется как событие.

**OE-001**

Создание объекта публикует событие ObjectCreated.

**OE-002**

Изменение состояния публикует событие ObjectChanged.

**OE-003**

Архивирование публикует событие ObjectArchived.

**OE-004**

Удаление публикует событие ObjectDeleted.

**OE-005**

Специализированные типы объектов могут публиковать дополнительные события.

**Архитектурное правило**

Изменения объектов наблюдаются посредством событий.

**12. Object Composition**

Platform Objects могут образовывать составные структуры.

**OC-001**

Составной объект может включать другие Platform Objects.

**OC-002**

Вложенные объекты сохраняют собственную идентичность и жизненный цикл.

**OC-003**

Родительский объект определяет контекст использования вложенных объектов.

**OC-004**

Удаление составного объекта не изменяет правила хранения вложенных объектов.

**OC-005**

Состав объектов определяется архитектурной моделью соответствующего типа.

**Архитектурное правило**

Вложенность организует объекты.

Она не отменяет их самостоятельность.

**13. Object References**

Связи между объектами реализуются посредством ссылок.

**RF-001**

Объект не содержит копии другого объекта.

**RF-002**

Взаимодействие осуществляется по ссылке на Identity.

**RF-003**

Повторное использование объектов является предпочтительным по отношению к их копированию.

**RF-004**

Разрешение ссылок выполняется Platform Kernel.

**RF-005**

Нарушенные ссылки рассматриваются как ошибка целостности модели.

**Архитектурное правило**

Платформа управляет сетью взаимосвязанных объектов, а не их копиями.

**14. Object Graph**

Platform Objects образуют единый граф платформы.

Граф является логической моделью взаимосвязей между объектами.

Он не зависит от способа физического хранения данных.

**OG-001**

Каждый Platform Object является вершиной графа.

**OG-002**

Каждая связь между объектами является ориентированным отношением.

**OG-003**

Связи имеют собственный тип и семантику.

**OG-004**

Связи могут использоваться для навигации между объектами.

**OG-005**

Изменение графа осуществляется только посредством Platform Kernel.

**Архитектурное правило**

Платформа управляет графом объектов, а не изолированными сущностями.

**15. Object Integrity**

Целостность графа Platform Objects должна сохраняться на протяжении всего жизненного цикла платформы.

**OI-001**

Platform Object не может ссылаться на несуществующий объект.

**OI-002**

Создание новых связей проверяется Platform Kernel.

**OI-003**

Удаление объекта не должно нарушать целостность графа.

**OI-004**

Нарушение целостности рассматривается как архитектурная ошибка платформы.

**OI-005**

Проверка целостности выполняется автоматически инфраструктурными сервисами платформы.

**Архитектурное правило**

Целостность модели важнее удобства реализации.

**16. Object Evolution**

Развитие платформы осуществляется посредством появления новых типов объектов.

**EV-001**

Новые Platform Objects должны использовать существующую метамодель.

**EV-002**

Добавление нового типа объекта не должно изменять ранее определённые категории.

**EV-003**

Расширение метамодели допускается только при невозможности классификации нового объекта.

**EV-004**

Каждое расширение метамодели должно быть обратно совместимым.

**EV-005**

Метамодель является наиболее стабильной частью архитектуры платформы.

**Архитектурное правило**

Сначала развивается модель.

Потом развивается реализация.

**17. Metamodel Principles**

Метамодель SSP основана на следующих принципах.

1.  Любая архитектурная сущность является Platform Object.

2.  Каждый объект принадлежит одной архитектурной категории.

3.  Каждый объект обладает собственной идентичностью.

4.  Каждый объект имеет самостоятельный жизненный цикл.

5.  Все объекты взаимодействуют посредством связей.

6.  Все изменения выполняются через Platform Kernel.

7.  История объектов является неизменяемой.

8.  Целостность графа платформы имеет абсолютный приоритет.

9.  Расширение платформы начинается с расширения метамодели.

10. Метамодель является единым архитектурным языком платформы.
