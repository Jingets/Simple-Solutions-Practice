# E-017. Модуль SDK

Version: 2.0

Status: Approved

---

# 1. Назначение

SDK (Software Development Kit) является единым стандартом разработки модулей платформы **Simple Solutions Practice (SSP)**.

Любой программный компонент платформы должен разрабатываться исключительно с использованием настоящего SDK.

SDK определяет архитектурные правила взаимодействия модулей, их жизненный цикл, требования к регистрации возможностей и единый интерфейс обмена данными.

---

# 2. Архитектурные принципы

При разработке модулей SSP используются следующие принципы:

* независимость модулей;
* отсутствие прямых зависимостей между модулями;
* взаимодействие только через Platform Kernel;
* событийная модель обмена данными;
* единый формат регистрации возможностей;
* единый жизненный цикл.

---

# 3. Архитектура взаимодействия

```text id="sdk-architecture"
                Platform Kernel
                       │
      ┌────────────────┼────────────────┐
      │                │                │
 Offer Module     Invoice Module    Report Module
      │                │                │
      └────────────────┼────────────────┘
                       │
                Business Events
```

Модули не взаимодействуют друг с другом напрямую.

Все обращения выполняются посредством Platform Kernel.

---

# 4. Жизненный цикл модуля

Каждый модуль проходит одинаковую последовательность состояний.

```text id="sdk-lifecycle"
Install
   ↓
Initialize
   ↓
Register Manifest
   ↓
Register Capabilities
   ↓
Register Event Subscriptions
   ↓
Ready
   ↓
Running
   ↓
Stopping
   ↓
Dispose
```

Переход между состояниями выполняется Platform Kernel.

---

# 5. Module Manifest

Каждый модуль обязан содержать файл Manifest.

Manifest является паспортом модуля и содержит сведения, необходимые Platform Kernel для регистрации компонента.

Manifest определяет:

* идентификатор модуля;
* имя;
* версию;
* описание;
* поддерживаемую версию SDK;
* список возможностей (Capabilities);
* публикуемые события;
* подписки на события;
* параметры конфигурации.

Без зарегистрированного Manifest модуль не может быть запущен.

---

# 6. Capability Contract

Каждая возможность (Capability) оформляется отдельным контрактом.

Capability Contract описывает:

* назначение возможности;
* входные параметры;
* выходные данные;
* используемый контекст;
* необходимые разрешения;
* создаваемые Business Events.

Capability является минимальной исполняемой единицей платформы.

---

# 7. Platform Context

SDK предоставляет каждому модулю единый Context.

Модуль может получать данные только посредством Context API.

Допускается доступ к:

* Project;
* Client;
* Contractor;
* Service;
* Configuration;
* Artifacts.

Прямой доступ к внутренним данным других модулей запрещён.

---

# 8. Business Events

Все изменения состояния платформы оформляются как Business Events.

Модуль может:

* публиковать зарегистрированные события;
* подписываться на зарегистрированные события.

Обработка незарегистрированных событий не допускается.

---

# 9. Artifacts

Все создаваемые документы, отчёты и файлы являются Artifacts.

Работа с артефактами осуществляется исключительно через Artifact API.

Поддерживаются операции:

* создание;
* чтение;
* обновление;
* архивирование.

---

# 10. Configuration

Конфигурация модулей хранится вне программного кода.

Использование жёстко заданных параметров (hardcoded configuration) не допускается.

---

# 11. Logging

Каждый модуль обязан вести журнал выполнения операций.

Все ошибки, предупреждения и ключевые этапы обработки должны регистрироваться средствами SDK.

---

# 12. Audit

Все действия, изменяющие бизнес-данные, должны отражаться в Audit Log платформы.

---

# 13. Health Check

Каждый модуль обязан реализовывать механизм проверки собственного состояния.

Platform Kernel использует Health Check для определения готовности модуля к работе.

---

# 14. Версионирование

Версии SDK и модулей используют семантическое версионирование (Semantic Versioning).

Изменения, нарушающие обратную совместимость, допускаются только при изменении Major-версии.

---

# 15. Требования к тестированию

Каждый модуль должен сопровождаться:

* модульными тестами;
* интеграционными тестами.

Без успешного прохождения тестов модуль не считается готовым к эксплуатации.

---

# 16. Definition of Done

Разработка модуля считается завершённой при выполнении следующих условий:

* зарегистрирован Module Manifest;
* зарегистрированы Capability Contracts;
* зарегистрированы подписки на Business Events;
* реализован Health Check;
* реализовано логирование;
* реализован аудит;
* успешно выполнены тесты;
* подготовлена документация.

---

# 17. Ограничения

При разработке модулей запрещается:

* прямое обращение к другим модулям;
* доступ к внутренним данным других модулей;
* использование неописанных Capability;
* использование незарегистрированных Business Events;
* хранение конфигурации в программном коде.
