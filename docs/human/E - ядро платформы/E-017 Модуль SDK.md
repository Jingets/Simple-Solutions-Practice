# E-017. Module SDK

## 1. Назначение

Module SDK определяет единый контракт разработки модулей платформы Simple Solutions Practice.

Каждый функциональный модуль Platform Kernel реализуется в соответствии с настоящей спецификацией.

SDK обеспечивает:

- единый жизненный цикл модулей;
- единый механизм регистрации;
- единые точки расширения;
- совместимость модулей;
- возможность независимой разработки;
- возможность автоматической проверки соответствия модулей требованиям платформы.

Настоящий документ является обязательным для всех модулей Pilot MVP.

---

# 2. Назначение SDK

SDK предоставляет разработчику стандартный набор интерфейсов, контрактов и правил, необходимых для интеграции нового модуля в Platform Kernel.

SDK не содержит бизнес-логики.

SDK определяет только правила взаимодействия.

---

# 3. Обязательная структура модуля

Каждый модуль должен иметь следующую структуру:

```text
module/

    module.py

    manifest.yaml

    api.py

    capabilities.py

    events.py

    models.py

    repository.py

    services.py

    workflows.py

    schemas.py

    artifacts.py

    tests/
```

Допускаются дополнительные файлы, не нарушающие контракт SDK.

---

# 4. Manifest

Каждый модуль обязан содержать:

```text
manifest.yaml
```

Минимальная структура:

```yaml
id:
name:
version:
description:

dependencies:

capabilities:

events:

artifacts:

api:

permissions:
```

Manifest является единственным источником информации о составе модуля.

---

# 5. Регистрация

Каждый модуль обязан регистрироваться в Module Registry.

Во время регистрации модуль публикует:

- Manifest;
- Capability;
- API;
- Events;
- Workflows;
- Artifacts.

Регистрация выполняется автоматически при запуске Platform Kernel.

---

# 6. Capability

Каждая публичная возможность модуля оформляется как Capability.

Capability должна:

- иметь уникальный идентификатор;
- иметь описание;
- иметь входной DTO;
- иметь выходной DTO;
- быть доступной через Platform Kernel.

Пример:

```text
create_project

publish_offer

complete_checkup
```

---

# 7. API

Все публичные endpoints должны быть объявлены в `api.py`.

SDK запрещает регистрацию API вне модуля.

Каждый endpoint обязан:

- использовать DTO;
- иметь OpenAPI-описание;
- использовать единый Error Contract;
- проходить авторизацию.

---

# 8. DTO

Все входные и выходные модели должны быть описаны в `schemas.py`.

Используются Pydantic-модели.

ORM-модели не должны использоваться в качестве DTO.

---

# 9. Repository

Repository отвечает исключительно за доступ к данным.

Repository запрещено:

- изменять бизнес-состояние;
- публиковать события;
- генерировать документы;
- выполнять Workflow.

---

# 10. Services

Services реализуют бизнес-логику модуля.

Services могут:

- использовать Repository;
- использовать Capability других модулей;
- публиковать Business Events;
- вызывать Artifact Manager.

---

# 11. Business Events

Каждый модуль обязан объявить собственные события в `events.py`.

Все события должны быть зарегистрированы в Event Dispatcher.

Каждое событие должно иметь:

- уникальный тип;
- описание;
- структуру payload;
- версию.

---

# 12. Workflows

Сложные последовательности действий оформляются в `workflows.py`.

Workflow может:

- вызывать Capability;
- публиковать события;
- инициировать генерацию Artifact.

Workflow не должен содержать HTTP-логику.

---

# 13. Artifacts

Если модуль генерирует документы, они описываются в `artifacts.py`.

Каждый Artifact должен содержать:

- тип;
- YAML-описание;
- шаблон;
- источник данных.

---

# 14. Зависимости

Модуль может зависеть только от:

- Platform Kernel;
- Capability других модулей;
- публичных SDK-контрактов.

Запрещены зависимости от внутренних классов других модулей.

---

# 15. Жизненный цикл модуля

```text
Load
    ↓
Manifest Validation
    ↓
Dependency Check
    ↓
Registration
    ↓
Capability Registration
    ↓
API Registration
    ↓
Event Registration
    ↓
Workflow Registration
    ↓
Ready
```

При любой ошибке регистрация модуля отменяется.

---

# 16. Проверка совместимости

Platform Kernel при запуске обязан проверить:

- уникальность Module ID;
- корректность Manifest;
- существование зависимостей;
- уникальность Capability;
- уникальность Events;
- корректность API;
- корректность Artifact.

При обнаружении ошибки запуск платформы прекращается.

---

# 17. Обязательные тесты

Каждый модуль обязан содержать:

- unit tests;
- integration tests.

Минимально проверяются:

- регистрация;
- API;
- Capability;
- Repository;
- Workflow;
- события.

---

# 18. Ограничения

SDK запрещает:

- прямой доступ к Repository другого модуля;
- импорт внутренних моделей другого модуля;
- изменение состояния без Business Event;
- регистрацию API вне модуля;
- изменение Manifest во время выполнения.

---

# 19. Совместимость с AI

Каждый модуль должен быть полностью описан таким образом, чтобы AI мог:

- определить состав модуля;
- определить зависимости;
- определить публичные Capability;
- определить API;
- определить события;
- определить Workflow;
- определить генерируемые документы;
- автоматически построить каркас реализации.
