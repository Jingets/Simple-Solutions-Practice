# E-006. Архитектура API

## 1. Назначение

Документ определяет единую архитектуру REST API платформы Simple Solutions Practice для Pilot MVP.

Все внешние взаимодействия между пользовательскими интерфейсами и Platform Kernel выполняются через REST API.

Настоящий документ определяет:

- структуру API;
- правила проектирования endpoints;
- формат запросов и ответов;
- обработку ошибок;
- правила версионирования;
- требования к безопасности;
- правила публикации OpenAPI.

# 3. Архитектурные принципы

REST API является единственной публичной точкой взаимодействия с платформой.

API должно быть:

- stateless;
- versioned;
- idempotent там, где это требуется;
- документировано через OpenAPI;
- независимо от UI;
- независимо от внутренней структуры модулей.

Platform Kernel публикует только публичные контракты.

Repository, ORM и внутренние модели никогда не раскрываются наружу.

---

# 4. Базовый URL

```
/api/v1
```

Примеры:

```
GET    /api/v1/projects
POST   /api/v1/projects
GET    /api/v1/projects/{id}
PATCH  /api/v1/projects/{id}
DELETE /api/v1/projects/{id}
```

Изменение версии API выполняется только изменением префикса.

---

# 5. Формат URL

Используется только:

- существительные;
- множественное число;
- snake_case при необходимости.

Правильно:

```
/projects
/customers
/checkups
/workspaces
/business-events
```

Неправильно:

```
/createProject
/getCustomer
/doCheckup
```

---

# 6. HTTP методы

Используются:

| Метод | Назначение |
|--------|------------|
| GET | чтение |
| POST | создание |
| PUT | полная замена |
| PATCH | частичное изменение |
| DELETE | удаление (если допустимо бизнес-правилами) |

Если операция является действием, изменяющим состояние по бизнес-событию, допускается отдельный endpoint действия.

Например:

```
POST /projects/{id}/accept-offer
POST /projects/{id}/resume
POST /projects/{id}/submit-results
```

Такие операции обязаны публиковать Business Event.

---

# 7. Формат успешного ответа

Все успешные ответы имеют единую структуру.

```json
{
  "success": true,
  "data": {},
  "meta": {}
}
```

Поле `meta` используется для:

- пагинации;
- служебной информации;
- диагностических данных.

Если служебных данных нет, `meta` возвращается пустым объектом.

---

# 8. Формат ошибки

Все ошибки используют единый контракт.

```json
{
  "success": false,
  "error": {
    "code": "PROJECT_INVALID_TRANSITION",
    "message": "Transition is not allowed",
    "details": {}
  }
}
```

### code

Машиночитаемый код.

Используется:

- логикой клиента;
- тестами;
- интеграциями.

### message

Краткое описание ошибки.

### details

Дополнительные сведения.

Допускается пустой объект.

---

# 9. HTTP-коды

Используются только стандартные коды.

| Код | Значение |
|------|----------|
|200|OK|
|201|Created|
|202|Accepted|
|204|No Content|
|400|Bad Request|
|401|Unauthorized|
|403|Forbidden|
|404|Not Found|
|409|Conflict|
|422|Validation Error|
|500|Internal Error|

422 используется только для ошибок валидации входных данных.

409 используется для нарушений бизнес-правил.

---

# 10. Пагинация

Используются параметры:

```
page
page_size
```

Пример:

```
GET /projects?page=1&page_size=20
```

Ответ:

```json
{
  "success": true,
  "data": [],
  "meta": {
    "page": 1,
    "page_size": 20,
    "total": 145
  }
}
```

---

# 11. Сортировка

Используется параметр:

```
sort=
```

Пример:

```
sort=created_at
sort=-created_at
sort=name
sort=-updated_at
```

Знак "-" означает обратный порядок.

---

# 12. Фильтрация

Допускаются query parameters.

Например:

```
status=IN_PROGRESS
customer_id=...
manager_id=...
```

Сложные фильтры не входят в Pilot MVP.

---

# 13. UUID

Все идентификаторы являются UUID.

Пример:

```
GET /projects/4a39b8fd-....
```

Числовые идентификаторы не используются.

---

# 14. Аутентификация

Используется JWT.

Передача токена:

```
Authorization: Bearer <token>
```

Все защищённые endpoints требуют валидного токена.

---

# 15. Авторизация

Используется ролевая модель.

Минимальные роли:

```
ADMIN
MANAGER
SYSTEM
```

Проверка полномочий выполняется до выполнения бизнес-логики.

---

# 16. Correlation ID

Каждый запрос может содержать:

```
X-Correlation-ID
```

Если заголовок отсутствует, сервер обязан создать новый идентификатор.

Correlation ID должен:

- сохраняться в Business Event;
- записываться в журнал;
- возвращаться в ответе.

---

# 17. Идемпотентность

Для операций повторного выполнения используется:

```
Idempotency-Key
```

Обязательно для:

- создания документов;
- публикации оферты;
- регистрации оплаты;
- генерации Artifact.

Повторный запрос с тем же ключом и тем же payload возвращает предыдущий результат.

---

# 18. OpenAPI

OpenAPI генерируется автоматически FastAPI.

Документация доступна:

```
/docs
```

JSON-схема:

```
/openapi.json
```

Ручное редактирование OpenAPI запрещено.

---

# 19. Версионирование

Изменения, нарушающие обратную совместимость, требуют новой версии API.

Например:

```
/api/v2
```

Внутри одной версии запрещено:

- менять формат ответа;
- менять имена полей;
- удалять обязательные поля;
- менять семантику endpoint.

---

```

```

Дополнительные ресурсы допускаются только после появления соответствующего модуля.

---

# 21. Endpoint действий

Изменение жизненного цикла выполняется отдельными действиями.

Например:

```
POST /projects/{id}/accept-offer
POST /projects/{id}/pause
POST /projects/{id}/resume
POST /projects/{id}/request-client-action
POST /projects/{id}/submit-results
POST /projects/{id}/approve-results
POST /projects/{id}/close
```

Каждый endpoint:

- проверяет допустимость перехода;
- сохраняет Business Event;
- изменяет состояние;
- возвращает единый контракт ответа.

---

# 22. Требования к реализации

Каждый endpoint обязан:

- иметь OpenAPI-описание;
- использовать Pydantic DTO;
- проходить авторизацию;
- использовать единый Error Contract;
- использовать Correlation ID;
- публиковать события при изменении состояния;
- иметь integration tests.

---

# 23. Не входит в Pilot MVP

Не реализуются:

- GraphQL;
- gRPC;
- WebSocket API;
- публичный Event API;
- API Gateway;
- распределённый Event Bus;
- подписка на события через NATS;
- webhook framework.
