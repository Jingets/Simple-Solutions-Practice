**E-005 Архитектура данных**

**Версия:** 1.0

**Статус:** Approved

**Раздел:** E — Engineering Architecture

**1. Scope**

Настоящий документ определяет архитектуру хранения данных цифровой платформы Simple Solutions Practice.

Документ описывает:

- модель хранения данных;

- используемые технологии;

- правила проектирования схем данных;

- соглашения по именованию;

- требования к производительности;

- требования к целостности данных.

**2. Data Platform Overview**

Платформа использует специализированные хранилища данных, каждое из которых отвечает за собственный тип информации.

Использование нескольких специализированных хранилищ предпочтительнее универсального решения.

**Primary Database**

Назначение:

хранение операционных данных платформы.

Технология:

**PostgreSQL 17**

**Cache Layer**

Назначение:

ускорение чтения часто используемых данных.

Технология:

**Valkey**

**Search Platform**

Назначение:

полнотекстовый поиск и аналитические выборки.

Технология:

**OpenSearch**

**Object Storage**

Назначение:

хранение файлов.

Технология:

**S3 Compatible Object Storage**

**Event Storage**

Назначение:

очереди сообщений и гарантированная доставка событий.

Технология:

**NATS JetStream**

**Архитектурное правило**

Каждый тип данных должен храниться в специализированном хранилище.

Использование PostgreSQL для хранения файлов, кэша или поисковых индексов не допускается.

**3. PostgreSQL Architecture**

PostgreSQL является единственным источником истины (System of Record) для всех операционных данных платформы.

**DA-001**

Все изменения бизнес-данных выполняются только через PostgreSQL.

**DA-002**

PostgreSQL используется исключительно для хранения нормализованных данных.

**DA-003**

Полнотекстовый поиск реализуется через OpenSearch.

**DA-004**

Кэширование реализуется через Valkey.

**DA-005**

Хранение файлов реализуется через S3-совместимое объектное хранилище.

**Архитектурное правило**

PostgreSQL остаётся единственным владельцем состояния платформы.

Все остальные хранилища являются производными и могут быть полностью восстановлены из PostgreSQL.

**4. Database Design Principles**

Все базы данных платформы проектируются по единым правилам.

Основной целью является обеспечение целостности данных, производительности и долгосрочной сопровождаемости.

**DDP-001**

Все бизнес-данные хранятся в нормализованном виде.

Денормализация допускается только при наличии измеримого выигрыша производительности.

**DDP-002**

Каждая таблица имеет единственного владельца в рамках Platform Service.

Совместное владение таблицами несколькими сервисами запрещается.

**DDP-003**

Каждая таблица должна иметь первичный ключ.

В качестве основного идентификатора используется UUID версии 7 (UUIDv7).

**DDP-004**

Все изменения структуры базы данных выполняются исключительно через миграции Entity Framework Core.

Ручное изменение схемы рабочей базы данных запрещается.

**DDP-005**

Все ограничения целостности реализуются средствами PostgreSQL.

Использование бизнес-кода вместо ограничений базы данных допускается только при невозможности реализации соответствующего ограничения на уровне СУБД.

**Архитектурное правило**

Целостность данных обеспечивается прежде всего средствами базы данных, а затем бизнес-логикой приложения.

**5. Naming Conventions**

Все объекты PostgreSQL используют единые правила именования.

**Tables**

Имена таблиц:

- единственное число;

- PascalCase.

Примеры:

Project

Customer

Invoice

DecisionPoint

BusinessEvent

**Columns**

Имена столбцов:

- PascalCase;

- без сокращений.

Примеры:

ProjectId

CreatedAt

UpdatedAt

CreatedBy

Status

**Primary Keys**

Первичный ключ каждой таблицы имеет имя:

Id

Тип:

UUIDv7

**Foreign Keys**

Внешние ключи имеют формат:

&lt;EntityName&gt;Id

Примеры:

CustomerId

ProjectId

OwnerId

ArtifactId

**Indexes**

Имена индексов:

IX\_&lt;Table&gt;\_&lt;Column&gt;

Примеры:

IX\_Project\_Status

IX\_Project\_CreatedAt

IX\_Invoice\_Number

**Unique Constraints**

UX\_&lt;Table&gt;\_&lt;Column&gt;

**Foreign Keys**

FK\_&lt;Table&gt;\_&lt;ReferencedTable&gt;

**Архитектурное правило**

Имена объектов базы данных должны быть предсказуемыми и формироваться автоматически по единым правилам.

**7. Data Lifecycle**

Каждый Business Object проходит определённый жизненный цикл.

Жизненный цикл определяется бизнес-логикой платформы и не зависит от способа хранения данных.

**DLC-001**

Объект создаётся в состоянии **Active**.

**DLC-002**

Во время эксплуатации объект может изменяться неограниченное количество раз.

Все изменения регистрируются через Audit Service.

**DLC-003**

После завершения активного использования объект переводится в состояние **Archived**.

Архивирование означает:

- исключение из операционной деятельности;

- сохранение всей истории;

- сохранение ссылочной целостности;

- доступность для поиска и анализа.

**DLC-004**

Физическое удаление бизнес-объектов не является стандартной операцией платформы.

Оно допускается только для объектов, явно определённых архитектурой как временные.

**DLC-005**

Архивирование не изменяет идентификатор объекта.

Все внешние ссылки продолжают оставаться корректными.

**Архитектурное правило**

История бизнеса ценнее свободного места на диске.

**8. Referential Integrity**

Связи между объектами являются частью бизнес-модели платформы.

**RI-001**

Все связи между Business Objects реализуются внешними ключами PostgreSQL.

**RI-002**

Удаление родительского объекта при наличии зависимых записей запрещается.

**RI-003**

Использование ON DELETE CASCADE для бизнес-таблиц запрещается.

Каскадное удаление допускается только для временных технических данных.

**RI-004**

Все нарушения ссылочной целостности рассматриваются как критическая ошибка проектирования.

**RI-005**

Изменение первичного ключа объекта запрещается.

Идентификатор объекта остаётся неизменным в течение всего жизненного цикла.

**Архитектурное правило**

Связи между объектами являются частью бизнес-логики и должны защищаться средствами СУБД.

**9. Optimistic Concurrency**

Платформа использует оптимистичную модель конкурентного доступа.

**OC-001**

Каждый изменяемый Business Object содержит поле **Version**.

**OC-002**

Изменение объекта возможно только при совпадении версии.

**OC-003**

При конфликте версий операция завершается ошибкой конкурентного изменения.

**OC-004**

Повторное выполнение операции выполняется на основании повторного чтения актуального состояния объекта.

**OC-005**

Пессимистические блокировки допускаются только при наличии подтверждённого требования производительности или целостности.

**Архитектурное правило**

Оптимистичная блокировка является стандартной моделью конкурентного доступа SSP.

**10. Transactions and Consistency**

Все изменения бизнес-данных должны обеспечивать согласованность платформы.

**TC-001**

Все операции изменения данных выполняются внутри транзакции PostgreSQL.

**TC-002**

Транзакция должна изменять только данные одного Platform Service.

Распределённые транзакции между сервисами запрещаются.

**TC-003**

Взаимодействие между сервисами обеспечивается исключительно через Business Events.

**TC-004**

После успешной фиксации транзакции создаётся запись Transactional Outbox.

**TC-005**

Согласованность между сервисами достигается посредством событийной модели (Eventual Consistency).

**Архитектурное правило**

Платформа предпочитает простую локальную транзакцию сложной распределённой транзакции.

**11. Database Organization**

Платформа использует единый кластер PostgreSQL.

Внутри кластера размещается единая база данных SSP.

Логическое разделение данных выполняется с использованием отдельных схем (Schemas).

**DBO-001**

Каждый Platform Service владеет собственной схемой PostgreSQL.

Схема outbox используется всеми сервисами для Transactional Outbox (общая таблица).

Пример:

identity

business

automation

artifact

notification

configuration

audit

**DBO-002**

Таблицы сервиса размещаются исключительно в принадлежащей ему схеме.

Размещение таблиц различных сервисов в одной схеме запрещается.

**DBO-003**

Доступ к таблицам другого сервиса напрямую запрещён.

Обмен информацией осуществляется:

- через публичный API;

- через Business Events;

- через контрактные модели.

**DBO-004**

Каждая схема имеет собственную историю миграций Entity Framework Core.

Миграции различных сервисов независимы друг от друга.

**DBO-005**

Права доступа PostgreSQL должны ограничивать возможность изменения объектов только владельцем соответствующей схемы.

**Архитектурное правило**

Каждый Platform Service является единственным владельцем своей схемы данных.

**12. Indexing Strategy**

Индексы создаются только при наличии практической необходимости.

Избыточное индексирование не допускается.

**IDX-001**

Первичный ключ индексируется автоматически.

Дополнительное индексирование первичного ключа запрещается.

**IDX-002**

Внешние ключи индексируются всегда.

**IDX-003**

Индексы создаются для:

- часто используемых фильтров;

- сортировок;

- соединений (JOIN);

- уникальных ограничений.

**IDX-004**

Полнотекстовый поиск не реализуется средствами PostgreSQL.

Для полнотекстового поиска используется OpenSearch.

**IDX-005**

Перед созданием нового индекса должен быть подтверждён сценарий его использования.

Индексы не создаются «на будущее».

**Архитектурное правило**

Каждый индекс должен иметь измеримую пользу.

**13. Data Types**

Для всех новых таблиц используются единые типы данных.

**Identifier**

UUID (UUIDv7)

**Date and Time**

timestamp with time zone (timestamptz)

**Boolean**

boolean

**Integer**

integer

bigint

Используются в зависимости от предполагаемого диапазона значений.

**Decimal Numbers**

numeric(p,s)

Используется для денежных и расчётных значений.

Типы float и double precision запрещены для финансовых данных.

**Text**

text

Использование varchar(n) допускается только при наличии объективного ограничения длины.

**JSON**

jsonb

Используется только для:

- расширяемых настроек;

- технических метаданных;

- интеграционных данных.

Хранение основной бизнес-модели в JSON запрещается.

**Архитектурное правило**

Тип данных должен отражать смысл информации, а не удобство реализации.

**14. Audit Data**

История изменений является обязательной частью платформы.

**AUD-001**

Удаление записей аудита запрещается.

**AUD-002**

Записи аудита являются неизменяемыми.

Изменение существующей записи аудита не допускается.

**AUD-003**

Все записи аудита содержат:

- идентификатор объекта;

- тип объекта;

- тип операции;

- автора изменения;

- дату изменения;

- версию объекта.

**AUD-004**

Audit Service не содержит бизнес-логики.

Его задача — регистрация и хранение истории изменений.

**Архитектурное правило**

История изменений рассматривается как самостоятельный бизнес-актив платформы.

**15. Object Storage**

Все бинарные объекты платформы хранятся исключительно в S3-совместимом объектном хранилище.

PostgreSQL не используется для хранения содержимого файлов.

**OS-001**

В PostgreSQL сохраняются только метаданные файла.

Минимальный набор:

- ArtifactId;

- StorageKey;

- OriginalFileName;

- ContentType;

- FileSize;

- SHA-256 Checksum;

- Version;

- CreatedAt;

- CreatedBy.

**OS-002**

Физическое содержимое файла хранится только в объектном хранилище.

**OS-003**

Обращение к файлам осуществляется исключительно через Artifact Service.

Прямой доступ сервисов к объектному хранилищу запрещён.

**OS-004**

Каждый объект имеет неизменяемый идентификатор и уникальный Storage Key.

Изменение содержимого создаёт новую версию объекта.

**OS-005**

Контроль целостности файла выполняется по криптографической контрольной сумме (SHA-256).

**Архитектурное правило**

База данных хранит сведения о файле.

Файл хранится в объектном хранилище.

**16. Backup Strategy**

Резервное копирование выполняется независимо для каждого типа данных.

**BKS-001 PostgreSQL**

PostgreSQL резервируется средствами PostgreSQL.

Резервная копия должна обеспечивать полное восстановление состояния базы данных.

**BKS-002 Object Storage**

Объектное хранилище резервируется независимо от PostgreSQL.

Резервные копии файлов не должны зависеть от резервных копий базы данных.

**BKS-003 Configuration**

Конфигурация платформы резервируется отдельно.

Включает:

- параметры сервисов;

- секреты (в соответствии с политикой безопасности);

- настройки инфраструктуры.

**BKS-004 Observability**

Метрики, журналы и трассировки не являются частью обязательной резервной копии платформы.

Их сохранение определяется политикой эксплуатации.

**BKS-005 Backup Independence**

Отказ резервного копирования одного компонента не должен препятствовать выполнению резервного копирования остальных компонентов.

**Архитектурное правило**

Каждый тип данных резервируется наиболее подходящим для него способом.

**17. Recovery Strategy**

Восстановление платформы выполняется поэтапно.

**RS-001**

Сначала восстанавливается PostgreSQL как единственный источник истины.

**RS-002**

Затем восстанавливается объектное хранилище.

**RS-003**

После восстановления PostgreSQL выполняется:

- повторное заполнение кэша Valkey;

- переиндексация OpenSearch;

- синхронизация производных данных.

**RS-004**

Производные хранилища не требуют отдельного резервного копирования для обеспечения согласованности бизнес-данных.

**RS-005**

После восстановления выполняется автоматическая проверка:

- ссылочной целостности;

- доступности файлов;

- соответствия контрольных сумм;

- готовности сервисов к работе.

**Архитектурное правило**

Восстановление платформы начинается с данных, а не с инфраструктуры.

Сначала восстанавливается источник истины, затем все производные компоненты приводятся в согласованное состояние.

**18. Data Retention**

Для каждого типа данных платформы должна быть определена политика хранения.

**DR-001**

Бизнес-данные не имеют срока автоматического удаления.

**DR-002**

Архивные данные сохраняются до принятия отдельного управленческого решения.

**DR-003**

Технические данные могут иметь ограниченный срок хранения.

К ним относятся:

- временные файлы;

- кэш;

- журналы диагностики;

- промежуточные результаты обработки.

**DR-004**

Политика хранения определяется владельцем соответствующего Platform Service.

**DR-005**

Автоматическое удаление данных допускается только для объектов, явно обозначенных как временные.

**Архитектурное правило**

Удаление данных должно быть исключением, а не стандартной операцией.

**19. Data Quality**

Качество данных является обязанностью всей платформы.

**DQ-001**

Каждый Business Object должен находиться в согласованном состоянии.

**DQ-002**

Дублирование информации между сервисами не допускается, если оно не является частью событийной модели.

**DQ-003**

Каждый Platform Service отвечает за качество принадлежащих ему данных.

**DQ-004**

Все ограничения предметной области должны иметь техническую реализацию.

**DQ-005**

Изменение данных в обход официальных сервисов платформы запрещается.

**Архитектурное правило**

Качество данных обеспечивается архитектурой, а не последующей очисткой.

**20. Data Evolution**

Модель данных развивается непрерывно.

Все изменения должны сохранять работоспособность платформы.

**DEV-001**

Изменение структуры данных выполняется только посредством миграций.

**DEV-002**

Каждая миграция должна быть воспроизводимой.

**DEV-003**

Удаление объектов базы данных допускается только после полного прекращения их использования.

**DEV-004**

Все изменения модели данных проходят архитектурную проверку.

**DEV-005**

Изменения должны обеспечивать возможность обновления без потери данных.

**Архитектурное правило**

Эволюция модели данных предпочтительнее её радикальной переработки.

**21. Fundamental Principles**

Архитектура хранения данных SSP основана на следующих принципах:

1.  PostgreSQL является единственным источником истины.

2.  Каждый Platform Service владеет только своими данными.

3.  Каждый тип данных хранится в специализированном хранилище.

4.  Производные данные могут быть полностью восстановлены.

5.  История бизнеса сохраняется.

6.  Простота предпочтительнее универсальности.

7.  Целостность данных важнее производительности.

8.  Архитектура должна обеспечивать развитие платформы без изменения ранее принятых решений.
