**E-010 Исполнительная модель**

**Версия:** 1.0

**Статус:** Draft

**Раздел:** E — Engineering Architecture

**1. Scope**

Настоящий документ определяет модель исполнения платформы Simple Solutions Practice.

Execution Model описывает единый механизм обработки любых действий, выполняемых платформой.

Модель исполнения не зависит от источника запроса и является обязательной для всех компонентов платформы.

**2. Execution Principles**

Platform Kernel рассматривает любое действие как единицу исполнения.

Источник действия не влияет на порядок его обработки.

**EX-001**

Любое действие проходит единый процесс исполнения.

**EX-002**

Источник действия не изменяет алгоритм обработки.

**EX-003**

Platform Kernel принимает решения только на основании текущего состояния платформы и зарегистрированных правил.

**EX-004**

Каждый этап исполнения является наблюдаемым.

**EX-005**

Исполнение должно быть воспроизводимым.

**Архитектурное правило**

Одинаковые входные условия приводят к одинаковому результату исполнения.

**3. Execution Request**

Любое действие начинается с формирования Execution Request.

Execution Request является единицей работы Platform Kernel.

**ER-001**

Execution Request содержит описание требуемого действия.

**ER-002**

Execution Request имеет уникальную идентичность.

**ER-003**

Execution Request создаётся до начала обработки.

**ER-004**

После регистрации Execution Request не изменяется.

**ER-005**

Execution Request используется для полной трассировки исполнения.

**Архитектурное правило**

Platform Kernel исполняет не пользовательские запросы, а Execution Requests.

**4. Execution Context**

Для обработки Execution Request Platform Kernel формирует Execution Context.

Execution Context содержит всю информацию, необходимую для принятия решения.

**EC-001**

Execution Context создаётся автоматически перед началом обработки.

**EC-002**

Execution Context включает только данные, необходимые для исполнения текущего запроса.

**EC-003**

Execution Context существует только в течение обработки Execution Request.

**EC-004**

Execution Context не сохраняется как самостоятельный объект платформы.

**EC-005**

После завершения исполнения Execution Context уничтожается.

**Архитектурное правило**

Контекст исполнения является временной рабочей областью Platform Kernel.

**5. Execution Lifecycle**

Каждый Execution Request проходит последовательность фаз исполнения.

Порядок фаз является обязательным и не может быть изменён.

**Phase 1. Accept**

Platform Kernel принимает Execution Request.

На данной фазе фиксируется факт поступления запроса.

Изменение состояния платформы не выполняется.

**Phase 2. Resolve**

Platform Kernel определяет объекты платформы, необходимые для обработки запроса.

На данной фазе формируется полная модель исполнения.

Изменение состояния объектов не допускается.

**Phase 3. Evaluate**

Platform Kernel определяет допустимость выполнения действия.

Оценка выполняется с использованием архитектурных механизмов платформы.

Результатом фазы является решение:

- разрешить исполнение;

- отклонить исполнение;

- отложить исполнение.

**Phase 4. Execute**

Platform Kernel выполняет разрешённые действия.

Все изменения рассматриваются как единая операция исполнения.

**Phase 5. Commit**

Platform Kernel подтверждает успешное завершение исполнения.

После подтверждения изменения становятся частью текущего состояния платформы.

**Phase 6. Publish**

Platform Kernel публикует события, сформированные в процессе исполнения.

Публикация выполняется только после успешного завершения предыдущих фаз.

**Phase 7. Complete**

Platform Kernel завершает Execution Request.

Все временные структуры исполнения освобождаются.

Execution Context уничтожается.

**Архитектурное правило**

Каждый Execution Request проходит одинаковый жизненный цикл независимо от своего происхождения.

**6. Execution Decision**

Platform Kernel принимает единственное решение на каждой фазе исполнения.

Исключение: при ошибке выполнения допускается повторное исполнение (Retry) в соответствии с политиками платформы.

**ED-001**

Решение принимается только один раз.

**ED-002**

После перехода к следующей фазе возврат к предыдущей фазе запрещается.

**ED-003**

Каждое решение фиксируется как часть истории исполнения.

**ED-004**

Решение не может быть изменено после подтверждения фазы.

**ED-005**

Все решения являются воспроизводимыми при одинаковом Execution Context.

**Архитектурное правило**

Исполнение представляет собой последовательность необратимых решений.

**7. Execution Outcome**

Каждый Execution Request завершается одним итоговым состоянием.

**EO-001**

Completed

Исполнение успешно завершено.

**EO-002**

Rejected

Исполнение отклонено до внесения изменений.

**EO-003**

Deferred

Исполнение отложено до выполнения необходимых условий.

**EO-004**

Failed

Исполнение завершилось ошибкой.

**EO-005**

Compensated

Ошибка была устранена посредством компенсационного исполнения.

**Архитектурное правило**

Execution Request всегда имеет одно окончательное состояние.

**8. Execution Modules**

Platform Kernel не выполняет прикладные операции самостоятельно.

Исполнение прикладной логики осуществляется специализированными Execution Modules.

**EM-001**

Execution Module реализует одну или несколько архитектурных возможностей платформы.

**EM-002**

Platform Kernel взаимодействует с Execution Module исключительно через публичный контракт.

**EM-003**

Внутренняя реализация Execution Module не влияет на архитектуру платформы.

**EM-004**

Execution Module может быть заменён другой реализацией при сохранении архитектурного контракта.

**EM-005**

Execution Module не принимает архитектурных решений.

Архитектурные решения принимает Platform Kernel.

**Архитектурное правило**

Kernel управляет исполнением.

Execution Modules выполняют работу.

**9. Module Contract**

Каждый Execution Module публикует архитектурный контракт.

Контракт определяет возможности модуля без раскрытия особенностей реализации.

**MC-001**

Контракт определяет предоставляемые операции.

**MC-002**

Контракт определяет входные данные.

**MC-003**

Контракт определяет возможные результаты выполнения.

**MC-004**

Контракт определяет архитектурные ограничения использования.

**MC-005**

Изменение реализации модуля не требует изменения Platform Kernel при сохранении контракта.

**Архитектурное правило**

Platform Kernel зависит от контракта.

Он не зависит от реализации.

**10. Module Replacement**

Execution Module может быть заменён альтернативной реализацией.

**MR-001**

Замена допускается только при полном соблюдении архитектурного контракта.

**MR-002**

Замена не должна изменять модель исполнения Platform Kernel.

**MR-003**

Замена не должна изменять жизненный цикл Execution Request.

**MR-004**

Замена не должна изменять модель Platform Objects.

**MR-005**

Совместимость новой реализации проверяется до её ввода в эксплуатацию.

**Архитектурное правило**

Платформа развивается посредством замены модулей, а не изменения Kernel.

**11. Technology Independence**

Execution Modules могут использовать различные технологии реализации.

**TI-001**

Выбор технологии является ответственностью разработчика Execution Module.

**TI-002**

Platform Kernel не зависит от языка программирования, фреймворка или способа хранения данных внутри модуля.

**TI-003**

Различные Execution Modules могут использовать различные технологии реализации одновременно.

**TI-004**

Технологические особенности не являются частью архитектурного контракта.

**TI-005**

Архитектурная совместимость имеет приоритет над технологическим единообразием.

**Архитектурное правило**

Архитектура платформы определяет поведение.

Технологии определяют способ реализации.

**12. Execution Capabilities**

Platform Kernel взаимодействует с Execution Modules посредством архитектурных возможностей (Execution Capabilities).

Execution Capability представляет собой абстрактную возможность платформы выполнить определённый класс операций.

**CP-001**

Execution Capability имеет уникальный идентификатор.

**CP-002**

Execution Capability определяет только назначение возможности.

Она не определяет способ реализации.

**CP-003**

Одна Capability может иметь одну или несколько совместимых реализаций.

**CP-004**

Execution Module реализует одну или несколько Execution Capabilities.

**CP-005**

Platform Kernel использует Capability как единственную точку выбора исполнителя.

**Архитектурное правило**

Kernel запрашивает Capability.

Модуль предоставляет её реализацию.

**13. Capability Resolution**

Определение конкретного Execution Module выполняется во время исполнения.

**CR-001**

Platform Kernel не хранит жёстких зависимостей на Execution Modules.

**CR-002**

Выбор реализации выполняется на основании зарегистрированных Capability.

**CR-003**

При наличии нескольких совместимых реализаций выбор определяется политиками платформы.

**CR-004**

Отсутствие реализации Capability рассматривается как ошибка конфигурации платформы.

**CR-005**

Замена реализации Capability не требует изменения логики Platform Kernel.

**Архитектурное правило**

Kernel выбирает возможность.

Платформа выбирает исполнителя.

**14. Module Registry**

Все Execution Modules регистрируются в едином реестре платформы.

**RG-001**

Module Registry содержит сведения о доступных Capability.

**RG-002**

Каждый зарегистрированный модуль публикует поддерживаемые Capability.

**RG-003**

Platform Kernel использует Registry только для разрешения Capability.

**RG-004**

Registry не содержит информации о внутреннем устройстве модулей.

**RG-005**

Изменение состава зарегистрированных модулей допускается без изменения архитектуры Platform Kernel.

**Архитектурное правило**

Реестр описывает возможности платформы, а не её внутреннюю реализацию.

**15. Execution Independence**

Execution Modules являются полностью автономными компонентами.

**EI-001**

Execution Module не должен зависеть от внутреннего устройства других модулей.

**EI-002**

Взаимодействие между модулями осуществляется только через Platform Kernel либо через опубликованные архитектурные контракты.

**EI-003**

Отказ одного Execution Module не должен нарушать работоспособность остальных модулей, если их функциональность не зависит от недоступной Capability.

**EI-004**

Execution Module может обновляться, заменяться или масштабироваться независимо от других модулей.

**EI-005**

Архитектурная изоляция модулей является обязательным требованием платформы.

**Архитектурное правило**

Execution Modules являются независимыми исполнителями общей архитектуры платформы.

**16. Capability Contract**

Каждая Execution Capability определяется архитектурным контрактом.

Контракт описывает ожидаемое поведение платформы независимо от конкретной реализации.

**CC-001**

Capability Contract определяет назначение Capability.

**CC-002**

Capability Contract определяет допустимые входные данные.

**CC-003**

Capability Contract определяет ожидаемые результаты исполнения.

**CC-004**

Capability Contract определяет условия успешного завершения.

**CC-005**

Все реализации одной Capability обязаны полностью соответствовать Capability Contract.

**Архитектурное правило**

Контракт определяет поведение.

Модуль реализует контракт.

**17. Execution Responsibility**

Ответственность за исполнение распределяется между архитектурными компонентами платформы.

**ERS-001**

Platform Kernel отвечает за координацию исполнения.

**ERS-002**

Execution Module отвечает за выполнение специализированной операции.

**ERS-003**

Capability Contract отвечает за единообразие поведения.

**ERS-004**

Platform Objects определяют предмет исполнения.

**ERS-005**

Business Rules определяют допустимость результата.

**Архитектурное правило**

Каждый компонент отвечает только за собственную область ответственности.

**18. Module Certification**

Execution Module допускается к использованию только после подтверждения совместимости с Capability Contract.

**MCF-001**

Каждая реализация Capability проходит архитектурную проверку.

**MCF-002**

Проверка подтверждает соответствие Capability Contract.

**MCF-003**

Реализация, нарушающая Capability Contract, не может использоваться Platform Kernel.

**MCF-004**

Замена реализации требует повторного подтверждения совместимости.

**MCF-005**

Результаты проверки фиксируются в Platform Registry.

**Архитектурное правило**

Platform Kernel доверяет только сертифицированным реализациям.

**19. Execution Consistency**

Использование различных реализаций одной Capability не должно изменять архитектурное поведение платформы.

**ECN-001**

Все реализации одной Capability должны приводить к одинаковому архитектурному результату.

**ECN-002**

Различия в технологии реализации не должны изменять модель исполнения.

**ECN-003**

Изменение реализации допускается без изменения Execution Model.

**ECN-004**

Capability остаётся неизменной при замене Execution Module.

**ECN-005**

Platform Kernel рассматривает все совместимые реализации как эквивалентные.

**Архитектурное правило**

Архитектурное поведение определяется контрактом, а не технологией реализации.

**20. Delegated Execution**

Platform Kernel не выполняет специализированные операции самостоятельно.

Исполнение передаётся соответствующему Execution Module.

**DE-001**

Kernel принимает решение о необходимости выполнения операции.

**DE-002**

Kernel выбирает соответствующую Execution Capability.

**DE-003**

Kernel делегирует исполнение зарегистрированному Execution Module.

**DE-004**

Kernel ожидает результат исполнения.

**DE-005**

Kernel анализирует результат и принимает последующее архитектурное решение.

**Архитектурное правило**

Kernel управляет исполнением.

Execution Module выполняет операцию.

Kernel управляет результатом.

**21. Module Isolation**

Execution Modules являются полностью изолированными исполнителями.

**MI-001**

Execution Module не управляет Platform Kernel.

**MI-002**

Execution Module не может инициировать изменение архитектурного состояния платформы.

**MI-003**

Execution Module не имеет доступа к внутреннему состоянию Platform Kernel.

**MI-004**

Execution Module получает только данные, необходимые для выполнения текущей операции.

**MI-005**

После завершения операции модуль возвращает только результат исполнения.

**Архитектурное правило**

Execution Module не управляет платформой.

Он предоставляет специализированную возможность.

**22. Execution Result**

Каждый Execution Module возвращает унифицированный результат исполнения.

**XR-001**

Результат содержит признак успешного или неуспешного выполнения.

**XR-002**

Результат может содержать созданные или изменённые Platform Objects.

**XR-003**

Результат может содержать диагностическую информацию.

**XR-004**

Результат не изменяет Platform Objects самостоятельно.

**XR-005**

Окончательное решение о принятии результата принимает Platform Kernel.

**Архитектурное правило**

Execution Module сообщает результат.

Platform Kernel определяет последствия.

**23. Execution Failure**

Ошибки исполнения являются частью архитектурной модели платформы.

**XF-001**

Ошибка Execution Module не считается ошибкой Platform Kernel.

**XF-002**

Platform Kernel определяет дальнейшие действия после получения ошибки.

**XF-003**

Ошибки различных Execution Modules обрабатываются единообразно.

**XF-004**

Execution Module не принимает решений о повторном выполнении операции.

**XF-005**

Политика обработки ошибок определяется архитектурой платформы.

**Архитектурное правило**

Модули выполняют работу.

Platform Kernel управляет последствиями её выполнения.

**24. Execution Resources**

Execution Module использует ресурсы платформы для выполнения специализированных операций.

Platform Kernel управляет доступностью ресурсов, но не их внутренней реализацией.

**RS-001**

Каждый Execution Resource имеет уникальную идентичность.

**RS-002**

Execution Resource предоставляет одну или несколько архитектурных возможностей.

**RS-003**

Execution Resource может использоваться несколькими Execution Modules.

**RS-004**

Execution Resource может быть временно недоступен.

**RS-005**

Доступность Execution Resource определяется Platform Kernel.

**Архитектурное правило**

Kernel управляет использованием ресурсов.

Execution Module использует предоставленные ресурсы.

**25. Resource Allocation**

Перед началом исполнения Platform Kernel определяет необходимые ресурсы.

**RA-001**

Выделение ресурсов выполняется до передачи управления Execution Module.

**RA-002**

Недостаточность ресурсов может привести к отложенному исполнению.

**RA-003**

Освобождение ресурсов выполняется после завершения Execution Request.

**RA-004**

Execution Module не управляет жизненным циклом ресурсов.

**RA-005**

Все операции распределения ресурсов являются наблюдаемыми.

**Архитектурное правило**

Ресурсы принадлежат платформе.

Модули получают их во временное использование.

**26. Resource Independence**

Execution Capability не зависит от конкретного ресурса.

**RI-001**

Capability определяет требуемый тип ресурса.

**RI-002**

Конкретный Execution Resource выбирается Platform Kernel.

**RI-003**

Замена Execution Resource не изменяет архитектурное поведение Capability.

**RI-004**

Несколько совместимых ресурсов могут использоваться одновременно.

**RI-005**

Выбор ресурса определяется политиками платформы.

**Архитектурное правило**

Capability использует абстрактный ресурс.

Platform Kernel выбирает конкретную реализацию.

**27. Execution Scalability**

Исполнение должно масштабироваться без изменения архитектурной модели платформы.

**SC-001**

Execution Modules могут масштабироваться независимо друг от друга.

**SC-002**

Execution Resources могут масштабироваться независимо от Execution Modules.

**SC-003**

Platform Kernel сохраняет единый процесс исполнения независимо от количества модулей и ресурсов.

**SC-004**

Добавление новых Execution Providers не требует изменения архитектуры исполнения.

**SC-005**

Масштабирование не должно изменять Capability Contract.

**Архитектурное правило**

Масштабируется реализация.

Архитектура исполнения остаётся неизменной.

**28. Execution Policy**

Execution Policy определяет правила выбора способа исполнения Execution Capability.

Политика исполнения является частью архитектуры платформы и применяется Platform Kernel до передачи управления Execution Provider.

**EP-001**

Execution Policy определяет допустимые способы исполнения Capability.

**EP-002**

Execution Policy может учитывать состояние платформы, доступность ресурсов и архитектурные ограничения.

**EP-003**

Execution Policy не зависит от реализации Execution Provider.

**EP-004**

Изменение Execution Policy не требует изменения Platform Kernel.

**EP-005**

Execution Policy применяется до начала исполнения операции.

**Архитектурное правило**

Политика определяет способ исполнения.

Исполнитель выполняет выбранную стратегию.

**29. Strategy Selection**

Platform Kernel выбирает Execution Strategy в соответствии с Execution Policy.

**ES-001**

Для одной Capability может существовать несколько Execution Strategy.

**ES-002**

Execution Strategy определяет общий способ выполнения операции.

**ES-003**

Execution Strategy не определяет конкретную технологию реализации.

**ES-004**

Выбор Execution Strategy выполняется отдельно для каждого Execution Request.

**ES-005**

Выбранная Strategy фиксируется в истории исполнения.

**Архитектурное правило**

Выбор стратегии является частью процесса исполнения.

**30. Provider Selection**

После выбора Execution Strategy Platform Kernel определяет Capability Provider.

**PS-001**

Capability Provider должен поддерживать выбранную Strategy.

**PS-002**

При наличии нескольких совместимых Provider выбор выполняется согласно Policy платформы.

**PS-003**

Platform Kernel может заменить Provider без изменения Strategy.

**PS-004**

Capability Provider не влияет на архитектурную модель исполнения.

**PS-005**

Замена Provider не требует изменения Capability Contract.

**Архитектурное правило**

Strategy определяет способ исполнения.

Provider определяет исполнителя.

**31. Adaptive Execution**

Execution Model допускает адаптивный выбор способа исполнения.

**AE-001**

Выбор Strategy может различаться для одинаковой Capability при разных условиях исполнения.

**AE-002**

Изменение выбранной Strategy не изменяет ожидаемый архитектурный результат.

**AE-003**

Platform Kernel обязан обеспечить эквивалентность архитектурного поведения независимо от выбранной Strategy.

**AE-004**

Адаптация способа исполнения является внутренним механизмом платформы.

**AE-005**

Использование адаптивного исполнения не изменяет Capability Contract.

**Архитектурное правило**

Платформа может изменять способ исполнения.

Она не изменяет архитектурное поведение.

**32. Execution Guarantees**

Platform Kernel обеспечивает архитектурные гарантии исполнения независимо от реализации Execution Providers.

Execution Guarantees являются обязательными требованиями ко всем компонентам платформы.

**EG-001**

Каждый Execution Request обрабатывается не более одного раза в рамках одного жизненного цикла исполнения.

**EG-002**

Execution Request всегда завершается определённым итоговым состоянием.

**EG-003**

Platform Kernel не допускает неопределённого результата исполнения.

**EG-004**

Execution Request может быть восстановлен после сбоя платформы.

**EG-005**

Результат исполнения должен быть воспроизводим при одинаковых входных условиях.

**Архитектурное правило**

Platform Kernel гарантирует корректность исполнения.

Execution Providers гарантируют корректность реализации.

**33. Execution State**

Platform Kernel является единственным владельцем состояния исполнения.

**ST-001**

Execution Module не хранит архитектурное состояние исполнения.

**ST-002**

Состояние Execution Request управляется исключительно Platform Kernel.

**ST-003**

Execution Provider получает только необходимый рабочий контекст.

**ST-004**

После завершения исполнения Platform Kernel определяет новое состояние платформы.

**ST-005**

Execution Module не принимает участие в управлении жизненным циклом Execution Request.

**Архитектурное правило**

Состояние принадлежит Platform Kernel.

Исполнение принадлежит Execution Provider.

**34. Provider Neutrality**

Execution Providers являются взаимозаменяемыми исполнителями архитектурных контрактов.

**PN-001**

Provider не определяет архитектурное поведение платформы.

**PN-002**

Provider не влияет на последовательность фаз исполнения.

**PN-003**

Provider не управляет Platform Objects.

**PN-004**

Provider не принимает архитектурных решений.

**PN-005**

Замена Provider не требует изменения Platform Kernel.

**Архитектурное правило**

Platform Kernel не зависит от конкретного исполнителя.

**35. Execution Architecture Principles**

Execution Model SSP основана на следующих принципах.

1.  Platform Kernel является координатором исполнения.

2.  Все действия начинаются с Execution Request.

3.  Все решения принимаются Platform Kernel.

4.  Capability определяет архитектурную возможность.

5.  Capability Contract определяет ожидаемое поведение.

6.  Execution Policy определяет правила выбора способа исполнения.

7.  Execution Strategy определяет общий способ выполнения.

8.  Capability Provider реализует выбранную стратегию.

9.  Execution Module выполняет специализированную работу.

10. Platform Kernel определяет архитектурные последствия исполнения.
