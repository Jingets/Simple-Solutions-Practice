**E-003 Технологический стэк**

**Версия:** 1.0

**Статус:** Approved

**Раздел:** E — Engineering Architecture

**1. Scope**

Настоящий документ определяет утверждённый технологический стек цифровой платформы Simple Solutions Practice.

Использование технологий, не указанных в настоящем документе, допускается только после архитектурного согласования.

**2. Technology Selection Principles**

При выборе технологий применяются следующие критерии:

- зрелость и стабильность;

- промышленная эксплуатация;

- открытая лицензия;

- активное сообщество;

- долгосрочная поддержка;

- возможность самостоятельного размещения (Self-Hosted);

- отсутствие привязки к облачному провайдеру.

**4. Technology Governance**

Все технологии платформы подразделяются на три категории.

**Approved**

Технологии, являющиеся официальным стандартом платформы.

Их использование допускается без дополнительного согласования.

**Allowed Alternatives**

Технологии, допускаемые при наличии технического обоснования.

Замена должна сохранять совместимость архитектуры платформы.

**Prohibited**

Технологии, использование которых не допускается без отдельного архитектурного решения.

**Архитектурное правило**

Во всех новых компонентах платформы должны использоваться утверждённые технологии.

Применение иных технологий допускается только после оценки влияния на сопровождение, безопасность, производительность и долгосрочное развитие платформы.

**8. Third-Party Dependency Policy**

Использование сторонних библиотек допускается только при соблюдении требований настоящего документа.

Все внешние зависимости должны проходить инженерную оценку перед включением в платформу.

**TDP-001 License Compliance**

Допускается использование библиотек с лицензиями:

- MIT;

- Apache 2.0;

- BSD;

- PostgreSQL License;

- ISC.

Использование библиотек с лицензиями GPL, LGPL, AGPL или другими лицензиями с обязательствами по раскрытию исходного кода допускается только после юридической и архитектурной оценки.

**TDP-002 Project Activity**

Предпочтение отдаётся проектам, удовлетворяющим следующим условиям:

- регулярные обновления;

- активное сопровождение;

- публичный репозиторий;

- открытая история разработки;

- наличие документации.

Проекты без признаков активной поддержки использовать не рекомендуется.

**TDP-003 Community Adoption**

При прочих равных условиях предпочтение отдаётся библиотекам, имеющим широкое промышленное применение и большое сообщество пользователей.

**TDP-004 Security Assessment**

Перед использованием новой библиотеки выполняется проверка:

- известных уязвимостей;

- репутации проекта;

- происхождения пакета;

- истории безопасности.

Компоненты с критическими неустранёнными уязвимостями использовать запрещается.

**TDP-005 Dependency Minimization**

Каждая новая зависимость должна иметь инженерное обоснование.

Добавление библиотек, решающих незначительные задачи, не допускается при наличии эквивалентной функциональности в используемом технологическом стеке.

**TDP-006 Version Pinning**

Все зависимости должны использовать фиксированные версии.

Использование автоматически обновляемых диапазонов версий запрещается.

**TDP-007 Dependency Ownership**

Каждая внешняя зависимость должна иметь владельца внутри команды разработки.

Владелец отвечает за:

- актуальность версии;

- мониторинг безопасности;

- планирование обновлений;

- анализ влияния изменений.

**9. Version Management**

Используемые технологии должны обновляться контролируемо.

**TVM-001 LTS Preference**

При наличии Long-Term Support версии предпочтение отдаётся ей.

**TVM-002 Planned Upgrades**

Обновление ключевых компонентов платформы выполняется в рамках планируемых инженерных релизов.

Массовое обновление зависимостей без предварительного тестирования запрещается.

**TVM-003 Compatibility Verification**

Перед обновлением проверяется совместимость:

- программного кода;

- API;

- схем данных;

- инфраструктуры;

- CI/CD.

**TVM-004 Rollback Capability**

Каждое обновление должно предусматривать возможность быстрого отката.

**TVM-005 Change Documentation**

Все изменения технологического стека документируются.

Документация должна содержать:

- изменённые компоненты;

- причину обновления;

- потенциальные риски;

- выполненные проверки.

- завершение жизненного цикла технологии;

- выявление критических уязвимостей;

- появление более эффективного промышленного решения;

- изменение лицензионной политики поставщика;

- существенное изменение требований платформы.

Решение об изменении утверждённого технологического стека принимается только после оценки влияния на архитектуру, совместимость и эксплуатацию платформы.

**13. Exceptions**

Использование технологий, отсутствующих в настоящем документе, допускается только при наличии утверждённого архитектурного решения.

Запрос на исключение должен содержать:

- обоснование выбора;

- анализ альтернатив;

- оценку влияния на архитектуру;

- оценку лицензионных рисков;

- оценку эксплуатационных последствий;

- план сопровождения.

Исключение имеет ограниченный срок действия и подлежит повторному рассмотрению при очередном пересмотре технологического стека.
