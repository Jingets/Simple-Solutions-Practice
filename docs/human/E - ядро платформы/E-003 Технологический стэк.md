# E-003. Технологический стек платформы

## 1. Назначение

Документ определяет утверждённый технологический стек для разработки и запуска Pilot MVP платформы Simple Solutions Practice.

Требования настоящего документа применяются только к Pilot MVP.

Целевая архитектура последующих версий платформы может использовать другой стек, но не должна влиять на реализацию Pilot MVP без отдельного архитектурного решения.

---

**Версия:** 2.0

## 3. Принципы выбора стека

Технологический стек Pilot MVP должен обеспечивать:

- быстрый запуск разработки;
- простое развёртывание;
- низкую стоимость инфраструктуры;
- возможность работы одного AI-разработчика или небольшой команды;
- прозрачную генерацию REST API;
- автоматическую генерацию OpenAPI;
- управляемые миграции БД;
- воспроизводимое локальное и серверное окружение;
- возможность дальнейшего масштабирования без полной переработки доменной модели.

Pilot MVP реализуется как модульный монолит.

Микросервисная архитектура не применяется.

## 4. Backend

### 4.1 Язык

Python 3.13

Допустимая минимальная версия:

Python 3.12

Основной код должен быть совместим с Python 3.13.

### 4.2 Web framework

FastAPI

FastAPI используется для:

* REST API;
* dependency injection на уровне HTTP;
* валидации входных данных;
* сериализации ответов;
* генерации OpenAPI;
* маршрутизации;
* обработки ошибок;
* middleware.

### 4.3 Модели данных и валидация

Pydantic v2

Pydantic используется для:

* request DTO;
* response DTO;
* конфигурации приложения;
* контрактов Capability;
* контрактов событий;
* валидации входных данных;
* сериализации доменных результатов.

Pydantic-модели не заменяют ORM-модели и доменные сущности.

### 4.4 ORM

SQLAlchemy 2.x

Обязательные требования:

* использование SQLAlchemy 2.x style;
* типизированные модели;
* явные транзакции;
* запрет скрытых commits внутри Repository;
* работа через session scope;
* использование PostgreSQL UUID;
* единый `snake_case` для таблиц и колонок.

### 4.5 Миграции

Alembic

Все изменения схемы БД выполняются только через Alembic.

Ручное изменение рабочей схемы БД запрещено.

### 4.6 Драйвер PostgreSQL

Рекомендуемый асинхронный драйвер:

asyncpg

Допускается использование синхронного драйвера только при явном решении для конкретного этапа реализации.

В одном приложении не следует смешивать синхронный и асинхронный доступ к БД без необходимости.

### 4.7 Сервер приложения

Uvicorn

Для production-запуска допускается:

Gunicorn + Uvicorn workers

Для Pilot MVP достаточно запуска Uvicorn внутри backend-контейнера.

---

## 5. База данных

### 5.1 Основная СУБД

PostgreSQL

PostgreSQL является единственной основной БД Pilot MVP.

SQLite не применяется как замена PostgreSQL в production или integration tests.

### 5.2 Требования

* UUID для идентификаторов;
* `snake_case` для таблиц и колонок;
* временные значения с часовым поясом;
* внешние ключи для обязательных связей;
* индексы на поля поиска и связи;
* уникальные ограничения для бизнес-идентификаторов;
* транзакционная запись состояния и Business Event;
* миграции через Alembic;
* возможность полного создания схемы с нуля.

### 5.3 Хранение JSON

Для структурированных payload допускается PostgreSQL `jsonb`.

`jsonb` не должен использоваться вместо нормально определённых доменных полей, если структура данных стабильна и участвует в запросах.

## 6. Frontend

### 6.1 Язык

TypeScript

Использование JavaScript без TypeScript допускается только для конфигурационных файлов, если это необходимо инструменту.

### 6.2 UI framework

React

### 6.3 Сборка

Vite

### 6.4 Маршрутизация

React Router

### 6.5 Работа с API и серверным состоянием

TanStack Query

TanStack Query используется для:

* получения данных;
* кэширования;
* повторных запросов;
* invalidation;
* обработки loading и error states.

### 6.6 Стили

Tailwind CSS

Pilot MVP не требует создания отдельной дизайн-системы.

Допускается использование минимального набора переиспользуемых компонентов.

### 6.7 Формы

Допускается использование:

React Hook Form

Для валидации frontend-схем допускается:

Zod

Frontend-валидация не заменяет backend-валидацию.

---

## 7. API

### 7.1 Формат

REST

Базовый префикс:

/api/v1

### 7.2 Спецификация

OpenAPI 3.x

OpenAPI генерируется из фактической реализации FastAPI.

Ручная спецификация не должна расходиться с работающим API.

### 7.3 Формат данных

JSON

Для файлов используются отдельные upload/download endpoints или ссылки на хранилище.

### 7.4 Канонический формат ответа

Успех:

{
  "success": true,
  "data": {},
  "meta": {}
}

Ошибка:

{
  "success": false,
  "error": {
    "code": "ERROR_CODE",
    "message": "Human-readable message",
    "details": {}
  }
}

## 8. Аутентификация и авторизация

### 8.1 Механизм

JWT

Pilot MVP использует:

* email и пароль;
* access token;
* refresh token — при необходимости;
* хранение хеша пароля;
* проверку ролей на backend.

### 8.2 Роли

ADMIN
MANAGER
SYSTEM

`MANAGER` соответствует роли Consultant в целевой бизнес-модели.

Customer не получает полноценную учётную запись в Pilot MVP.

### 8.3 Хеширование паролей

Допускается:

Argon2

или:

bcrypt

Предпочтительно использовать Argon2.

---

## 9. Platform Kernel

Platform Kernel реализуется внутри backend-приложения.

Обязательные компоненты:

* Module Registry;
* Capability Registry;
* Event Dispatcher;
* Workflow Dispatcher;
* Artifact Manager;
* Policy checks;
* Business Event persistence.

### 9.1 Event Dispatcher

Для Pilot MVP используется:

in-process Event Dispatcher

или обработка событий после фиксации транзакции через локальный outbox-процесс.

NATS JetStream не входит в Pilot MVP.

### 9.2 Workflow Dispatcher

Поддерживаемые типы исполнения:

* LINEAR;
* CONDITIONAL;
* RETRY.

Параллельные, распределённые и компенсирующие workflow не входят в Pilot MVP.

---

## 10. Business Events

Business Events сохраняются в PostgreSQL.

Событие содержит минимум:

event_id: uuid
event_type: string
aggregate_type: string
aggregate_id: uuid
occurred_at: datetime
actor_id: uuid | null
correlation_id: uuid
payload: object

Изменение доменного состояния и запись события выполняются в одной транзакции.

NATS не является обязательным транспортом событий Pilot MVP.

### 11.1 Шаблоны

Документы генерируются из:

knowledge/**/*.yaml
knowledge/**/*.template.md

### 11.2 Rendering

Для рендеринга допускается:

Jinja2

### 11.3 Форматы результата

Обязательный базовый формат:

Markdown

Для пользовательских документов допускается генерация:

* HTML;
* PDF.

PDF является производным Artifact и не должен быть единственным хранимым форматом.

### 11.4 Хранение

Для Pilot MVP допускается:

* локальное файловое хранилище Docker volume;
* S3-совместимое хранилище.

Выбор должен быть единым для всей реализации.

## 15. Контейнеризация

Используется:

Docker
Docker Compose

Обязательные контейнеры:

* nginx;
* frontend;
* backend;
* postgres.

Допускаются дополнительные одноразовые контейнеры для:

* миграций;
* тестов;
* административных команд.

NATS, Redis, Elasticsearch, Kafka и Kubernetes не являются обязательными компонентами Pilot MVP.

---

## 16. Развёртывание

Pilot MVP должен запускаться командой:

docker compose up -d

После запуска должны быть доступны:

/health
/api/v1
/docs

Обязательные проверки:

* backend подключается к PostgreSQL;
* миграции применены;
* frontend доступен через nginx;
* OpenAPI открывается;
* health check проходит.

---

## 17. Конфигурация

Конфигурация передаётся через переменные окружения.

Обязательные категории:

* application;
* database;
* JWT;
* CORS;
* file storage;
* logging;
* Platform Legal Profile;
* public URLs.

Секреты не хранятся в Git.

Для локальной разработки используется `.env.example` без реальных секретов.

---

## 18. Логирование

Используется структурированное логирование.

Каждая запись должна по возможности содержать:

* timestamp;
* level;
* message;
* correlation_id;
* user_id;
* module;
* operation.

Чувствительные данные, пароли, JWT и полные платёжные реквизиты не логируются.

---

## 19. Наблюдаемость Pilot MVP

Обязательный минимум:

* `/health`;
* журнал ошибок;
* correlation ID;
* логирование запросов;
* логирование фоновых задач;
* контроль успешности миграций.

Prometheus, Grafana, OpenTelemetry и распределённый tracing относятся к Post-MVP, если не потребуются для инфраструктуры финансирующего пилота.

---

## 20. Не применяемые к Pilot MVP технологии

Следующие технологии не используются как обязательная часть Pilot MVP:

* C#;
* .NET;
* ASP.NET Core;
* Entity Framework Core;
* Vue;
* PrimeVue;
* NATS JetStream;
* Kafka;
* Kubernetes;
* LiteLLM;
* Ollama;
* отдельный API Gateway;
* микросервисная архитектура.

Документы, описывающие эти технологии, относятся к целевой архитектуре Post-MVP и не управляют реализацией текущего Pilot MVP.

## 22. Критерии соблюдения стека

Требование выполнено, если:

* backend работает на Python/FastAPI;
* данные хранятся в PostgreSQL;
* ORM реализован на SQLAlchemy;
* миграции выполняются Alembic;
* frontend реализован на React/TypeScript/Vite;
* API документирован через OpenAPI;
* система запускается Docker Compose;
* NATS и Organizational Memory не нужны для прохождения E2E;
* отсутствует обязательная зависимость от .NET или Vue;
* тесты запускаются воспроизводимо.
