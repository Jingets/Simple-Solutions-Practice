**S-001 Стандарты разработки**

**Статус:** MVP

**Приоритет:** P0

**Цель**

Настоящий документ определяет единый стандарт разработки исходного кода платформы Simple Solutions Practice.

Все программные компоненты платформы должны соответствовать настоящему стандарту.

Настоящий документ обязателен для разработчиков, автоматизированных средств разработки и систем генерации программного кода.

**Основной принцип**

Исходный код является частью архитектуры платформы.

Код должен быть:

- понятным;

- воспроизводимым;

- модульным;

- предсказуемым;

- расширяемым.

При возникновении конфликта между краткостью и читаемостью приоритет имеет читаемость.

**Общие требования**

Исходный код должен:

- соответствовать архитектуре SSP;

- быть полностью типизирован;

- иметь однозначное назначение;

- не содержать скрытой логики;

- быть пригодным для автоматического анализа.

**Правила именования**

**Каталоги**

- lowercase

- snake\_case

Пример:

project\_execution

**Файлы**

snake\_case

Пример

workflow\_engine.py

**Классы**

PascalCase

Пример

ProjectExecutionService

**Функции**

snake\_case

Пример

create\_offer\_contract()

**Переменные**

snake\_case

Пример

project\_status

**Константы**

UPPER\_CASE

Пример

DEFAULT\_TIMEOUT

**Типизация**

Использование type hints обязательно.

Любая публичная функция должна иметь:

- тип входных параметров;

- тип возвращаемого значения.

Использование неявных типов запрещается.

**Размер компонентов**

Рекомендуемые ограничения:

Функция:

до 40 строк.

Класс:

до 300 строк.

Файл:

до 500 строк.

При превышении необходимо выполнить декомпозицию.

**Ответственность**

Каждый класс должен иметь одну ответственность.

Каждая функция должна выполнять одно действие.

Каждый модуль должен реализовывать одну бизнес-функцию.

**Dependency Injection**

Создание зависимостей внутри бизнес-логики запрещено.

Все зависимости должны передаваться извне.

**Исключения**

Обработка ошибок обязательна.

Запрещается:

except:

pass

Каждое исключение должно:

- быть обработано;

- зарегистрировано;

- возвращено вызывающему компоненту при необходимости.

**Логирование**

Использование print() запрещено.

Используется исключительно Platform Logging.

**Комментарии**

Комментарии используются только для объяснения бизнес-смысла.

Комментарии, повторяющие программный код, запрещены.

Предпочтительно использовать говорящие имена вместо комментариев.

**Docstring**

Все публичные классы и методы обязаны иметь Docstring.

Минимальный состав:

- назначение;

- параметры;

- результат.

**Магические значения**

Использование магических чисел запрещено.

Все значения должны быть вынесены:

- в константы;

- в конфигурацию;

- в Platform Policy.

**Глобальное состояние**

Использование глобальных переменных запрещено.

Состояние хранится исключительно через Platform Context или Repository.

**Работа с данными**

Прямые SQL-запросы внутри бизнес-логики запрещены.

Доступ к данным осуществляется через Repository Layer.

**Работа с Artifact**

Создание, изменение и чтение Artifact выполняется исключительно через Artifact Manager.

Прямой доступ к файловой системе запрещён.

**Асинхронность**

Асинхронный код используется только там, где это действительно необходимо.

Запрещается использовать async без объективной причины.

**Архитектурные запреты**

Запрещается:

- циклическая зависимость модулей;

- дублирование бизнес-логики;

- копирование одинакового кода между модулями;

- изменение Platform Kernel из бизнес-модулей;

- использование внутренних компонентов другого модуля.

**Читаемость**

Исходный код должен быть понятен без дополнительного объяснения.

Если реализация требует подробного описания принципов работы, необходимо упростить архитектурное решение.

**Definition of Done**

Код считается соответствующим стандарту, если:

- соблюдены правила именования;

- используется полная типизация;

- отсутствуют архитектурные нарушения;

- соблюдён принцип единственной ответственности;

- отсутствуют магические значения;

- реализована обработка ошибок;

- код соответствует модульной архитектуре SSP.

**Главный принцип**

Исходный код должен быть написан таким образом, чтобы любой разработчик или система генерации кода могла безопасно продолжить развитие платформы без предварительного изучения внутренней реализации существующих модулей.
