**S-000 Принципы развития платформы**

**Версия:** 1.0

**Статус:** Draft

**Раздел:** D — Development

**1. Scope**

Настоящий документ определяет стратегию разработки платформы Simple Solutions Practice.

Стратегия разработки обеспечивает эволюционное развитие платформы при сохранении целостности архитектуры.

**2. Development Principles**

Разработка SSP строится на принципах модульности, постепенного развития и проверки решений практикой.

**DP-001**

Архитектура платформы проектируется полностью.

**DP-002**

Реализация платформы выполняется поэтапно.

**DP-003**

Каждый новый модуль должен приносить практическую ценность.

**DP-004**

Каждый этап разработки должен завершаться работоспособным результатом.

**DP-005**

Разработка не должна нарушать архитектурные принципы платформы.

**Архитектурное правило**

Архитектура проектируется один раз.

Реализация развивается непрерывно.

**3. MVP First**

Разработка начинается с минимально достаточной функциональности.

MVP должен обеспечивать возможность реальной эксплуатации платформы.

**MVP-001**

В MVP реализуются только функции, необходимые для решения текущих практических задач.

**MVP-002**

Неиспользуемая функциональность не реализуется заранее.

**MVP-003**

Каждый последующий этап расширяет возможности платформы.

**MVP-004**

Расширение платформы выполняется посредством новых модулей.

**MVP-005**

Развитие платформы не должно требовать изменения архитектурного ядра.

**Архитектурное правило**

Сначала работающая система.

Потом её развитие.

**4. Modular Evolution**

Функциональность платформы развивается посредством независимых модулей.

Каждый модуль представляет собой самостоятельную единицу развития платформы.

**ME-001**

Модуль реализует ограниченную бизнес-функцию.

**ME-002**

Модуль взаимодействует с платформой только через архитектурные контракты.

**ME-003**

Модуль может заменяться без изменения Platform Kernel.

**ME-004**

Модуль может развиваться независимо от остальных модулей.

**ME-005**

Каждый модуль имеет собственный жизненный цикл.

**Архитектурное правило**

Платформа развивается заменой и добавлением модулей.

Не изменением архитектурного ядра.

**5. Customer-Driven Development**

Развитие SSP определяется практическими задачами, возникающими в процессе эксплуатации платформы и оказания профессиональных услуг.

Потребности реальных пользователей являются основным источником развития функциональности платформы.

**CDD-001**

Каждый новый модуль должен иметь подтверждённую практическую необходимость.

**CDD-002**

Приоритет разработки определяется реальной ценностью для пользователей.

**CDD-003**

Гипотетическая функциональность не является основанием для разработки.

**CDD-004**

Результаты эксплуатации используются для формирования требований к следующим версиям платформы.

**CDD-005**

Практический опыт имеет приоритет перед предположениями.

**Архитектурное правило**

Платформа развивается вслед за практикой.

Не опережает её.

**6. Practice-Driven Evolution**

Каждый реализованный проект рассматривается как источник развития платформы.

Практический опыт является частью процесса разработки SSP.

**PDE-001**

Результаты проектов анализируются после их завершения.

**PDE-002**

Выявленные закономерности используются при развитии платформы.

**PDE-003**

Повторяющиеся задачи рассматриваются как кандидаты на автоматизацию.

**PDE-004**

Новые возможности реализуются в виде самостоятельных модулей.

**PDE-005**

Организационная память используется как источник требований к развитию платформы.

**Архитектурное правило**

Практика определяет направление развития платформы.

**7. Evolution Cycle**

Развитие SSP представляет собой непрерывный цикл.

Практическая деятельность и разработка платформы рассматриваются как единый процесс.

**EC-001**

Создание MVP.

**EC-002**

Практическая эксплуатация.

**EC-003**

Накопление организационного опыта.

**EC-004**

Выявление повторяющихся закономерностей.

**EC-005**

Реализация следующей версии платформы.

**Архитектурное правило**

Каждая новая версия платформы должна основываться на подтверждённом организационном опыте.

**8. Every Project Improves SSP**

Каждый завершённый проект должен приносить ценность не только клиенту, но и самой платформе.

Развитие SSP является побочным результатом её практического применения.

**EPS-001**

Каждый проект формирует новые Artifact.

**EPS-002**

Каждый проект пополняет Organizational Memory.

**EPS-003**

Каждый проект может выявлять новые архитектурные требования.

**EPS-004**

Каждый проект может приводить к появлению новых модулей платформы.

**EPS-005**

Полученный опыт используется при разработке следующих версий SSP.

**Архитектурное правило**

Каждый выполненный проект делает платформу лучше.

**9. Rule of Three**

Автоматизация должна основываться на подтверждённой повторяемости практики.

Повторяющиеся задачи являются основным источником развития платформы.

**RT-001**

Первое выполнение задачи рассматривается как получение нового опыта.

**RT-002**

Второе выполнение задачи используется для уточнения процесса и проверки воспроизводимости.

**RT-003**

Третье успешное повторение задачи делает её кандидатом на автоматизацию.

**RT-004**

Автоматизация выполняется посредством создания нового модуля или расширения существующего.

**RT-005**

Решение о реализации принимает владелец платформы на основании накопленного организационного опыта.

**Архитектурное правило**

Платформа автоматизирует устойчивую практику.

Не единичные случаи.

**10. Module Lifecycle**

Каждый модуль платформы проходит единый жизненный цикл.

**ML-001**

Идея.

Появление повторяющейся практической задачи.

**ML-002**

Проверка.

Подтверждение повторяемости и практической ценности.

**ML-003**

MVP.

Реализация минимально достаточной функциональности.

**ML-004**

Эксплуатация.

Использование модуля в реальных проектах.

**ML-005**

Развитие.

Расширение функциональности на основании накопленного опыта эксплуатации.

**Архитектурное правило**

Каждый модуль развивается эволюционно.

**11. Implementation Priority**

Приоритет реализации определяется практической ценностью.

Архитектурная завершённость не означает обязательную реализацию всех предусмотренных возможностей.

**IP-001**

Архитектура может предусматривать возможности, отсутствующие в текущем MVP.

**IP-002**

Отсутствие реализации не является нарушением архитектуры.

**IP-003**

Каждая реализованная функция должна иметь подтверждённую практическую ценность.

**IP-004**

Приоритет получают функции, сокращающие трудозатраты или повышающие качество оказываемых услуг.

**IP-005**

Разработка выполняется небольшими завершёнными итерациями.

**Архитектурное правило**

Полнота архитектуры важнее полноты первой реализации.

**12. Success Criteria**

Каждый этап развития платформы считается завершённым только при достижении практического результата.

**SC-001**

Новая функциональность должна использоваться в реальной работе.

**SC-002**

Полученный опыт должен быть отражён в Organizational Memory.

**SC-003**

Результаты эксплуатации должны быть проанализированы.

**SC-004**

При необходимости должны быть сформированы требования к следующей итерации развития.

**SC-005**

Каждая завершённая итерация должна повышать практическую ценность платформы.

**Архитектурное правило**

Завершённой считается не написанная функция.

Завершённым считается решение, успешно применённое на практике.
