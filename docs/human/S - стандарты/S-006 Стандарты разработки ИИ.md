# S-006. Стандарты разработки с использованием ИИ

## 1. Назначение

Документ устанавливает обязательные правила использования AI-разработчиков при создании Pilot MVP платформы Simple Solutions Practice.

AI-разработчик рассматривается как исполнитель технической задачи. Он не является владельцем архитектуры и не принимает самостоятельных продуктовых или доменных решений.

---

## 2. Обязательные источники требований

Перед выполнением задачи AI-разработчик обязан использовать:

1. `docs/AI/AI-008. Pilot MVP Canonical Specification.md`;
2. соответствующий документ раздела `M`;
3. применимые документы раздела `X`;
4. применимые документы разделов `E`, `R` и `S`;
5. связанные спецификации и шаблоны из `knowledge/`.

Порядок приоритета документации определяется только документом `AI-008` и не дублируется в настоящем стандарте.

---

## 3. Основной принцип

AI-разработчик реализует только явно определённые требования.

Запрещено:

- создавать новые бизнес-сущности;
- вводить новые статусы;
- вводить новые события;
- изменять канонические имена;
- менять технологический стек;
- расширять границы Pilot MVP;
- самостоятельно устранять доменные противоречия;
- реализовывать Post-MVP-функциональность;
- заменять отсутствующую спецификацию предположением.

## 6. Размер задачи

Одна задача должна приводить к одному проверяемому результату.

Допустимый объём задачи:

* одна сущность;
* одна Capability;
* один API-сценарий;
* один Artifact;
* одна миграция или связанный набор миграций;
* один завершённый пользовательский сценарий.

Задача не должна одновременно охватывать несколько независимых модулей.

---

## 7. Требования к реализации

Каждая бизнес-возможность должна включать применимые элементы:

* доменную модель;
* SQLAlchemy-модель;
* Alembic-миграцию;
* Pydantic DTO;
* Repository;
* Service или Capability;
* API endpoint;
* авторизацию;
* проверку допустимости переходов;
* обработку ошибок;
* публикацию Business Event;
* unit tests;
* integration tests;
* OpenAPI-контракт.

Пропуск обязательного элемента должен быть явно зафиксирован в отчёте.

---

## 8. Правила изменения состояния

Состояние бизнес-сущности изменяется только через определённую операцию или Capability.

Для Project разрешены только статусы:

DRAFT
IN_PROGRESS
ON_HOLD
WAITING_CLIENT
REVIEW
COMPLETED
CLOSED

Прямое изменение поля `status` в обход проверки перехода запрещено.

Каждый успешный переход должен:

1. проверить текущее состояние;
2. проверить полномочия;
3. выполнить изменение атомарно;
4. сохранить Business Event;
5. вернуть результат по единому контракту.

---

## 9. Правила событий

Используются только канонические события из `AI-008`.

Минимальная структура Business Event:

event_id: uuid
event_type: string
aggregate_type: string
aggregate_id: uuid
occurred_at: datetime
actor_id: uuid | null
correlation_id: uuid
payload: object


Событие:

* создаётся после успешной валидации;
* сохраняется в одной транзакции с изменением состояния;
* не редактируется после сохранения;
* не используется под несколькими именами для одного факта.

---

## 10. Правила API

Базовый префикс:

/api/v1

Успешный ответ:

{
  "success": true,
  "data": {},
  "meta": {}
}

Ответ с ошибкой:

{
  "success": false,
  "error": {
    "code": "ERROR_CODE",
    "message": "Human-readable message",
    "details": {}
  }
}

Обязательные правила:

* URL и параметры используют `snake_case`;
* пагинация: `page`, `page_size`;
* сортировка: `sort=created_at`;
* обратная сортировка: `sort=-created_at`;
* correlation ID передаётся через `X-Correlation-ID`;
* API не раскрывает внутренние имена таблиц и ORM-моделей;
* OpenAPI должна соответствовать фактической реализации.

---

## 11. Правила базы данных

Обязательные требования:

* PostgreSQL;
* UUID для идентификаторов;
* `snake_case` для таблиц и колонок;
* миграции только через Alembic;
* ограничения и индексы определяются явно;
* внешние ключи создаются для всех обязательных связей;
* даты хранятся с часовым поясом;
* удаление данных не должно нарушать историю Business Events;
* схема должна создаваться с нуля одной последовательностью миграций.

Ручное изменение схемы БД без миграции запрещено.

---

## 12. Правила модулей

Бизнес-модуль:

* не обращается напрямую к внутренним объектам другого модуля;
* использует Platform Kernel и разрешённые контракты;
* регистрирует Manifest;
* регистрирует Capabilities;
* регистрирует подписки на события;
* не содержит инфраструктурных зависимостей в доменном слое;
* не вводит собственный формат Capability Result.

Состояния модуля определяются `AI-008`.

---

## 13. Идемпотентность

Операции, которые могут быть вызваны повторно, должны быть идемпотентными.

Для таких операций необходимо определить:

* `idempotency_key`;
* область уникальности;
* срок хранения результата;
* поведение при повторном запросе;
* поведение при совпадении ключа и различном payload.

Повторный вызов с тем же ключом и тем же payload должен возвращать ранее полученный результат без повторного изменения состояния.

---

## 14. Генерация документов

Перед реализацией Artifact AI-разработчик обязан проверить:

* наличие YAML-спецификации;
* наличие шаблона;
* соответствие `knowledge/document-standard.md`;
* существование события-триггера;
* существование источника каждого поля;
* наличие связи с Project;
* наличие данных Customer;
* наличие Platform Legal Profile;
* определённое место хранения результата;
* зарегистрированный тип Artifact.

Если обязательная переменная не имеет источника, генерация не реализуется.

---

## 15. Тестирование

Минимальный набор:

### Unit tests

Проверяют:

* бизнес-правила;
* переходы состояний;
* валидацию;
* формирование событий;
* идемпотентность.

### Integration tests

Проверяют:

* Repository;
* транзакции;
* миграции;
* API;
* авторизацию;
* генерацию Artifact;
* запись Business Events.

### E2E tests

Проверяют полный сценарий Pilot MVP:

Lead
→ Project
→ Workspace
→ Check-up
→ Estimation
→ Offer
→ Invoice
→ Payment
→ Execution
→ Acceptance Certificate
→ Closed Project

Тесты должны быть воспроизводимы в Docker Compose.

---

## 16. Работа с противоречиями

Если противоречие разрешено в `AI-008`, используется решение `AI-008`.

Если два документа одного уровня содержат несовместимые требования, AI-разработчик:

1. останавливает соответствующую часть задачи;
2. фиксирует конфликт;
3. указывает документы и конкретные требования;
4. не выбирает вариант самостоятельно.

Независимые части задачи могут быть продолжены.

---

## 17. Работа с отсутствующей спецификацией

При отсутствии обязательного контракта запрещено:

* придумывать поля;
* копировать модель из другой сущности без проверки;
* создавать новые статусы;
* создавать новые события;
* предполагать источники шаблонных данных;
* самостоятельно определять бизнес-правила.

Допускается создание технического каркаса только при явном разрешении владельца архитектуры.

## 19. Требования к коммитам

Каждый завершённый пакет изменений оформляется отдельным коммитом.

Формат:

AI-commit: <краткое описание результата>

Коммит должен:

* содержать один логически завершённый результат;
* включать связанные тесты;
* не содержать посторонних изменений;
* не смешивать рефакторинг и новую функциональность без необходимости;
* проходить тесты до фиксации.

---

## 20. Definition of Done задачи

Задача завершена, когда:

* требования реализованы;
* миграции применяются;
* тесты проходят;
* OpenAPI актуальна;
* события соответствуют каноническому каталогу;
* отсутствуют неописанные сущности и статусы;
* не нарушены границы Pilot MVP;
* результат воспроизводится в Docker Compose;
* отчёт сформирован.
