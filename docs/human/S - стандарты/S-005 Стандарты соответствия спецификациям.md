**S-005 Стандарты соответствия спецификациям**

**Статус:** MVP

**Приоритет:** P0

**Цель**

Настоящий документ определяет единый стандарт проверки соответствия реализации программных компонентов утверждённым спецификациям платформы Simple Solutions Practice.

Проверка соответствия является обязательной частью разработки.

Модуль не может считаться реализованным до успешного прохождения проверки соответствия.

**Основной принцип**

Документация является исполняемым контрактом.

Каждый документ серии **M** определяет обязательный состав функциональности.

Реализация обязана полностью соответствовать утверждённой спецификации.

**Источники требований**

Проверка соответствия выполняется относительно следующих документов:

- Architecture (A)

- Engine (E)

- Repository (R)

- Module Specification (M)

- Standards (S)

Приоритет документов определяется архитектурой платформы.

**Объекты проверки**

Для каждого модуля автоматически проверяется наличие и корректность:

- Module Manifest;

- Capability;

- Business Events;

- System Events;

- Artifact;

- API Endpoint;

- Repository;

- Workflow;

- Configuration;

- Definition of Done.

**Проверка Module Manifest**

Необходимо подтвердить наличие:

- Module ID;

- Name;

- Version;

- Description;

- Registered Capability;

- Published Events;

- Subscribed Events.

**Проверка Capability**

Для каждой Capability, описанной в спецификации:

- Capability существует;

- зарегистрирована в Kernel;

- доступна для вызова;

- возвращает ожидаемый результат.

Отсутствие хотя бы одной обязательной Capability считается нарушением спецификации.

**Проверка Business Events**

Для каждого Business Event проверяется:

- регистрация;

- публикация;

- корректность структуры;

- соответствие спецификации.

**Проверка Artifact**

Для каждого Artifact проверяется:

- создание;

- регистрация;

- тип;

- версия;

- принадлежность проекту.

**Проверка API**

Для каждого Endpoint проверяется:

- наличие;

- соответствие маршрута;

- HTTP Method;

- схема запроса;

- схема ответа;

- регистрация в OpenAPI.

**Проверка Workflow**

Для каждого Workflow проверяется:

- возможность запуска;

- корректность переходов между состояниями;

- регистрация обязательных событий;

- завершение сценария.

**Проверка Repository**

Проверяется:

- наличие Repository;

- отсутствие прямого доступа к БД;

- соответствие стандартам серии S.

**Проверка архитектурных ограничений**

Автоматически контролируется отсутствие:

- прямых вызовов между бизнес-модулями;

- бизнес-логики в Platform Kernel;

- доступа Frontend к БД;

- обхода Workflow Engine;

- обхода Artifact Manager;

- обхода Repository Layer.

**Проверка Definition of Done**

Каждый пункт раздела Definition of Done спецификации должен иметь подтверждение реализации.

Пункт считается выполненным только при наличии:

- программной реализации;

- автоматического теста;

- успешного результата проверки.

**Compliance Report**

После завершения проверки формируется Compliance Report.

Минимальный состав отчёта:

- модуль;

- версия;

- дата проверки;

- перечень выполненных требований;

- перечень нарушений;

- статус проверки.

**Статусы проверки**

Используются следующие статусы:

- Passed

- Passed with Warning

- Failed

- Blocked

**Правила принятия**

Модуль может быть интегрирован в платформу только при статусе:

Passed

Статусы Failed и Blocked запрещают регистрацию модуля в Platform Kernel.

**Автоматизация**

Проверка соответствия должна запускаться автоматически:

- при создании Pull Request;

- при сборке проекта;

- перед выпуском новой версии;

- перед регистрацией нового модуля.

Ручная проверка допускается только как дополнительная.

**Архитектурные ограничения**

Проверка соответствия не изменяет программный код.

Не исправляет нарушения автоматически.

Не изменяет спецификации.

Результатом проверки является исключительно отчёт о соответствии.

**Definition of Done**

Стандарт считается реализованным, если платформа способна автоматически подтвердить соответствие реализации требованиям архитектуры, спецификаций модулей и стандартов разработки без участия разработчика.

**Главный принцип**

В платформе SSP правильность реализации определяется не субъективной оценкой разработчика, а автоматической проверкой соответствия утверждённой спецификации.

Документ является первичным источником требований, а программный код — его реализацией.
