**Модель полномочий**

**Версия:** 1.0

**Статус:** Draft

**Раздел:** B — Business

**Связанные документы**

- B-001 Бизнес-модель

- B-002 Модель бизнес-процессов

- B-003 Справочник бизнес-событий

**1. Назначение**

Permission Model определяет полномочия участников цифровой платформы Simple Solutions Practice.

Документ устанавливает, какие бизнес-действия может выполнять каждая роль, а также правила проверки полномочий перед выполнением любого действия.

Permission Model является обязательной частью бизнес-архитектуры платформы.

**2. Основные принципы**

**2.1 Полномочия относятся к действиям**

Права доступа предоставляются не к данным и не к объектам.

Права предоставляются исключительно на выполнение определённых бизнес-действий.

**2.2 Любое действие создаёт Event**

Если действие разрешено —

создаётся соответствующее Business Event.

Если действие запрещено —

Event не создаётся.

Изменения бизнес-состояния не происходит.

**2.3 Отсутствие права безопаснее ошибки**

Если невозможно однозначно определить полномочия пользователя, действие запрещается.

Платформа всегда выбирает безопасный вариант поведения.

**2.4 Проверка обязательна**

Любое действие проходит проверку:

- роли;

- принадлежности проекта;

- текущего состояния объекта;

- дополнительных ограничений.

Только после успешной проверки допускается создание Event.

**2.5 Минимально необходимые полномочия**

Каждая роль получает только те полномочия, которые необходимы для выполнения её задач.

Избыточные права запрещаются.

**3. Роли платформы**

**Partner**

Представитель организации-заказчика или физическое лицо, взаимодействующее с SSP.

Partner принимает решения по своему проекту, но не управляет внутренними процессами платформы.

**Consultant**

Эксперт Simple Solutions Practice.

Консультант управляет проектом, принимает профессиональные решения и сопровождает партнёра.

**Administrator**

Технический администратор платформы.

Administrator обеспечивает работоспособность системы, но не вмешивается в бизнес-процессы.

**System**

Автоматизированные процессы платформы.

System выполняет действия, предусмотренные бизнес-логикой.

**External Service**

Внешние сервисы.

Например:

- банк;

- платёжный шлюз;

- Telegram;

- MAX;

- почтовые сервисы;

- API интеграций.

Внешние сервисы не обладают бизнес-полномочиями.

Они только инициируют разрешённые события.

**5. Ограничения полномочий**

Независимо от роли запрещается:

- изменять историю событий;

- удалять Business Events;

- изменять подтверждённые Agreement;

- изменять опубликованные Deliverable;

- изменять архивные объекты;

- обходить жизненный цикл объектов;

- изменять состояние объекта напрямую.

Administrator дополнительно запрещается:

- принимать коммерческие решения;

- изменять стоимость проекта;

- изменять условия сотрудничества;

- завершать проекты;

- принимать результаты работ.

External Service запрещается:

- создавать бизнес-объекты;

- изменять бизнес-решения;

- инициировать коммерческие действия.

Все действия External Service проходят через проверку платформой.

**6. Правила проверки полномочий**

Перед выполнением любого действия платформа последовательно проверяет:

1.  Подлинность пользователя.

2.  Активность учётной записи.

3.  Роль пользователя.

4.  Принадлежность проекта.

5.  Текущее состояние объекта.

6.  Дополнительные ограничения.

7.  Допустимость соответствующего Business Event.

Только после успешного завершения всех проверок действие считается разрешённым.

**7. Делегирование полномочий**

В версии 1.0 платформы делегирование полномочий не поддерживается.

Каждое действие выполняется исключительно пользователем, обладающим соответствующей ролью.

Поддержка временного делегирования может быть реализована в последующих версиях платформы.

**8. Архитектурные принципы**

**Бизнес важнее полномочий**

Полномочия существуют для реализации бизнес-процессов.

Они не являются самостоятельной частью платформы.

**Отсутствие универсальных прав**

В платформе отсутствует роль, обладающая неограниченными полномочиями.

Каждое действие требует отдельного разрешения.

**Неизменяемость истории**

Никакая роль не может удалить историю событий проекта.

История является частью бизнес-ценности платформы.

**Проверка перед выполнением**

Любое изменение бизнес-состояния возможно только после успешной проверки полномочий.

**Автоматизация не принимает решений**

System реализует утверждённую бизнес-логику.

System не принимает экспертных, коммерческих или организационных решений самостоятельно.

**9. Заключительные положения**

Permission Model определяет правила авторизации всех бизнес-действий платформы.

Все программные компоненты, пользовательские интерфейсы, API и автоматические процессы обязаны соблюдать настоящую модель полномочий.

Изменение Permission Model допускается только после утверждения соответствующего архитектурного решения.
