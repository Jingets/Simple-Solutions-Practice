- 🔴 **Critical** — блокирует генерацию кода/документов или создаёт неразрешимую двусмысленность для AI-агента;

## ЭТАП 1. Метауправление документацией: приоритет и «единственный источник истины»

Вся система AI-инструкций держится на одной идее: *«при конфликте документов побеждает документ с более высоким приоритетом»*. Проверка показала, что **самого приоритета в проекте три разных, взаимоисключающих версии**.

### Находка 1.1 🔴 Три несовпадающие таблицы приоритета документации

| Источник | Заявленный порядок (от высшего к низшему) |
|---|---|
| `README.md` (корень репозитория) | M → E → R → B → X → C → A (7 разделов, **S не упомянут вообще**) |
| `docs/AI/AI-001. How to Read SSP Documentation.md` | M → E → R → B → X → C → S → A (8 пунктов, но внутри списка дважды используется номер «4»: «4. B» и «4. X ↴» — техническая опечатка нумерации) |
| `docs/human/S - стандарты/S-006 Стандарты разработки ИИ.md` | **A → E → R → M → S** (5 пунктов; B, X, C вообще не упомянуты, а порядок инвертирован: Architecture (A) объявлена высшим приоритетом, Module Specification (M) — четвёртым!) |

Это не редакционная мелочь. AI-002/AI-005 буквально предписывают агенту останавливаться при конфликте документов и обращаться к приоритету, чтобы разрешить конфликт. Но если два «источника истины о приоритете» противоречат друг другу, у AI нет детерминированного способа решить, чей приоритет главнее — сам механизм разрешения конфликтов недоопределён. Это системный, а не точечный дефект.

### Находка 1.2 🟠 Циклическая инверсия зависимостей «B/C → E»

Практически каждый документ серии B и C в разделе «Заключительные положения» объявляет себя **основой для E-001** (и часто для других E-документов):
- B-006 → «основа для… E-001»;
- C-001 → «основа для… E-001»;
- C-002, C-003, C-004, C-005, C-006, C-007, C-008, C-009 → все аналогично объявляют себя основой для E-001 (и иногда для E-002…E-008).

Но согласно приоритету из README/AI-001, **E имеет более высокий приоритет, чем B и C** (E=2, B=4, C=6). Получается смысловая петля: документ с низшим приоритетом (C) декларирует себя фундаментом документа с высшим приоритетом (E), то есть при возникновении противоречия между ними формально должен победить E (по таблице приоритета), но содержательно C явно претендует на роль первоисточника. Это не техническая циклическая зависимость (нет прямого A→B→A импорта), но это **логическая инверсия иерархии авторитетности**, которая на практике будет создавать споры «какой документ правит».

### Находка 1.3 🟡 R описан как «мост» между B/C и E, но приоритетно стоит выше обоих

`docs/human/R - системные сервисы/README.md`: «Раздел R… является мостом между архитектурой (разделы A, B, C) и реализацией (раздел E)». По смыслу «мост» должен опираться на архитектуру и обслуживать реализацию, т.е. быть *ниже* архитектурных разделов по авторитетности. Но по таблице приоритета R (=3) стоит выше B (=4) и C (=6). Формально не противоречие, но термин «мост» вводит в заблуждение относительно фактической иерархии.

### Рекомендации к Этапу 1
1. Утвердить **единственную** таблицу приоритета в одном документе (предлагается — новый `A-000 Governance & Priority Model`), остальные документы (README, AI-001, S-006) должны **ссылаться**, а не дублировать список.
2. Убрать из S-006 собственную инвертированную таблицу приоритета — она должна цитировать A-000.
3. Исправить дублирование номера «4.» в AI-001.
4. Явно зафиксировать: если нижестоящий по приоритету документ (B/C) фактически является источником требований для вышестоящего (E) — это нормально (архитектура черпает бизнес-требования из B), но **при прямом текстовом противоречии** побеждает документ с более высоким приоритетом. Это нужно явно проговорить, иначе правило неприменимо на практике.

## ЭТАП 2. Сквозные противоречия между разделами

### Находка 2.1 🔴 Два несовместимых технологических стека — самое серьёзное расхождение во всей документации

`E-003 Технологический стэк` (статус **Approved**) утверждает:
- Backend: **C# 13 / ASP.NET Core 9 / .NET 9 LTS**
- ORM: **Entity Framework Core**
- Frontend: **Vue 3 / TypeScript / PrimeVue / Tailwind**
- Messaging: **NATS JetStream**
- AI Gateway: **LiteLLM + Ollama**

`E-004 Архитектура бэкэнда` (Approved) детально описывает **.NET Clean Architecture** (Api/Application/Domain/Infrastructure/Contracts/Tests, PascalCase-конвенции, Transactional Outbox на EF Core).

Однако **весь раздел M (M-101…M-107), весь раздел R (R-001, R-002), весь раздел X (X-005, X-006, X-007) и весь раздел S (S-001, S-002, S-003)** без единого исключения используют:
- Backend: **Python 3.12/3.13, FastAPI, SQLAlchemy 2.x, Alembic**
- Frontend: **React + TypeScript + Vite** (X-006 прямо: «React 18+, TypeScript, Vite, React Router, TanStack Query, Tailwind CSS»)
- Именование БД: **snake_case** (S-003, X-002) — прямо противоположно PascalCase-конвенции E-005 («Project», «CreatedAt» как имена колонок).

Дополнительно `AI-E-017.yaml` (машинная спецификация SDK) указывает третий вариант: `output.language: typescript`.

**Итог: в проекте фактически существуют ТРИ конкурирующих технологических стека (C#/.NET, Python/FastAPI, TypeScript-SDK), и ни один документ не объясняет, какой из них актуален для Pilot MVP, а какой — для «зрелой» версии платформы.** Ни E-003, ни E-004, ни E-005 не помечены как «целевая архитектура после MVP» — они имеют статус Approved наравне с M/X/R/S, которые используют другой стек. Для AI-агента, работающего по AI-001/AI-002 (приоритет M > E), формально должен победить Python (M выше E), но нигде это явно не написано, и разработчик, впервые открывший E-003 как «утверждённый стандарт», получит прямо противоположные инструкции.

### Находка 2.2 🟠 Три разные модели жизненного цикла Project

| Документ | Состояния Project |
|---|---|
| `M-001`, `X-001`, `X-002`, `X-004`, `M-106` | DRAFT → IN_PROGRESS → ON_HOLD → WAITING_CLIENT → REVIEW → COMPLETED → CLOSED (7 статусов) |
| `B-002 Business State Model` (§11 Project) | Preparing → Awaiting Payment → Active → On Hold → Completed → Archived (PJ-01…PJ-06, 6 статусов, другие названия) |
| `M-105` | Явно называет **AWAITING_PAYMENT** отдельным статусом проекта («проект может находиться в статусе AWAITING_PAYMENT») |
| `X-001` | Прямо **опровергает** M-105: «Статус AWAITING_PAYMENT не выделен в отдельное состояние… отображается как DRAFT с флагом offer_sent=true» |

То есть B-002 (Approved, «нормативный документ бизнес-модели») описывает вообще другую модель состояний Project, чем X-001/X-004 (Approved, доменная модель для реализации), а M-105 (MVP-модуль, P0, обязательный) противоречит X-001 в пределах одного milestone.

### Находка 2.3 🔴 B-серия описывает бизнес-модель, которой физически нет в X/M/R

`B-001 Бизнес-модель` определяет 15 сущностей: **Partner, Contact, Inquiry, Discovery Meeting, Proposal, Agreement, Cooperation Format, Project, Project Stage, Deliverable, Document, Payment, Event, Notification, Workspace.**

`X-001 Доменная модель` (единственный источник для генерации ORM/БД/API) определяет **12 совсем других сущностей**: User, Customer, Lead, Project, Check-up, Estimation Report, Offer Contract, Project Workspace, Artifact, Business Event, System Event, Acceptance Certificate, Organizational Memory Entry.

**Discovery Meeting, Proposal, Agreement, Contact, Partner, Cooperation Format, Project Stage, Deliverable — присутствуют в B-001/B-002/B-004/B-005/B-006 как полноценные бизнес-объекты со своими состояниями и правами доступа, но НЕ существуют ни в X-001 (домен), ни в X-002 (физическая модель), ни в R-001 (список модулей: `lead_intake, checkup, offer_contract, project_execution, acceptance_certificate, organizational_memory` — нет `proposal/`, `agreement/`, `discovery_meeting/`).**

Последствия:
- `B-004 Модель полномочий` содержит права на действия «Создать Agreement», «Подтвердить Agreement», «Принять Proposal» и т.д. — для сущностей, которых не существует в реализации;
- `B-006 Automation Blueprint` (Approved!) описывает автоматический процесс **AP-004 «Принятие Proposal»**, который создаёт Agreement + Project + Workspace + Offer + Invoice **одновременно** — это прямо противоречит M-104/M-105, где Offer формируется только после отдельного шага Estimation, причём **вручную** консультантом («Опубликовать оценку»), а не автоматически;
- `B-003 Business Event Catalogue` (заявлен как «единственный допустимый механизм запуска автоматизации») не содержит НИ ОДНОГО события из фактически используемых в M-104…M-107: нет `CheckupCompleted`, `ProjectEstimated`, `OfferPublished`, `OfferAccepted`, `ProjectCompleted`, `ProjectClosed`. Каталог обрывается на EV-020 (Agreement Cancelled) и не описывает вообще тот процесс, который реализует MVP.

Это не мелкая нестыковка — это означает, что **половина «Approved»-документации раздела B описывает архитектуру, параллельную и несовместимую с MVP**, без единого документа-моста, который бы явно сказал: «для Pilot MVP Proposal/Agreement/Discovery Meeting не реализуются, их роль выполняют Estimation Report/Offer Contract».

### Находка 2.4 🟠 Несовпадение имён событий для одного и того же факта

| Факт | Имя в X-001/X-004 | Имя в M-105 | Имя в knowledge/contracts/ofr.yaml |
|---|---|---|---|
| Оплата подтверждена → проект переходит в работу | `ContractAccepted` | `OfferAccepted` | `accepted: OfferAccepted` |
| Договор-оферта сформирован/отправлен | — | `OfferPublished` | `created: OfferGenerated` |

`ofr.yaml` (машинная спецификация, единственный канонический источник по document-standard.md) использует `trigger: ProposalApproved` — событие, которого **нет ни в одном каталоге событий** (в B-003 есть только `Proposal Accepted`, с другим написанием и без связи с Offer вообще, а M-105 никогда не публикует `ProposalApproved`, так как в MVP-модели Proposal не существует — см. находку 2.3). Это означает, что если генератор документов будет буквально следовать `ofr.yaml`, автоматическое формирование OFR **никогда не запустится**, потому что событие-триггер никогда не будет опубликовано.

### Находка 2.5 🔴 Organizational Memory одновременно «вне MVP» и «обязательна для MVP»

- `M-001` (дорожная карта MVP): «До завершения MVP не реализуются: … Organizational Memory».
- `docs/AI/AI-000. Read Me First.md`: «Do Not Build: … Organizational Memory».
- `M-108`: статус «MVP (принципы)», приоритет **P1** (не P0!) — то есть сам M-108 признаёт, что это не обязательный для MVP модуль, а только принципы на будущее.
- Но `X-008 MVP Последовательность реализации` включает **Этап 14 (Organizational Memory)** и **Этап 15 (Repository Optimization)** как обязательные стадии Milestone 3, с тестами и Definition of Done, и — что критично — **Этап 16 (MVP Completion, финальный E2E-тест)** требует шагов «9. Формирование Organizational Memory Entry» и «10. Оптимизация памяти (проверка, что дубли удалены)» как условие прохождения приёмочного теста всего MVP.

Итог: один документ (M-001/AI-000) прямо запрещает делать Organizational Memory в рамках MVP, другой документ (X-008) делает её обязательным условием прохождения приёмки MVP. Это блокирующее противоречие для планирования релиза.

### Находка 2.6 🟠 NATS JetStream: одновременно «не нужен» и «обязательный контейнер MVP»

- `M-101` (Platform Kernel, P0): «Не реализовывать… Event Bus» — явно исключён из первой версии.

Компонент, явно исключённый M-101, у X-007 значится обязательным для запуска MVP через `docker compose up -d`.

### Находка 2.7 🟡 Ценообразование: фиксированный прайс-лист vs произвольная оценка консультанта

`knowledge/services/prc.yaml` определяет фиксированные цены по каждой услуге (например, CHECKUP = 30 000 ₽, модель `fixed`), и `knowledge/contracts/ofr.yaml`/`knowledge/accounting/inv.yaml` берут переменные `{{pricing.price}}` из PRC-001 как единственный источник стоимости. Но `M-104` (Project Estimation) описывает **произвольную оценку стоимости консультантом** («Определить стоимость проекта» вручную, без ссылки на PRC-001), и именно Estimation Report, а не PRC-001, служит источником стоимости для Offer Contract (M-105: «на основании утверждённой оценки проекта»). Неясно, что имеет приоритет — фиксированный прайс из каталога услуг или ручная оценка консультанта — knowledge/ и M-104 описывают два разных механизма ценообразования без явного разграничения (например: «для SRV-001/002 — фикс. прайс, для SRV-003 (custom_price: true) — ручная оценка» — такое разграничение подразумевается полем `custom_price` в `prc.yaml`, но нигде не описано текстом).

### Находка 2.8 🟡 knowledge/fieldwork описывает более богатый процесс, чем может сохранить доменная модель

`knowledge/fieldwork/README.md` определяет полноценный конвейер: Request Package → Documents → Interview → Observation → Metrics → Findings → Report, с отдельными YAML/шаблонами `REQ`, `INT`, `OBS`, `MET`, `FND`. Однако `X-001`/`X-002` определяют сущность **Check-up** только с полем `summary` (текст) и версией/статусом — **нет отдельных таблиц/сущностей для Interview, Observation, Metrics, Findings.** `M-104` (модуль Check-up для MVP) тоже не упоминает Observation/Metrics/Findings — там только два Capability: `diagnostic_interview` и `project_estimation`, результат — единый `Check-up Report`. Получается, что богатая методология `knowledge/fieldwork` не имеет пути персистентности в реализации MVP — она либо избыточна для MVP, либо модель данных неполна.

## ЭТАП 3. Циклические зависимости и нарушение уровней архитектуры

### Находка 3.1 🟠 Дублирование идентификаторов внутри одного документа (E-014)

`E-014 Архитектура рабочих модулей` использует префикс **MC-** для двух совершенно разных наборов правил:
- §5 «Module Contract» → `MC-001…MC-005` (правила контракта модуля: ID, версия, Capability, зависимости, init/shutdown);
- §12 «Module Catalog» → `MC-001…MC-005` (правила каталога модулей: содержит сведения, обновляется автоматически и т.д.)

Одинаковые коды используются для двух не связанных концепций внутри одного файла — при автоматическом парсинге/цитировании (например, AI-агентом, ссылающимся на «см. MC-003») невозможно понять, о каком правиле речь. Это же отражено и в собственном README раздела E, где E-014 помечен как «❌ Критическая доработка (дублирование разделов 13–14)».

### Находка 3.2 🟠 Дублирование идентификаторов внутри B-006

`B-006 Схема автоматизации` использует префикс **AP-** дважды:
- §4 «Каталог автоматических процессов» → `AP-001…AP-013` (конкретные процессы: «Обработка нового Inquiry», «Подготовка Proposal» и т.д.);
- §8 «Архитектурные принципы» → `AP-001…AP-007` (принципы: «Автоматизация следует за бизнесом», «Событие первично» и т.д.)

Оба набора начинаются с `AP-001`, но описывают разные вещи. Ссылка «AP-001» в этом документе неоднозначна.

### Находка 3.3 🔴 Три несовместимых модели жизненного цикла «модуля» одновременно

| Документ | Состояния жизненного цикла модуля |
|---|---|
| `E-017 Module SDK` §4 | Install → Initialize → Register Manifest → Register Capabilities → Register Event Subscriptions → Ready → Running → Stopping → Dispose (9 шагов) |
| `E-014` §22 (Module States) | Registered → Initializing → Ready → Degraded → Unavailable → Stopping → Stopped (7 состояний, есть Degraded, которого нет в E-017) |
| `R-002` (таблица переходов) | Registration → Initialization → Active → Suspended → Disabled → Removed (6 состояний, совсем другие названия: «Active» вместо «Ready/Running», есть «Suspended/Disabled», которых нет ни в E-017, ни в E-014) |

Три канонических документа одного раздела (E-014, E-017) и контрактный документ R-002, который должен реализовывать именно то, что описывает E-017/E-014, задают **три разные конечные автоматы** для одного и того же понятия. Ни один документ не ссылается на два других как на «то же самое, изложенное иначе» — читатель обязан сам догадаться, что это должно быть одно понятие.

### Находка 3.4 🟡 Нарушение уровня: технический паттерн в философском разделе A

`A-006 Источник достоверной информации` (раздел A — «философия», по декларации README не должен содержать техническую реализацию) вводит конкретный технический механизм: «Для каждого Business Object должен быть определён **Snapshottable State** — точка, с которой можно начинать восстановление без пересчёта всей истории (например, ежедневный снепшот)». Это уровень C-001/E-005 (техническая архитектура/архитектура данных), а не A (принципы). Формально небольшое нарушение, но показательное — граница между «зачем» (A) и «как» (C/E) в документе A-006 стирается.

### Находка 3.5 🟡 E-017 ссылается на несуществующий документ

`E-017 Модуль SDK` §18 «Связанные документы» ссылается на **C-011 Архитектура Platform Kernel** — такого документа не существует нигде в предоставленном корпусе (раздел C по собственному README содержит только C-000…C-010). Это «висячая» ссылка.

### Рекомендации к Этапу 3
1. Переименовать один из двух конфликтующих `MC-` наборов в E-014 (например, «Module Catalog» → `MCT-001…005`).
2. Переименовать один из двух `AP-` наборов в B-006 (например, архитектурные принципы → `AR-001…007`, оставив `AP-` только за процессами автоматизации).

## ЭТАП 4. Готовность knowledge/ к генерации документов

### Общая структура
knowledge/ содержит: `services/` (SRV, PRC), `contracts/` (OFR), `accounting/` (INV), `reports/` (REP), `fieldwork/` (REQ, INT, OBS, MET, FND). Каждый YAML в целом соответствует схеме `document-standard.md`.

### Находка 4.1 🔴 Отсутствует шаблон/спецификация для Acceptance Certificate (ACT)

`M-107` (P0, обязательный модуль MVP) требует создания Artifact **Acceptance Certificate** («Регистрация документа: Создать Artifact: Acceptance Certificate»). `document-standard.md` явно перечисляет `ACT` как тип документа платформы («Акт выполненных работ»). Но **в предоставленном дереве knowledge/ нет ни `ACT.yaml`, ни `ACT.template.md`** — ни в существующих каталогах, ни в отдельном каталоге `certificates/`, который упомянут в `knowledge/README.md` как часть структуры («certificates/»), но не содержит файлов. Это блокирующий пробел: без этого файла нельзя автоматически сгенерировать финальный документ, обязательный для завершения любого MVP-проекта (M-107 — последний шаг перед закрытием проекта).

### Находка 4.2 🟡 CRT (Сертификат) объявлен, но нигде не используется

`document-standard.md` определяет тип `CRT` (Сертификат) как отдельный от `ACT` документ. `M-001` упоминает финальный шаг пайплайна как «…Execution → Certificate» — неясно, это ACT или CRT. Ни один M-модуль не описывает генерацию CRT. Рекомендуется либо удалить CRT из стандарта (если не нужен в обозримом будущем), либо явно указать что CRT относится к SRV-004 (Стратегическое сопровождение) или другому формату, для которого он предусмотрен.

### Находка 4.3 🟡 Proposal упоминается в процессных диаграммах knowledge/, но не имеет спецификации-документа

`knowledge/services/README.md` и `knowledge/contracts/README.md` рисуют пайплайн `Service → Pricing → Proposal → Offer → Invoice → Project`, включая шаг «Proposal», но ни `document-standard.md`, ни фактические файлы knowledge/ не содержат `PRP.yaml`/`PRP.template.md`. Учитывая находку 2.3 (Proposal не реализуется в MVP), это либо унаследованный от B-серии рудимент диаграммы, который надо убрать из README knowledge/, либо признак того, что Proposal всё же должен быть отдельным артефактом.

### Находка 4.4 🟠 Триггеры генерации ссылаются на несуществующие/несогласованные события (детали см. находку 2.4)
- `ofr.yaml`: `trigger: ProposalApproved` — событие не публикуется никаким модулем.
- `inv.yaml`: `trigger: OfferGenerated` — не совпадает с M-105 (`OfferPublished`).
- `ofr.yaml.business_events.created: OfferGenerated` — третье имя того же факта, отличное от обоих вышеперечисленных.

### Находка 4.5 ⚪ document-standard.md содержит два несовпадающих списка «обязательных полей»

В разделе «Единая структура YAML» перечислено 15 полей (`id, title, version, document_type, status, template, description, inputs, sources, generation, outputs, business_events, storage, editable, language`), а чуть ниже в разделе «Обязательные поля YAML» — другой список из 8 полей (`id, title, version, document_type, generated, project_id, template, status`), включающий `generated` и `project_id`, которых нет в первом списке, и не включающий `sources/outputs/business_events` и т.д. Это внутреннее противоречие одного документа-стандарта — неясно, какой список действителен.

### Находка 4.6 🟡 Часть fieldwork-YAML не содержит поле `sources`

`int.yaml`, `obs.yaml`, `met.yaml`, `fnd.yaml` не содержат поле `sources` (в отличие от `req.yaml`, `ofr.yaml`, `inv.yaml`, `rep.yaml`, где оно есть). Формально это может быть осознанно (первичные документы не имеют «источников»), но стандарт (см. находку 4.5) не разъясняет, когда поле обязательно, а когда нет.

1. **Создать `knowledge/certificates/act.yaml` + `act.template.md`** — блокирующая задача перед стартом M-107.

3. Убрать шаг «Proposal» из диаграмм knowledge/services и knowledge/contracts, либо создать `PRP.yaml`, если Proposal всё же нужен (зависит от решения по находке 2.3).
4. Синхронизировать `trigger`/`business_events` во всех YAML с итоговым, согласованным набором имён Business Events (после исполнения рекомендации 4 из Этапа 2).

## ЭТАП 5. E-017 Module SDK — достаточно ли спецификаций для AI-генерации кода

**Вывод: недостаточно.** E-017 задаёт хороший верхнеуровневый контракт (принципы, состав Manifest, Capability Contract, Context API, Artifact API, Event API), но для безопасной автогенерации кода AI-агенту не хватает следующего:

### Находка 5.1 🔴 Конфликт жизненного цикла модуля (см. находку 3.3) — придётся выбрать одну из трёх версий, иначе Kernel и модули не смогут синхронизироваться по состояниям.

### Находка 5.2 🔴 Нет формальной схемы (JSON Schema/OpenAPI) — только списки имён полей
Manifest, Capability Contract и Capability Result описаны как перечни названий полей (`module_id`, `version`, `capabilities`…) без типов данных, форматов, обязательности, ограничений длины. Пример JSON есть только в R-002 (не в самом E-017!), и он не покрывает все поля, перечисленные в E-017/AI-E-017.yaml. Для code-gen нужна единая машиночитаемая схема (например, JSON Schema файл), которой сейчас нет вообще ни в E-017, ни в AI-E-017.yaml (последний — тоже просто список имён, без типов).

### Находка 5.3 🟠 E-017 не содержит формата Capability Result (Error Contract)
Формат ответа `{status, result, errors, warnings, generated_artifacts, published_events}` определён только в **R-002**, но E-017 (главный SDK-документ) даже не ссылается на R-002 в этой части. AI, читающий только E-017 (согласно AI-001, читать нужно «минимально необходимое»), не узнает про этот контракт вообще.

### Находка 5.4 🟠 Нет таксономии кодов ошибок на уровне Capability
`E-006 Архитектура API` определяет коды ошибок только для HTTP API (`errorCode`, `message`, `correlationId`), но не для внутреннего вызова Capability. Модулю нужно из чего-то формировать `errors: []` в Capability Result — единого перечня допустимых кодов ошибок для Capability-уровня нет.

### Находка 5.5 🟡 Нет явного упоминания Shared Library / Dependency Contract в E-017
R-002 вводит «Dependency Contract» (модуль зависит только от Kernel и Shared Library), но E-017 не упоминает Shared Library вообще, хотя это ключевое архитектурное ограничение (запрет прямых зависимостей между модулями).

### Находка 5.6 🟡 Нет механизма идемпотентности на уровне Capability Contract
E-001 (ECR-003) и B-006 требуют идемпотентности всех операций, но ни в E-016 (Capability Specification), ни в E-017 нет обязательного поля вроде `idempotency_key` или явного описания, как Kernel гарантирует неповторное выполнение одной и той же Capability при повторной доставке события.

### Находка 5.7 🟡 Несогласованность целевого языка реализации SDK
`AI-E-017.yaml.output.language: typescript` — притом что весь остальной backend (M/R/X/S) — Python, а E-003/E-004 — C#. Это третий вариант языка для одного и того же артефакта (см. находку 2.1). Неясно, TypeScript SDK — это для frontend-модулей, для отдельного slim-SDK, или ошибка копирования шаблона.

### Что ещё нужно AI для безопасной реализации модулей (сводка)
1. Единая, финально выбранная модель жизненного цикла модуля (см. рекомендацию Этапа 3).
2. JSON Schema для Module Manifest, Capability Contract, Capability Result, Error Contract — в одном файле, с версией.
3. Явная ссылка E-017 → R-002 (или перенос Error/Result Contract целиком в E-017, а R-002 пусть на него ссылается).
4. Таксономия кодов ошибок Capability-уровня (отдельно от HTTP-кодов E-006).
5. Определение Shared Library (состав, расположение — `backend/shared/`, уже упомянуто в R-002 — но не в E-017) и синхронизация терминологии между E-017/R-002.
6. Механизм идемпотентности Capability (ключ, окно дедупликации, где хранится).
7. Разрешение конфликта языка реализации (Python/TS/C#) — см. рекомендацию Этапа 2.1.
8. Исправление/удаление ссылки на несуществующий C-011 (находка 3.5).

## ЭТАП 7. Соответствие шаблонов knowledge/ физической модели данных (X-002/X-003)

Этот этап проверяет не декларации, а **фактическую вычислимость** переменных `{{...}}` в шаблонах `.template.md` — можно ли их подставить, опираясь только на поля, которые реально существуют в X-001/X-002/X-003.

### Находка 7.1 🔴 Сущность «Contractor» используется во всех юридических документах, но не существует в доменной модели

`ofr.template.md`, `inv.template.md` (и, по аналогии, будущий `act.template.md`) используют `{{contractor.legal_name}}`, `{{contractor.inn}}`, `{{contractor.ogrn}}`, `{{contractor.address}}`, `{{contractor.bank_account}}`, `{{contractor.bank_name}}`, `{{contractor.bank_bik}}`, `{{contractor.bank_corr}}`. Ни в `X-001 Доменная модель`, ни в `X-002 Физическая модель`, ни в `X-003` (Project/Artifact) нет сущности **Contractor** (реквизиты исполнителя — самой платформы SSP). Это не бизнес-объект в смысле B-001 (там его тоже нет), это, по сути, статические реквизиты компании-владельца платформы. Сейчас для этих данных **нет ни таблицы, ни конфигурационного объекта, ни API** — их негде взять программно.

### Находка 7.2 🟡 Наименование «Client» в шаблонах vs «Customer» в доменной модели

Все шаблоны (`ofr.template.md`, `inv.template.md`) используют переменную `client.*` (`client.organization`, `client.inn`, `client.email`…), а `X-001`/`X-002` называют эту сущность **Customer**. Формально это может быть просто разный человекочитаемый лейбл для одного и того же объекта, но нигде это явно не сопоставлено — при автогенерации кода (Pydantic DTO/Jinja-контекст) разработчик должен либо переименовать поле контекста рендеринга в `client`, либо переименовать сущность в `Client` во всей модели. Ни один документ не фиксирует это решение.

### Находка 7.3 🔴 Нет связи Project ↔ Service ни в одной физической таблице

Шаблоны `ofr.template.md`/`inv.template.md` требуют `{{service.name}}`, `{{service.description}}`, `{{service.deliverables}}`, `{{pricing.price}}`, `{{pricing.currency}}` — то есть нужно знать, **какую именно услугу (SRV-XXX) купил конкретный проект**. Проверка `X-002 Физическая модель данных`:
- таблица `projects`: id, lead_id, status, opened_at, closed_at, created_by, updated_by — **нет service_id**;
- таблица `estimation_reports`: id, project_id, checkup_id, estimated_hours, estimated_cost, complexity, version — **нет service_id**;
- таблица `offer_contracts`: id, project_id, estimation_report_id, amount, payment_status, contract_status, version — **нет service_id**.

Ни в одной из трёх таблиц, теоретически способных хранить эту связь, поля `service_id`/`service_code` не предусмотрено. `X-003-003` (спецификация Project) тоже не содержит его. Это значит, что **при буквальной реализации по X-002 платформа физически не сможет определить, какую услугу каталога SRV она продала по конкретному проекту** — а значит, не сможет автоматически сформировать OFR/INV, где `{{service.name}}` — обязательная переменная. Это более серьёзный пробел, чем находки 2.7/4.3: там речь о неоднозначности процесса, здесь — об отсутствии самого поля в схеме БД.

### Находка 7.4 🟡 Переменные `{{execution.duration_days}}` (ofr.template.md) не имеют источника
`ofr.template.md`: «Исполнитель обязуется завершить оказание услуги в течение **{{execution.duration_days}} рабочих дней**». `ofr.yaml.inputs` не содержит `execution` вообще (список: project, contractor, client, contract, service, pricing). Ближайший кандидат-источник — поле `execution_days` в `knowledge/services/srv.yaml` (там оно определено на уровне услуги, например Checkup = 5 дней) — то есть это, вероятно, `service.execution_days`, а не отдельный объект `execution`. Имя переменной в шаблоне не совпадает ни с одним реально существующим полем ни в SRV, ни в Estimation Report (`estimated_hours`, не дни).

### Находка 7.5 🟡 `rep.template.md` использует `project.start_date` / `project.end_date`, которых нет в X-001
X-001 определяет для Project поля `Opened At` / `Closed At` (`opened_at`/`closed_at` в X-002). Шаблон итогового отчёта использует другие имена (`project.start_date`, `project.end_date`). Мелкое, но реальное расхождение имён полей между генерируемым документом и физической моделью.

## ЭТАП 8. Аудит контрактов API (S-002 vs E-006 vs R-002)

### Находка 8.1 🔴 Два несовместимых формата ответа API в двух «действующих» стандартах

`S-002 Стандарты API` (статус MVP) определяет:
```
Успех:  { "success": true, "data": {}, "meta": {} }
Ошибка: { "success": false, "error": { "code": "", "message": "", "details": {} } }
```

`E-006 Архитектура API` (статус **Approved**) определяет:
```
Ошибка: { "errorCode": "PROJECT_ALREADY_ARCHIVED", "message": "...", "correlationId": "...", "timestamp": "..." }
```

Это два структурно разных контракта для одной и той же концепции (тело ответа об ошибке): разный набор полей (`error.code` вложенный объект vs плоский `errorCode`), разный набор метаданных (`details` vs `correlationId`+`timestamp`, у S-002 нет `correlationId` вообще, у E-006 нет `details`), и разная обёртка успешного ответа (E-006 вообще не описывает единую обёртку `{success, data, meta}` — согласно RRM-002/RRM-003 E-006, ответ должен быть «минимальным» DTO без единой обёртки). Frontend (X-006), написанный по одному контракту, не будет совместим с Backend, реализованным по другому.

### Находка 8.2 🟡 Пагинация: разное имя параметра размера страницы
- S-002: `page`, `page_size` (snake_case, соответствует общему стилю S-002 для URL/параметров);
- E-006: `page`, `pageSize` (camelCase).

### Находка 8.3 🟡 Сортировка: разный регистр значения параметра
- S-002: параметр `sort` без примеров формата значения;
- E-006: `sort=CreatedAt` / `sort=-CreatedAt` — значение параметра в PascalCase (имя колонки БД), что противоречит собственному правилу E-006 «API описывает бизнес-возможности, а не внутреннее устройство» — использовать имя колонки БД (`CreatedAt`, ещё и в PascalCase, характерном для C#/EF Core, а не для Python/snake_case стека) как значение публичного query-параметра — утечка деталей реализации на уровень контракта, вдобавок ещё раз подтверждающая находку 2.1 (C#-конвенции просочились в документ, который должен быть нейтральным к стеку).

### Рекомендации к Этапу 8
1. Выбрать один формат ответа (рекомендуется — вариант S-002, как более простой и уже согласованный со стилем Python/FastAPI; либо явно спроектировать конвертацию между слоями, но два публичных контракта в одном проекте недопустимы).
2. Унифицировать `page_size`/`pageSize` в пользу snake_case (согласуется с S-002/S-003/общим Python-стеком).
3. Убрать PascalCase-пример сортировки из E-006, заменить на нейтральный `sort=created_at`.

## ЭТАП 9. Аудит модели полномочий и аутентификации (B-004 vs C-004 vs X-008)

### Находка 9.1 🔴 Роли B-004 не совпадают с ролями, реально реализуемыми в MVP

`B-004 Модель полномочий` (Approved) определяет 5 ролей: **Partner, Consultant, Administrator, System, External Service** — и строит на них полную матрицу из 23 бизнес-действий (создать Inquiry, принять Proposal, подтвердить Agreement и т.д.).

`X-008` Этап 4 (Authentication, единственное место, где вообще описана реализация ролей для MVP) создаёт только: **ADMIN, MANAGER, SYSTEM** — **ни «Partner», ни «Consultant», ни «External Service» в явном виде не заводятся как роли системы аутентификации.** При этом `AI-000` прямо говорит: «в MVP весь функционал доступен консультанту без разделения ролей. Клиент имеет доступ только к публичным документам (Offer, Certificate)» — то есть Partner (клиент) **вообще не проходит аутентификацию** в Pilot MVP (получает документы по прямой ссылке, без логина).

Следствие: **вся матрица B-004 неисполнима в Pilot MVP** — например, правило «Принять Proposal — разрешено только Partner» невозможно проверить программно, потому что Partner не имеет ни учётной записи, ни сессии, ни Identity в смысле C-004. Это не ошибка B-004 самого по себе (она описывает целевую, а не MVP-модель), но нигде явно не сказано «в Pilot MVP матрица B-004 не проверяется программно, вместо неё действует упрощённое правило: единственный залогиненный пользователь = Consultant = ADMIN/MANAGER».

### Находка 9.2 🟡 «Consultant» (B-004/B-002/B-006) vs «MANAGER» (X-008) — не сопоставлены явно
Ни один документ не говорит прямо: «роль MANAGER в X-008 реализует полномочия роли Consultant из B-004». Это должно быть зафиксировано хотя бы одной строкой в M-100 (см. рекомендацию Этапа 6.5).

### Находка 9.3 🟡 C-004 Identity & Trust Model — избыточна по масштабу относительно MVP
`C-004` (Approved) описывает 5 уровней доверия (TL-0…TL-4), Delegated Identity, Trust Escalation, Re-authentication для критичных операций и т.д. — полноценная enterprise-модель. Для Pilot MVP (по X-008 Этап 4) реализуется только: email+password → JWT, без каких-либо Trust Levels, эскалации или делегирования. Это не противоречие (C-004 — целевая архитектура), но при отсутствии пометки «Target/Post-MVP» создаёт тот же риск, что и находка 2.1 — разработчик, открывший C-004 как «утверждённый стандарт безопасности», может решить, что обязан реализовать TL-0…TL-4 в первой версии.

### Рекомендации к Этапу 9
1. В новом `M-100 Identity & Access (MVP)` явно зафиксировать: единственная используемая в Pilot MVP модель ролей — ADMIN/MANAGER/SYSTEM; Partner не аутентифицируется, получает документы по подписанной прямой ссылке (магической ссылке) без логина.
2. Явно сопоставить `Consultant` (B-004/B-002) ↔ `MANAGER` (X-008) как одну и ту же роль под разными именами на разных уровнях документации.
3. Пометить `C-004` как «Target Architecture» относительно Trust Levels/Delegation — эти механизмы не входят в Definition of Done Pilot MVP.
4. Явно исключить из проверки Definition of Done M-102/M-105 (Proposal Accepted / Agreement Confirmed — действия роли Partner из B-004), так как соответствующие сущности не реализуются (см. находку 2.3) — их права доступа в MVP неприменимы в принципе.

## Итоговый вывод

Документация SSP архитектурно продумана на уровне отдельных документов (глубина проработки E-серии, B-серии, C-серии впечатляющая), но **страдает от отсутствия единого контроля версий и синхронизации между «Approved»-документами разных разделов**. Ключевая системная проблема — не отдельные баги, а то, что в проекте одновременно живут (а) полная целевая архитектура (B, C, E — со своим стеком, событиями, сущностями) и (б) урезанная MVP-реализация (M, R, X, S — с другим стеком, другими событиями, другими сущностями), и **нет ни одного документа, который бы формально признавал это расслоение и управлял им**. Раздел `docs/AI/` частично компенсирует это (явно говорит «не строй Automation Engine, AI Agents» и т.д.), но делает это выборочно, не затрагивая стек, доменную модель и модель событий.

Рекомендованный первый шаг — не писать код, а закрыть **Этап 0** этого аудита: без него любой AI-агент, следующий AI-002/AI-003 буквально, обязан остановиться на первом же реальном использовании документации (например, при первой попытке понять, на чём писать backend).
